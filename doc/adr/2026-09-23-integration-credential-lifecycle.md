# Store connector credential material in Secrets; govern its lifecycle separately

- **Status:** Recommended for outbound connector implementation planning; not an implementation approval.
- **Date:** 2026-09-23
- **Decision scope:** Elsa Core outbound connector authorization and token lifecycle, assessed against `origin/main` commit `610790ec57ae9d5c334181d50c1e65f99613fd86`.

## Context

Outbound integrations need to connect accounts, resolve credentials during workflow execution, refresh credentials in background work, survive process restarts, and disconnect/revoke grants. These operations combine vendor-side state with Elsa-owned connection state. They also need tenant ownership and environment isolation. A database transaction cannot include an OAuth provider call, and the current generic Secrets manager has no lifecycle operation record or caller-supplied revision.

The current Secrets module provides useful encrypted storage, secret type/store abstractions, version metadata, management endpoints, and ambient-tenant persistence. However, `ISecretManager.RotateAsync` reads an aggregate, chooses the next version, retires the active version, and saves without an expected revision; EF `SaveAsync` copies the incoming version list. Existing uniqueness/concurrency logic protects create or deleted-name reuse, not concurrent rotations. `ISecretResolver` checks optional type/scope and resolves the latest active value. Its contracts do not carry actor, tenant, environment, use authorization, or a pinned version. The Secrets endpoints' view/write/delete/test permissions apply to management routes; direct in-process resolution is trusted-caller behavior.

The encrypted store protects `SecretPayload.Value` with the configured AES-GCM key but copies other metadata. The default protector has no key identifier or rotation/re-encryption workflow. The configuration store resolves deployment-owned values by configuration key; its `Write` capability writes only reference metadata and `Delete` does not remove configuration. Thus neither the current name/version API nor the configuration-backed store is by itself an outbound OAuth lifecycle manager.

External Authentication provides a useful pattern: it stages a unique managed secret, then uses a revision-checked connection pointer update and cleans up an unpublished or superseded reference. That module manages inbound identity-provider login connections and is host-scoped; it is precedent for lifecycle mechanics, not an outbound tenant-connection capability.

Provider token behavior also varies. Official Moneybird docs advise persisting both a currently non-expiring access token and its refresh token, and revoking either pair member revokes both. Slack documents optional one-time refresh-token rotation, short grace, token limits, and distinct token revoke versus uninstall operations. Treat these only as examples: each provider adapter must own and test its own rules.

## Decision

Use the existing `Elsa.Secrets` storage and protection abstractions for sensitive token material, and build a separate connector connection/lifecycle application service for connection metadata, ownership, environment binding, provider policy, refresh orchestration, concurrency, reconciliation, and authorization. Do not copy the Secrets encrypted store or add a second generic credential vault. Do not make the generic Secrets API itself responsible for OAuth protocol state.

The lifecycle service stores durable non-secret connection state: provider registration/account identifiers, owning tenant or platform scope, environment binding, scopes, lifecycle/status, current generation reference, expected revision, refresh lease/attempt state, provider policy identifier, and safe operation/audit identifiers. Tenant grants and platform OAuth client registrations have distinct owners and authorization policies. Tenant-supplied OAuth app credentials (BYO app) are outside this recommendation until separately scoped.

For each committed token set, create a fresh, unique Secrets record and publish its reference with a durable compare-and-swap on the connection revision. Keep access and refresh token values together in the encrypted `Value` envelope when the provider rotates them as a set. Do not put tokens, provider bodies, or sensitive headers in `SecretPayload.Metadata`; encrypted store metadata is copied in cleartext. Managed token-set secret records are intended to be immutable by lifecycle policy: create one generation per successful provider grant/refresh and move the connection pointer, rather than rotating one name in place. The current `SecretReference` resolves latest-active only and cannot pin an explicit version. Unique lifecycle-owned names are therefore only a convention until implementation provides an ownership marker and an enforced management guard that prevents generic callers from rotating or replacing those records. Current Secrets does not provide this guard. Keep the existing `ISecretResolver`, `ISecretManager`, and `SecretReference` public surfaces compatible for current consumers; add ownership enforcement through a compatible policy/management boundary or a separately reviewed additive contract.

For token caching, default short-lived access tokens to a bounded in-memory cache keyed by tenant, environment, connection, committed generation, and requested scope set. Invalidate entries when the connection pointer changes, or the connection is revoked or disconnected. Require an expiry safety margin before returning cached values. Persist the access token with the refresh token when the provider requires access-token survival across restart, documents a grace/recovery window that depends on retaining it, issues a non-expiring/long-lived token that is operationally needed after restart, or rotates access and refresh credentials as an inseparable durable pair. Persist any issued refresh token in Secrets. Provider policy and provider documentation override this default; do not classify a token as cache-only without evidence that it can be reacquired safely.

Refresh must be serialized by a durable per-connection claim/revision in the lifecycle store, not by the Secrets aggregate's version count or an in-process lock. After an upstream refresh, persist the replacement token set as a fresh secret generation, then compare-and-swap the connection pointer. A losing worker re-reads the connection and must not replay a consumed one-time refresh token. Record a durable operation/idempotency identifier before the provider call and associate staged encrypted generations with that operation so reconciliation can find them without reading token values into metadata or logs. Lease expiry fences stale local writes, but does not prove the provider request did not complete: do not let a takeover worker issue another call with the old one-time token while the earlier attempt's outcome is unknown. Reconcile the recorded attempt or move it to `RecoveryRequired` unless provider-specific semantics prove replay safe.

There is no distributed transaction with the provider. If the process loses the provider response or cannot persist a replacement after the provider may have consumed a one-time refresh token, mark the connection `RecoveryRequired` (or an equivalent safe reauthentication state) and do not automatically replay the old token unless that provider documents idempotency, grace, or safe recovery. If the replacement was encrypted and staged but pointer commit failed, reconciliation must find it by the durable operation ID and conditionally commit it against the expected connection revision when that operation is still current. If the provider outcome or replacement material is unavailable, do not discard the only recoverable state and reuse the possibly-consumed token; mark recovery/reauth required. Keep staged or superseded secret material until reference checks and provider policy permit cleanup. Local disconnect, provider token revocation, and provider installation uninstall are distinct actions and states. Disable local use immediately on disconnect; provider revocation/uninstall and secret cleanup follow documented provider semantics and an idempotent retry/reconciliation record.

All human and background resolution goes through the lifecycle service. It restores/validates the connection tenant and environment, authorizes the actor or narrowly scoped system operation, checks status/provider compatibility, then calls existing Secrets abstractions. The generic resolver remains a trusted low-level primitive and gains no implied caller permission. Logs, response DTOs, traces, audit/outbox payloads, and exception messages contain references/status/operation IDs only. This cannot guarantee redaction after a workflow author deliberately copies resolved cleartext into arbitrary workflow values or a third-party activity; that disclosure boundary must be documented and tested at product integration points.

Encryption-key delivery and rotation remain host/platform responsibilities until Elsa provides a key-ring contract. Every runtime replica that resolves a secret must access the same durable key material. Before production key rotation is claimed, define versioned key selection and a tested re-encryption/migration procedure; a single `SecretsOptions.EncryptionKey` switch can make old values unreadable. Environment promotion copies logical connection configuration only; each environment provisions its own secret generation and key context, and raw token values never enter exports.

## Alternatives considered

| Option | Assessment |
|---|---|
| Reuse `ISecretManager` as the complete connection/token lifecycle | Rejected. It has no connection ownership, provider operation state, refresh lease, expected-revision CAS, background tenant authorization, or upstream revoke/uninstall distinction. Its latest-active resolution and unconditional rotate/save are not enough to coordinate a one-time refresh across nodes. |
| Extend Secrets into a connector/OAuth lifecycle manager | Rejected for this integration boundary. It would conflate generic named secret values with provider grants, tenant connection state, upstream protocol behavior, and environment-specific ownership. A future generic expected-version/CAS capability may be useful independently, but this ADR does not assume or require it. |
| Build a dedicated encrypted connector-token store | Rejected. It duplicates existing encrypted value storage and creates a second secret-value boundary. Use Secrets for protected material and add only the lifecycle-specific durable state and operations needed by connections. |
| Separate lifecycle service backed by Secrets | Recommended. It keeps existing Secrets storage and consumer contracts, while assigning provider-aware concurrency, ownership, recovery, and disconnect behavior to the domain that can enforce them. |

## Compatibility and prerequisites

- Existing Secrets APIs and generic references remain source/binary compatible. The new service and connection lifecycle model are additive.
- Lifecycle integration must not infer that management permission grants runtime use permission. Connection manage/use/background policies need explicit definitions and tests.
- Current resolver references do not encode a version; unique, lifecycle-owned secret names are the safe generation boundary until an explicit pinned-reference contract is designed.
- The existing Secrets encryption setting has no key ring. Key delivery, multi-replica availability, and rotation/re-encryption are deployment prerequisites and product gaps, not capabilities provided by this decision.
- A separate inventory found duplicate public Secrets persistence package IDs across Core and Extensions, with divergent source trees. Decide package publisher/compatibility and migration ownership before any cross-repository package cutover; this ADR does not select one.
- No cloud vault, operating-system certificate store, outbound polling, webhook token renewal, or tenant connector support is implied by this recommendation.

## Consequences

The lifecycle service must have durable state and a testable state machine in addition to Secrets persistence. It must explicitly model ambiguous provider refresh outcomes, reconcile staged orphan generations and post-swap cleanup, and carry tenant/environment context into resumed workflows and background renewal. Implementations need fake-provider failure injection and multi-node concurrency tests before claiming safe refresh. Connector code may resolve token values only inside authorized, short-lived operations and must keep them out of general workflow data wherever possible.
