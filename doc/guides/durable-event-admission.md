# Configure and operate isolated durable event admission

This transport-independent boundary is for one reviewed in-process LocalWorkflowRuntime host with PostgreSQL admission and normal workflow definition/instance/runtime persistence. It is an offline implementation foundation, not a live Slack connection or Socket Mode acknowledgement adapter. See the [decision and guarantees](../adr/2026-10-08-durable-event-admission-and-isolated-execution.md).

## Prepare the host

Use `Elsa.Workflows.Admission`, `Elsa.Workflows.Admission.Persistence.EFCore` and `Elsa.Workflows.Admission.Persistence.EFCore.PostgreSql`. The ledger uses `AdmissionElsaDbContext`, separate from credential and workflow contexts, with migration `20261008040000_InitialAdmission` and default history table `__AdmissionMigrationsHistory`.

Select the existing PostgreSQL workflow definition, instance and runtime persistence modules too. Classic registration uses `UseAdmissionPersistence(feature => ...)` and its PostgreSQL `UsePostgreSql(...)`; set explicit TenantId, EnvironmentId, connection and migration options. Configure `Admission.Features.AdmissionFeature.Configuration` with an `AdmissionHostConfiguration` after the selected host services are registered. Shell registration uses `Admission.ShellFeatures.AdmissionFeature` and `PostgreSqlAdmissionPersistenceShellFeature`, with explicit Configuration/TenantId/EnvironmentId/ConnectionString. Select the corresponding normal workflow persistence Shell features separately. Admission's provider selection does not silently select workflow or credential persistence.

A host configuration requires exact audited concrete service types, allowed activity types and predefined subscription configurations. This is an executable support inventory, not a permissive list of interface names. Review actual registry/materializer/provider callbacks, notifications, invoker, logger generators, observer, storage drivers, commit services and execution-cycle registry. The isolated host replaces custom workflow/activity setup factories without running them, freezes known compositions, and rejects contributors. No arbitrary FastEndpoints/import/alteration routes, remote/Proto.Actor execution, autonomous background execution, second store-sharing executor or unaudited definition writer may remain invocable. Existing credential/grant services are reused; unsupported connection lifecycle and tenant mutations fail closed.

The concrete classic and Shell offline reference host is `test/workers/Elsa.Workflows.Admission.WorkerProcess/AdmissionRuntimeHost.cs`. Its synthetic artifact, tenant, clock, audit inventory and policy values are fixtures, not production defaults or approved live owner policy. Do not copy its test observer, gates or PostgreSQL counter/variable tables into a deployment. A selected live host requires its own audited inventory and owner-controlled activation settings.

## Provision inactive, then activate

1. Supply stable logical installation and subscription identities, trusted tenant/environment/channel, exact definition version and full content fingerprint. Do not derive installation identity from an envelope, reconnect or credential generation. Edits retain the subscription identity; retirement cannot reset it.
2. Supply every `AdmissionPolicy` value explicitly. Require identity horizon strictly beyond age plus skew, explicit late/invalid disposition, active and retained-record capacities, payload/event-ID byte bounds and bounded cleanup authority. Choose an explicit activation boundary. Never infer retention from a presumed Socket retry cutoff.
3. Prepare a fixed JSON workflow artifact with explicit identity/version/content, IsPublished=false and IsLatest=false. Normalize timestamps to supported PostgreSQL microsecond precision before provisioning. `AdmissionDefinitionFingerprint.Compute` binds the persisted full content; it canonicalizes valid stored JSON representation without equating executable input CLR kinds.
4. With the same guarded host inactive, call `AdmissionBootstrapService.ProvisionAsync(configuration, artifact)`. It serializes competing logical-definition/subscription coordinators, performs insert-or-verify with the actual management codec, and runs normal publication/verification only after definitive insertion.
5. Activate explicitly with the returned subscription revision using `ActivateAsync`. A null result is a lost/invalid CAS and does not authorize admission. Unknown bootstrap/publication outcome stays inactive/reconciliation. Never retry notifications by overwriting or importing the row. Repeat already verified bootstrap only verifies content; it does not republish.

No provisioning or activation creates credentials, delegates credential use or grants outbound reply authority. Existing exact-instance connection-use grants remain separately required and default-deny. Production policy and sandbox app/workspace/channel consent, delegation/reply binding, operator responsibility and credential bindings are live activation gates; explicit synthetic fixture values suffice for offline tests.

## Admit and execute

The later transport calls `AdmissionExecutionService.AdmitAsync` with provider event identity and payload after resolving the trusted subscription. The boundary checks stable installation/channel, human/loop filters, activation/time policy, immutable configuration/digests and atomic capacity. Acknowledgement eligibility is true only for definite Committed or verified Duplicate outcomes. A thrown/uncertain write is not acknowledgement success. Preserve provider event identity across reconnect/redelivery; envelope ID is not the dedup key. Independent subscriptions intentionally fan out the same provider event once each.

`ExecuteAsync(admissionId)` uses actual insert-only creation and its saved notifications, then only definitive first permit commit can bind one private invocation. A null return means this call did not establish a runnable attempt; do not turn it into a retry/start permit. Do not call ordinary runtime clients to start allocated admission-owned Pending instances. Public direct runner calls without private binding and public pipeline/activity delegates are denied. Unowned workflow behavior remains available.

Execution retains the same execution-cycle owner through final commit, trailing save and full unwind. Persistent variables load before scheduling and save through the normal commit path. A real Suspended result remains nonterminal. A successful runner return alone does not establish the trusted checkpoint: recording the final persisted full-state/bookmark fingerprint is a separate definite boundary.

For continuation, use the actual runtime client with the exact recorded BookmarkId after ExecutionObserved. Arbitrary activity handles, variable/property/scheduling changes and imported snapshots do not authorize continuation. Optional workflow output is returned as detached persisted data only when requested. Consumed, forged, missing-owner or ambiguous checkpoints fail closed.

## Withdraw and reconcile

The supported definition lifecycle path is `WithdrawAndRetractAsync(subscriptionId, revision, retire)`. It commits withdrawal before normal retract. A subsequent failure remains withdrawn with a reconciliation code, even if the definition still appears published. Never reactivate by resetting fields or importing records. Generic disconnect/tenant-delete/import/alteration support is outside this host.

Withdrawal uses the supplied revision as a control precondition. Admission and record transitions also advance the subscription revision, so concurrent traffic can cause a definite conflict. On conflict, no withdrawal or retraction is accepted: reload and inspect the current subscription configuration and activation state before issuing a fresh request. Do not blindly retry an old request across reconfiguration or reactivation. For a busy subscription, pause incoming admission and let local work settle before retrying; this operation does not promise an unconditional stop under continuous revision churn.

Withdrawal before permit issuance prevents start; already-issued delayed authority may run once. It is not retroactive cancellation of provider calls or a cross-store atomic guarantee. Before resolving uncertain work, stop/establish quiescence of every outstanding invocable owner, including delayed ones; absence of active workflow state or lease expiry is insufficient. Establish actual effects through an operator-owned reconciliation procedure. `ResolveAsync` requires bounded AuditReference plus explicit attestations and checks actual local owners/persisted executing state. Attestations are an audited operator boundary, not automatic evidence that unknown remote effects disappeared.

`RecoverAsync` classifies uncertainty without replaying insertion, notifications, permits or activity effects. `ListRecoveryAsync(limit, afterId)` returns safe state/revision/ownership indicators with bounded exclusive ID pagination; follow cursors to visit the current outstanding set, then restart scans for later insertions. Keep raw payloads, event contents, credentials and arbitrary exception text out of public exports and logs.

## Retain and clean up

Only qualified terminal dispositions have a terminal retention clock. Completed follows durably Finished status; distinguish handled fault substatus from successful business completion. SuppressedBeforeStart and Resolved require their explicit conditions. Suspended, long-running, materialized, authorized and ambiguous records are not terminal.

Cleanup requires exact revision and configured authority and atomically checks terminality, outstanding authority and release state. Payload expiry does not erase immutable event/input digests. Identity expiry does not remove ownership of a still-startable instance. Allocated-instance tombstones remain charged to retained-record capacity; this intentionally bounds metadata even when event keys are gone. Active reservations release once at qualified terminal transition. Retained capacity releases once only for actually removed non-owned terminal records. Plan retained capacity and reconciliation accordingly; there is no universal ownership-row cleanup promise.

PostgreSQL timestamps round upward to microseconds so retention cannot end early. Terminal retention origin is at least persisted admission time. Do not widen MaximumEventAge within an existing namespace: identities forgotten under the old horizon must not become eligible again. A new policy/namespace needs an explicit activation/replay decision, not an automatic reset.

## Verify changes

Use the existing PostgreSQL integration project and Admission worker, with declared fixture values, immutable container/process identity and deterministic barriers. Real process proof uses one execution process plus nonexecuting controllers and sequential restart; on hosted Linux the forced-crash lane requires a running worker, successful kill request, exit137, no handled-command-failure marker and no completion RESULT. Exercise real manager insertion/notifications, final writes, both registration paths, continuation and policy/host negatives. The hosted runner requires exact source/manifest-to-TRX-to-observation binding and sanitized receipts. A missing case, skip, zero result or incomplete catalog is not acceptance. Build affected production modules for net8/net9/net10; tests use the repository's configured test framework.

Live Socket Mode ack/reconnect/restart, additive channel-watch/message activities, legacy Token compatibility/migration, durable remote-post uncertainty, human-message-to-same-thread reply and live operator/runbook acceptance remain separate parent outcomes. This guide does not authorize live credentials, publication, deployment or cutover.
