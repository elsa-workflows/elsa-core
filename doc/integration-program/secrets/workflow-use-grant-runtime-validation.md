# Workflow-use grant runtime validation

This test-only slice installs `SyntheticCredentialUseWorkflow` and `SyntheticCredentialUseActivity` in an Elsa 3 host. The workflow waits on a durable `Event` bookmark. A second service provider opens the same SQLite stores and resumes it through `IWorkflowRuntime` and `IWorkflowClient`. The activity resolves the logical `payments` binding through `IWorkflowCredentialResolver`; the synthetic token goes only to an in-memory call probe.

Run `dotnet test test/unit/Elsa.Connections.UnitTests/Elsa.Connections.UnitTests.csproj -f net10.0 --no-restore`. On 2026-09-24, all 63 tests passed. The existing eight fresh-host OAuth runtime cases cover allowed, no grant, withdrawn, rebound, disconnected, grant for another workflow instance, wrong tenant, and wrong host environment. Five additional API-key cases use the same persisted-workflow resume path and cover allowed use, a rotated generation, disconnect, wrong tenant, and wrong host environment. Lifecycle tests also cover expiry while replacement has accepted a key but has not staged a generation: recovery restores the prior API key only when the planned generation is absent, fences the late writer, and cleans its orphaned generation. Unknown credential kinds and malformed API-key envelopes fail closed. The allowed cases verify the exact tenant, environment, and connection passed to the host credential service. Denials verify no credential service call or synthetic activity call; post-routing denials also record a persisted safe-denial incident. Wrong-tenant routing cannot load or execute the instance, so it records no attempt.

The API-key fixture creates encrypted managed Secrets generations and durable workflow-use grants through the real feature registrations. It proves that a replacement is published through lifecycle revision/fence checks, old generations can be retired, and a disconnected or out-of-scope connection cannot be resolved by the persisted workflow. Its marker is absent from raw persisted workflow data, reloaded workflow state, serialized workflow state, and captured host logs. Separate lifecycle tests cover concurrent replacement, stale-revision denial, local retirement/disconnect, and recovery after a lost staged-generation write. These are synthetic tests; no provider account or real API key is used.

The first host runs under tenant `tenant-a` and persists the workflow, bookmark, binding, and grant. The second host applies tenant routing from its trusted host context before loading the instance. Wrong-tenant routing cannot load the tenant-scoped instance. The environment comes from host configuration, never workflow input. This proves persisted resume through the real runtime client; it does not prove automatic routing by `RestartInterruptedWorkflowsTask`, a scheduler, or a queue consumer.

The test checks the raw persisted workflow `Data` column, the reloaded workflow input, output, properties and incident messages, the same `IWorkflowStateSerializer` used by workflow-instance export, and captured host logs for the synthetic access-token marker. It does not invoke the HTTP export endpoint or prove that every optional execution-log/bookmark export setting is safe. The granted call is already admitted once the resolver returns; a later withdrawal, rebind, or disconnect cannot retract an in-flight provider call. Lifecycle authorization and a final active-connection check remain separate boundaries.

No provider account, real OAuth token or API key, production host, or legacy Extensions `ConnectionDefinition` adapter is part of this fixture. Consumers inspect `ConnectionAccessCredential.Kind`: API-key material is available through `ApiKey`, while the existing `ExpiresAt` contract remains for OAuth and throws for an API key, which has no expiry value. API keys have no refresh-token exchange: `RefreshAsync` returns a safe unsupported error, and token-pair remote revocation rejects API-key generations. Disconnect and generation cleanup are local Elsa actions and do not revoke a provider-side key. This proof does not invoke the HTTP export endpoint, prove every optional execution-log/bookmark export setting, install a scheduled reconciler, or test provider-specific key rotation/revocation. The provider-specific activity, imported source-history compatibility, customer credential migration, and production operations remain separate program work.
