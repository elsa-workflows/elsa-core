# Workflow-use grant runtime validation

This test-only slice installs `SyntheticCredentialUseWorkflow` and `SyntheticCredentialUseActivity` in an Elsa 3 host. The workflow waits on a durable `Event` bookmark. A second service provider opens the same SQLite stores and resumes it through `IWorkflowRuntime` and `IWorkflowClient`. The activity resolves the logical `payments` binding through `IWorkflowCredentialResolver`; the synthetic token goes only to an in-memory call probe.

Run `dotnet test test/unit/Elsa.Connections.UnitTests/Elsa.Connections.UnitTests.csproj -f net10.0 -c Release`. On 2026-09-24, 66 tests passed with none skipped. The existing eight fresh-host OAuth runtime cases cover allowed, no grant, withdrawn, rebound, disconnected, grant for another workflow instance, wrong tenant, and wrong host environment. Five additional API-key cases use the same persisted-workflow resume path and cover allowed use, a rotated generation, disconnect, wrong tenant, and wrong host environment. Lifecycle tests also cover expiry while replacement has accepted a key but has not staged a generation: recovery restores the prior API key only when the planned generation is absent, fences the late writer, and cleans its orphaned generation. Unknown credential kinds and malformed API-key envelopes fail closed. The allowed cases verify the exact tenant, environment, and connection passed to the host credential service. Denials verify no credential service call or synthetic activity call; post-routing denials also record a persisted safe-denial incident. Wrong-tenant routing cannot load or execute the instance, so it records no attempt.

The API-key fixture creates encrypted managed Secrets generations and durable workflow-use grants through the real feature registrations. It proves that a replacement is published through lifecycle revision/fence checks, old generations can be retired, and a disconnected or out-of-scope connection cannot be resolved by the persisted workflow. Its marker is absent from the grant, raw persisted workflow data, reloaded workflow state, serialized workflow state, and captured host logs. Separate lifecycle tests cover concurrent replacement, stale-revision denial, local retirement/disconnect, and recovery after a lost staged-generation write. These are synthetic tests; no provider account or real API key is used.

Grant issuance now checks the host's distinct workflow-instance sharing decision as well as grant-management authorization. The test host registers both policies explicitly; the feature's default sharing policy denies issuance. A focused unit case proves that grant management alone writes no share, that the share request carries the trusted tenant/environment and exact binding snapshot, and that a grant can still be withdrawn after sharing permission is removed. The persisted grant remains the use-time entitlement, so the next resolution after withdrawal fails closed. General person/team sharing and provider-side consent delegation are outside this contract.

The first host runs under tenant `tenant-a` and persists the workflow, bookmark, binding, and grant. The second host applies tenant routing from its trusted host context before loading the instance. Wrong-tenant routing cannot load the tenant-scoped instance. The environment comes from host configuration, never workflow input. This proves persisted resume through the real runtime client; it does not prove automatic routing by `RestartInterruptedWorkflowsTask`, a scheduler, or a queue consumer.

The runtime test checks the raw persisted workflow `Data` column, the reloaded workflow input, output, properties and incident messages, the same `IWorkflowStateSerializer` used by workflow-instance export, and captured host logs for the synthetic credential marker. Run the separate persisted two-host TestServer test with `dotnet test test/integration/Elsa.Connections.Credentials.Persistence.PostgreSql.IntegrationTests/Elsa.Connections.Credentials.Persistence.PostgreSql.IntegrationTests.csproj -f net10.0 -c Release --filter FullyQualifiedName~ExportAfterPersistedApiKeyWorkflowResume_RedactsCredentialFromAllOptionalSections`. On 2026-09-24, the filtered test passed (1/1, none skipped). It invokes single-instance HTTP GET and POST exports, then a bulk ZIP export containing two workflow instances, with bookmarks, activity execution logs, and workflow execution logs included. It scans every returned response and ZIP entry plus the raw persisted state for the API-key marker. The fixture uses SQLite and synthetic activity output; it does not establish redaction of an arbitrary secret deliberately written into a workflow log or validate a production provider. The granted call is already admitted once the resolver returns; a later withdrawal, rebind, or disconnect cannot retract an in-flight provider call. Lifecycle authorization and a final active-connection check remain separate boundaries.

No provider account, real OAuth token or API key, production host, or legacy Extensions `ConnectionDefinition` adapter is part of these fixtures. Consumers inspect `ConnectionAccessCredential.Kind`: API-key material is available through `ApiKey`, while the existing `ExpiresAt` contract remains for OAuth and throws for an API key, which has no expiry value. API-key-only hosts need no OAuth credential provider. API keys have no refresh-token exchange: `RefreshAsync` returns a safe unsupported error without advancing the revision, and token-pair remote revocation rejects API-key generations. Disconnect and generation cleanup are local Elsa actions and do not revoke a provider-side key. The tests do not install a scheduled reconciler or test provider-specific key rotation/revocation. The provider-specific activity, imported source-history compatibility, customer credential migration, and production operations remain separate program work.
