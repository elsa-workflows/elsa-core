# Workflow-use grant runtime validation

This test-only slice installs `SyntheticCredentialUseWorkflow` and `SyntheticCredentialUseActivity` in an Elsa 3 host. The workflow waits on a durable `Event` bookmark. A second service provider opens the same SQLite stores and resumes it through `IWorkflowRuntime` and `IWorkflowClient`. The activity resolves the logical `payments` binding through `IWorkflowCredentialResolver`; the synthetic token goes only to an in-memory call probe.

Run `dotnet test test/unit/Elsa.Connections.UnitTests/Elsa.Connections.UnitTests.csproj -f net10.0 --no-restore`. On 2026-09-24, all 50 tests passed, including eight fresh-host runtime cases: allowed, no grant, withdrawn, rebound, disconnected, grant for another workflow instance, wrong tenant, and wrong host environment. The allowed case verifies the exact tenant, environment, and connection passed to the host credential service. Six post-routing denial cases record one resolution attempt in the installed activity and a persisted safe-denial incident from that activity. Wrong-tenant routing cannot load or execute the instance, so it records no attempt. All seven denial cases verify that no credential service call or synthetic activity call occurs.

The first host runs under tenant `tenant-a` and persists the workflow, bookmark, binding, and grant. The second host applies tenant routing from its trusted host context before loading the instance. Wrong-tenant routing cannot load the tenant-scoped instance. The environment comes from host configuration, never workflow input. This proves persisted resume through the real runtime client; it does not prove automatic routing by `RestartInterruptedWorkflowsTask`, a scheduler, or a queue consumer.

The test checks the raw persisted workflow `Data` column, the reloaded workflow input, output, properties and incident messages, the same `IWorkflowStateSerializer` used by workflow-instance export, and captured host logs for the synthetic access-token marker. It does not invoke the HTTP export endpoint or prove that every optional execution-log/bookmark export setting is safe. The granted call is already admitted once the resolver returns; a later withdrawal, rebind, or disconnect cannot retract an in-flight provider call. Lifecycle authorization and a final active-connection check remain separate boundaries.

No provider account, real OAuth token, production host, or legacy Extensions `ConnectionDefinition` adapter is part of this fixture. The provider-specific activity, imported source-history compatibility, customer credential migration, and production operations remain separate program work.
