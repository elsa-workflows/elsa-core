# Credential lifecycle validation slice

This is a bounded validation recommendation for integration work, based on Core `origin/main` `610790ec57ae9d5c334181d50c1e65f99613fd86`. It describes tests for a future outbound connection lifecycle service. It does not claim the current Secrets or workflow runtime implements these scenarios.

## Test harness

Use a deterministic fake OAuth provider and a fake/SQLite `ISecretManager` setup. Use only synthetic token strings and synthetic tenant identifiers; do not call a live vendor or log token material. Make the provider expose controllable responses for expiry, refresh-token rotation, revocation scope, retry/idempotency, and each failure boundary. Run tests with two independently scoped service instances when exercising concurrency so in-process locks cannot masquerade as distributed coordination.

Keep the existing `ISecretResolver` and `ISecretManager` consumer contracts unchanged. The test subject is a new application service that owns connection metadata, actor policy, operation state, expected revision, environment binding, and the reference to a credential generation. All resolution goes through an authorized service path; raw values must not appear in connection DTOs, logs, audit payloads, or serialized workflow summaries. The test cannot assert that arbitrary user-authored workflow values or downstream third-party activities remain redacted after explicit value injection.

## Required scenarios

| Scenario | Setup and action | Assertions |
|---|---|---|
| Connect and stage | Create a tenant-owned connection and synthetic grant. Stage a unique Secrets record holding the complete provider token set in `Value`; fail before connection pointer commit and retry. | A returned connection DTO contains provider/account/status and a reference/generation, never values. Failed staging is either safely removed or retained as an identifiable orphan; retry cannot point at a partial grant. The client secret/client registration binding and tenant grant have separate owner policies. |
| Resolve current generation | Commit a connection pointer, then resolve it for an authorized activity under the connection tenant and environment. | The resolved generation matches the connection's committed revision, expiry/provider policy is applied, and reference metadata is checked. The test documents that current generic `SecretReference` resolves latest-active only; lifecycle-created token-set secret names are unique per committed generation and are not rotated in place. |
| Unauthorized use | Try resolution using an unauthorized principal, a different tenant's ambient context, a mismatched connection tenant, and an absent/mismatched environment binding. Repeat from a background execution with no ambient tenant established. | Each request is denied before value resolution; no existence/value oracle leaks in errors; background/resumed execution must establish tenant and authorize against connection owner before dereference. |
| Concurrent refresh | Two nodes read the same connection revision and one-time refresh token, then race the same due refresh. Provider returns a replacement access/refresh pair on the winning request. | A durable per-connection claim/revision admits one provider call. The winner persists the replacement token pair and advances the connection pointer exactly once; the loser re-reads the latest state and never replays the consumed refresh token. Assert no secret aggregate last-write-wins race is relied on as CAS. |
| Slow refresh and lease expiry | Worker A acquires the durable lease and sends the provider request but is paused before observing the response. Let the lease expire while worker B attempts takeover. Then release worker A with a successful one-time token rotation response. | Lease expiry fences local writes but does not imply provider non-execution. Worker B does not call the provider with the same refresh token while A's outcome is unknown. Persist attempt state is reconciled; if the replacement is unavailable, transition to recovery/reauth rather than replay. If A did persist a staged generation, a current operation may conditionally commit it using operation ID and expected connection revision; stale workers cannot publish over a newer connection revision. |
| Provider failure before rotation | Provider rejects before consuming the refresh credential, times out, or returns a documented retryable response. | State transition and retry decision follow that provider's documented contract; no blind replay occurs where consumption is unknown. Error details are normalized and redacted. |
| Persistence failure after provider success | Inject failure after the provider consumes the old token and returns a replacement but before replacement material is durably stored; then restart the worker. | Cross-system atomicity is acknowledged. The connection enters a durable `RecoveryRequired`/reauth state unless that provider documents a safe grace/idempotent retry. The stale refresh token is not retried automatically; an operation/audit record identifies the ambiguous step without containing values. |
| Pointer/cleanup crash windows | Fail after a provider consumed a refresh token and the new encrypted generation was stored but before pointer swap; separately fail after pointer swap but before old secret cleanup. Restart reconciliation. | The staged replacement is associated with a durable operation ID. If that operation is still current, reconciliation conditionally commits it against the expected connection revision; if stale, it cannot overwrite newer state. Do not discard a replacement while the provider may have consumed the old refresh token. If no replacement can be recovered, mark recovery/reauth required. After pointer commit, cleanup is idempotent and removes only lifecycle-owned, unreferenced prior generations. |
| Access-token cache policy | Exercise short-lived access tokens, an expired token near the safety margin, pointer swap, scope changes, tenant/environment changes, revoke, and disconnect. Restart the process with and without persisted access material. | Default short-lived access-token cache keys include tenant, environment, connection, generation, and scopes; expiration has a safety margin. Pointer change/revoke/disconnect invalidates cached entries. Persist access alongside refresh when provider policy needs restart survival, grace recovery, non-expiring access, or atomic pair rotation; never assume a refresh call can recover the last usable access token. |
| Workflow suspension and resume | Suspend a workflow on a trigger, expire credentials, renew or mark recovery required in background, then resume the workflow after process restart under the original tenant. | Resume resolves the current committed credential generation and connection state, not a serialized cleartext token or stale cached token. Trigger/webhook/polling paths reauthorize and restore tenant/environment context. If unavailable or reauthentication-required, the workflow receives a safe, deterministic failure path. |
| Local disconnect and provider revoke | Disconnect locally, enqueue provider revoke, inject transient and terminal vendor failures, then retry/reconcile. Also test provider uninstall separately. | Local use is disabled immediately. “Disconnect this connection,” revoke an individual token/pair, and uninstall/revoke all installation grants are distinct user-confirmed operations with provider-specific semantics. Do not delete encrypted material required for retry until revocation outcome/policy permits cleanup; retain safe tombstone/audit state. |
| Delete and shared references | Delete a connection with managed secret refs; test an intentionally shared platform client secret and a tenant-owned token set. | Only lifecycle-owned, unreferenced generations are eligible for removal; shared/platform-owned material is not deleted by tenant disconnect. Secrets deletion does not imply upstream revocation. Retention and cleanup are explicit and idempotent. |
| Redaction boundaries | Put synthetic marker strings in access/refresh tokens and provider error bodies; exercise endpoint, logger, audit event, exception mapping, trace, and workflow summary. | No marker appears in response metadata, logs, audit/outbox fields, telemetry tags, or exception text. Test documents the boundary: once a caller intentionally places a resolved value into arbitrary workflow data, universal redaction cannot be guaranteed by Secrets. |
| Provider token policy | Model one provider with non-expiring access but issued refresh token and another with one-time rotating refresh. | Policy persists both when provider docs require it; only permits access-token cache-only treatment when provider docs prove safe. Persist replacement pairs as one generation and test provider-specific retry/revoke/grace behavior. |
| Environment promotion | Export/promote a workflow connection definition between test and production environments. | Only logical provider metadata and binding intent are promoted. Each environment provisions its own secret generation and encryption-key context; raw values and resolved token values are never exported. A reference from one environment cannot resolve in another. |

## Failure-injection checkpoints

At minimum, inject process termination or store/provider exceptions after each durable boundary:

1. lifecycle operation intent/claim recorded;
2. provider request sent, before a response is observed;
3. provider response received, before encrypted secret creation;
4. encrypted secret generation created, before connection compare-and-swap;
5. connection pointer committed, before old-generation cleanup;
6. provider revoke accepted, before local revocation result is saved.

Tests should verify idempotent reconciliation and exact allowed state transitions at each point. A provider call that may have consumed a one-time refresh token is an ambiguity boundary, not a generic retry case.

## Exit criteria and follow-up scope

The lifecycle implementation is not ready to claim safe connector auth until these scenarios pass for the chosen persistence provider(s), a two-node concurrency test passes, a restart/reconciler test passes, and host authorization/redaction tests cover human and background resolution. Provider-specific adapters need their own pinned documentation and conformance cases. This slice is intentionally not a live credential canary and makes no cloud-vault or provider-support assertion.
