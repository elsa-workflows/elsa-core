# Credential lifecycle validation slice

This file began as a bounded validation recommendation based on Core `origin/main` `610790ec57ae9d5c334181d50c1e65f99613fd86`. The initial synthetic Core lifecycle slice now implements and tests part of this matrix. The matrix remains broader than the shipped code; current proof and deferred scenarios are distinguished below. The governing recommendation is [the dated credential lifecycle ADR](../../adr/2026-09-23-integration-credential-lifecycle.md).

## Current implementation and proof

The initial implementation adds `Elsa.Connections`, `Elsa.Connections.Credentials.Persistence.EFCore`, and its SQLite adapter. The new persistence package names are additive to the existing `Elsa.Connections.Persistence.EFCore` packages in Extensions. The separate `Elsa.Connections.Credentials.Workflows` adapter is non-packable, and the new package family remains non-packable until the release-unit manifest explicitly opts selected units in. The Connections feature supplies a default tenant accessor when multitenancy is absent and preserves the host's configured accessor when present. The unit tests use actual Connections, Secrets, and workflow-management EF feature registrations, durable SQLite files, and synthetic values only. [`ConnectionLifecycleTests`](../../../test/unit/Elsa.Connections.UnitTests/ConnectionLifecycleTests.cs) verifies the lifecycle scenarios below. [`WorkflowCredentialBindingTests`](../../../test/unit/Elsa.Connections.UnitTests/WorkflowCredentialBindingTests.cs) verifies logical binding persistence, trusted tenant and configured environment selection, default-deny authorization, rebind revision races and in-flight semantics, cross-tenant isolation, explicit target-environment binding, metadata-only workflow state, and a real SQLite workflow restart path: the original DI container is disposed, a new worker opens the same database, `RestartInterruptedWorkflowsTask` restores the persisted tenant, and the resolver reads the durable binding. The restart test uses a restarter callback to exercise the resolver; it does not install a workflow activity or run-grant integration.

- `dotnet test test/unit/Elsa.Connections.UnitTests/Elsa.Connections.UnitTests.csproj -f net10.0 --no-restore` — 29/29 (`net10.0`), including deterministic concurrent-create conflict classification and unrelated database failure propagation.

This is synthetic SQLite proof, not a live provider or released package claim. The current implementation does not include a hosted recovery scheduler, workflow activity/run-grant integration, Studio UX, a workflow export/import pipeline, provider-specific refresh/revoke semantics, or automatic cleanup/offboarding orchestration. It proves target-environment mapping must be created through the host-authorized binding manager; it does not claim end-to-end export or promotion. The [operations guide](credential-lifecycle-operations.md) records those limits and the deployment/rollback boundary. The matrix below remains the acceptance plan for those future capabilities; rows are not claims that the behaviors already exist.

## First implementation slice

Prove one tenant-owned connection from synthetic OAuth grant through authorized token resolution and a one-time rotating refresh, using SQLite-backed lifecycle state and the existing encrypted Secrets store. The fake provider must model token consumption and expose a pause/failure point around the refresh response. Use synthetic tenant, environment, account, and token values only; make no vendor network calls.

The first slice is Core-only and has no connection UI, real provider adapter, provider account approval, BYO OAuth client credentials, or cloud-vault integration. Treat the OAuth client registration as test/deployment configuration owned by the host; it is separate from the tenant's token grant. Validate SQLite behavior only. Other supported database providers need their own persistence conformance before the service is claimed portable across them.

Connection ownership is the persisted `(tenantId, environmentId)` pair. A human request carries an authenticated actor and is authorized for the specific connection operation; management permission does not imply runtime use. A background or resumed workflow carries an explicit system identity scoped to that tenant, environment, and connection. Missing or mismatched context is denied before Secrets is read. Ambient tenant state may help scope persistence but is not the authorization input.

Each successful connect or refresh writes access and refresh material together in a fresh, unique Secrets generation's encrypted `Value`; token values, provider bodies, and sensitive headers never enter metadata. A generation is immutable once staged. Generic Secrets update, rotate, and delete paths must reject lifecycle-owned generations; only the lifecycle cleanup path can remove its own unreferenced generation after checking the current pointer and unresolved operations. Keep the existing generic Secrets contracts compatible.

The owner marker must be durable and protected from generic edits; a generated name or mutable tag alone is not an ownership guard. It identifies the lifecycle owner and generation without storing token material. The lifecycle path proves that owner identity before staging or removing a generation. After the connection service authorizes a request, it establishes the validated owner-tenant scope for Secrets persistence rather than trusting an unrelated ambient tenant.

The pilot decisions and safe deferrals are:

| Concern | Pilot decision | Safe deferral |
|---|---|---|
| Credential storage | Reuse the existing encrypted Secrets store; keep connection and provider-operation state in a separate durable lifecycle boundary. | Provider-specific external vaults and broad Secrets API changes. |
| Concurrency and state | Durable per-connection revision CAS plus operation ID and fencing attempt; lease expiry never permits replay when provider outcome may be unknown. | Tuning lease duration and provider-specific safe retry rules. |
| Generation ownership | Fresh immutable generation per grant/refresh; durable owner marker; generic management mutations denied; lifecycle cleanup checks references and in-flight operations. | Cross-repository package cutover and production key-ring/rotation promises. |
| Identity | Tenant and environment are persisted; human use and narrowly scoped background/system use are authorized separately before secret lookup. | Exact user experience and role names for a future management UI. |
| Provider | Deterministic fake with one-time rotating refresh token and injected failures. | Real vendor accounts, app approval, expiry/grace, idempotency, token revoke scope, and installation uninstall until a vendor and its current docs are selected. |
| Persistence proof | Two independent service instances and restart against SQLite and the real encrypted Secrets repository. | Claims of conformance for other EF Core providers until their test suites run. |

## Durable operation and race rules

Record an operation ID, connection revision, and fencing/attempt number durably before calling the provider. Claiming refresh uses a compare-and-swap on lifecycle state, not a process lock or a Secrets aggregate version. The call may consume a single-use refresh token even if Elsa times out or the worker disappears; lease expiry therefore permits investigation/reconciliation only and never authorizes a second call with that token while the outcome is unknown.

When the response is known, stage its replacement generation under the operation ID, then publish the reference only if the operation is still current, the expected connection revision still matches, and the connection remains locally usable. A stale worker cannot publish after another operation changes the row. If provider success is known but neither a replacement generation nor a safe provider retry can be recovered, persist `RecoveryRequired` and require provider-specific recovery or reauthentication. Do not silently return to Active.

Local disconnect immediately disables use and advances the connection revision. Keep local `Disconnected`/disabled state distinct from `RevocationPending` and `Revoked`; only a confirmed provider result can mark remote revocation complete. Installation uninstall is a separate operation from revoking one token or connection. If disconnect or the start of revocation wins while refresh is in flight, the late refresh response cannot republish a generation or reactivate the connection. Retain any staged material needed to reconcile the provider outcome; clean it only after no current pointer or unresolved operation references it and provider policy permits removal. Provider revocation that succeeded remotely but was not recorded locally is reconciled from a durable operation record, not by assuming local deletion revoked the grant.

## Test harness

Use the real SQLite-backed Secrets repository and encrypted store with synthetic values, plus a deterministic fake OAuth provider. Give two independently constructed lifecycle service/store instances separate dependency-injection containers and database contexts over the same SQLite database; share only the fake provider as the simulated remote system. Configure every container and restart from the same durable synthetic 16/24/32-byte `SecretsOptions.EncryptionKey`, supplied outside the SQLite database. Do not share a protector/service instance as a substitute for independent configuration. Assert that values written by one container resolve in a second container and after restart with that key; absent or mismatched keys must fail resolution without disclosure. For restart cases, dispose the first container and construct a new one over the same database, with no shared in-memory coordinator or token cache. Make the provider expose a consumed-token ledger, controllable pause before response observation, one-time refresh rotation, and injected failures. Never log token material.

Keep the existing `ISecretResolver`, `ISecretManager`, and `SecretReference` consumer contracts unchanged. The test subject is a new application service that owns connection metadata, human/system authorization, operation state, expected revision, environment binding, and the reference to a credential generation. All resolution goes through an authorized service path; raw values must not appear in connection DTOs, logs, audit payloads, or serialized workflow summaries. The test cannot assert that arbitrary user-authored workflow values or downstream third-party activities remain redacted after explicit value injection.

## Slice sequencing

The required-scenario table is the complete lifecycle proof, not a claim that every row belongs in the first pull request. The first implementation task is [#8270](https://github.com/elsa-workflows/elsa-core/issues/8270), grouped under [story #8269](https://github.com/elsa-workflows/elsa-core/issues/8269). It covers the synthetic connect/resolve/refresh vertical slice: connect and stage; authorized resolution; unauthorized tenant/environment/system-identity checks; concurrent and slow refresh; provider-success persistence failure; staged-generation/pointer crash recovery; local-disconnect-versus-refresh fencing; and response/log/audit redaction. Include the Secrets-owned-generation guard because unique names alone do not prevent a generic Secrets caller from rotating or deleting a generation.

The next slice is [#8271](https://github.com/elsa-workflows/elsa-core/issues/8271), which depends on #8270 and covers durable logical workflow bindings, trusted tenant restoration on persisted restart, resolver authorization/rebind fencing, and explicit target-environment mapping. Durable local disconnect, provider revoke/uninstall, reconciliation, and cleanup are a separate sibling task, [#8296](https://github.com/elsa-workflows/elsa-core/issues/8296), blocked by #8270 and #8271. Full workflow activity/run-grant/resume integration and any shared token cache remain outside those slices. These tasks belong to F4.2 story #8269 and are linked here for traceability. Keep real provider adapters in separate conformance work after a provider is selected and current official docs define token expiry, refresh replay/idempotency, grace, revoke scope, and uninstall behavior. Do not create provider-specific Tasks or claim account/provider support before that evidence exists.

## Required scenarios

| Scenario | Setup and action | Assertions |
|---|---|---|
| Connect and stage | Create a tenant-owned connection and synthetic grant. Stage a unique Secrets record holding the complete provider token set in `Value`; fail before connection pointer commit and retry. | A returned connection DTO contains provider/account/status and a reference/generation, never values. Failed staging is either safely removed or retained as an identifiable orphan; retry cannot point at a partial grant. The client secret/client registration binding and tenant grant have separate owner policies. |
| Resolve current generation | Commit a connection pointer, then resolve it for an authorized activity under the connection tenant and environment. | The resolved generation matches the connection's committed revision, expiry/provider policy is applied, and reference metadata is checked. The test documents that current generic `SecretReference` resolves latest-active only; lifecycle-created token-set secret names are unique per committed generation and are not rotated in place. |
| Unauthorized use | Try resolution using an unauthorized principal, a different tenant's ambient context, a mismatched connection tenant, and an absent/mismatched environment binding. Repeat from a background execution with no ambient tenant established. | Each request is denied before value resolution; no existence/value oracle leaks in errors; background/resumed execution must establish tenant and authorize against connection owner before dereference. |
| Concurrent refresh | Two nodes read the same connection revision and one-time refresh token, then race the same due refresh. Provider returns a replacement access/refresh pair on the winning request. | A durable per-connection claim/revision admits one provider call. The winner persists the replacement token pair and advances the connection pointer exactly once; the loser re-reads the latest state and never replays the consumed refresh token. Assert no secret aggregate last-write-wins race is relied on as CAS. |
| Slow refresh and lease expiry | Worker A acquires the durable lease and sends the provider request but is paused before observing the response. Let the lease expire while worker B attempts takeover. Then release worker A with a successful one-time token rotation response. | Lease expiry fences local writes but does not imply provider non-execution. Worker B does not call the provider with the same refresh token while A's outcome is unknown. Persist attempt state is reconciled; if the replacement is unavailable, transition to recovery/reauth rather than replay. If A did persist a staged generation, a current operation may conditionally commit it using operation ID and expected connection revision; stale workers cannot publish over a newer connection revision. |
| Disconnect/revoke racing refresh | Pause refresh after the fake provider consumes the token. Persist local disable/revocation-pending with a revision CAS, then release the provider response. | Local use is blocked immediately and the late refresh cannot publish or reactivate the connection. Remote `Revoked` is recorded only after provider confirmation. Keep any generation needed by the unresolved operation until cleanup/reconciliation is safe; a new worker never replays the consumed refresh token. |
| Provider failure before rotation | Provider rejects before consuming the refresh credential, times out, or returns a documented retryable response. | State transition and retry decision follow that provider's documented contract; no blind replay occurs where consumption is unknown. Error details are normalized and redacted. |
| Persistence failure after provider success | Inject failure after the provider consumes the old token and returns a replacement but before replacement material is durably stored; then restart the worker. | Cross-system atomicity is acknowledged. The connection enters a durable `RecoveryRequired`/reauth state unless that provider documents a safe grace/idempotent retry. The stale refresh token is not retried automatically; an operation/audit record identifies the ambiguous step without containing values. |
| Pointer/cleanup crash windows | Fail after a provider consumed a refresh token and the new encrypted generation was stored but before pointer swap; separately fail after pointer swap but before old secret cleanup. Restart reconciliation. | The staged replacement is associated with a durable operation ID. If that operation is still current, reconciliation conditionally commits it against the expected connection revision; if stale, it cannot overwrite newer state. Do not discard a replacement while the provider may have consumed the old refresh token. If no replacement can be recovered, mark recovery/reauth required. After pointer commit, cleanup is idempotent and removes only lifecycle-owned, unreferenced prior generations. |
| Access-token cache policy | Exercise short-lived access tokens, an expired token near the safety margin, pointer swap, scope changes, tenant/environment changes, revoke, and disconnect. Restart the process with and without persisted access material. | Default short-lived access-token cache keys include tenant, environment, connection, generation, and scopes; expiration has a safety margin. Pointer change/revoke/disconnect invalidates cached entries. Persist access alongside refresh when provider policy needs restart survival, grace recovery, non-expiring access, or atomic pair rotation; never assume a refresh call can recover the last usable access token. |
| Workflow suspension and resume | Suspend a workflow on a trigger, expire credentials, renew or mark recovery required in background, then resume the workflow after process restart under the original tenant. | Resume resolves the current committed credential generation and connection state, not a serialized cleartext token or stale cached token. Trigger/webhook/polling paths reauthorize and restore tenant/environment context. If unavailable or reauthentication-required, the workflow receives a safe, deterministic failure path. |
| Local disconnect and provider revoke | Disconnect locally, enqueue provider revoke, inject transient and terminal vendor failures, then retry/reconcile. Also test provider uninstall separately. | Local use is disabled immediately. “Disconnect this connection,” revoke an individual token/pair, and uninstall/revoke all installation grants are distinct user-confirmed operations with provider-specific semantics. Do not delete encrypted material required for retry until revocation outcome/policy permits cleanup; retain safe tombstone/audit state. |
| Delete and shared references | Delete a connection with managed secret refs; test an intentionally shared platform client secret and a tenant-owned token set. | Only lifecycle-owned, unreferenced generations are eligible for removal; shared/platform-owned material is not deleted by tenant disconnect. Secrets deletion does not imply upstream revocation. Retention and cleanup are explicit and idempotent. |
| Redaction boundaries | Put synthetic marker strings in access/refresh tokens and provider error bodies; exercise endpoint, logger, audit event, exception mapping, trace, and workflow summary. | No marker appears in response metadata, logs, audit/outbox fields, telemetry tags, or exception text. Test documents the boundary: once a caller intentionally places a resolved value into arbitrary workflow data, universal redaction cannot be guaranteed by Secrets. |
| Provider token policy | Model one provider with non-expiring access but issued refresh token and another with one-time rotating refresh. | Policy persists both when provider docs require it; only permits access-token cache-only treatment when provider docs prove safe. Persist replacement pairs as one generation and test provider-specific retry/revoke/grace behavior. |
| Environment promotion | Export/promote a workflow connection definition between test and production environments. | Only logical provider metadata and binding intent are promoted. Each environment provisions its own secret generation and encryption-key context; raw values and resolved token values are never exported. A reference from one environment cannot resolve in another. |

## Failure-injection checkpoints

At minimum, inject process termination or store/provider exceptions after each durable boundary:

1. lifecycle operation intent/claim recorded;
2. provider request sent, before a response is observed;
3. provider response received, before encrypted secret creation;
4. encrypted secret generation created, before connection compare-and-swap;
5. connection pointer committed, before old-generation cleanup;
6. provider revoke accepted, before local revocation result is saved.

Tests should verify idempotent reconciliation and exact allowed state transitions at each point. A provider call that may have consumed a one-time refresh token is an ambiguity boundary, not a generic retry case.

## Exit criteria and follow-up scope

Full connector integration and provider support are not ready to claim until the relevant scenarios pass for each selected persistence provider, the production host's authorization and scheduling paths are tested, and provider-specific adapters have pinned documentation and conformance cases. The implemented synthetic slice is intentionally not a live credential canary and makes no cloud-vault or provider-support assertion.

F4.2's reviewed follow-up hierarchy is [story #8269](https://github.com/elsa-workflows/elsa-core/issues/8269), [task #8270](https://github.com/elsa-workflows/elsa-core/issues/8270) for the synthetic durable lifecycle, [task #8271](https://github.com/elsa-workflows/elsa-core/issues/8271) for restart-safe workflow credential bindings, and sibling [task #8296](https://github.com/elsa-workflows/elsa-core/issues/8296) for offboarding and revoke recovery. Provider-specific conformance remains deferred until a vendor is selected and its current behavior is documented.
