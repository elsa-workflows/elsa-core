# Credential lifecycle architecture and operations

This guide records the boundaries and operational limits of the initial Core credential-lifecycle implementation. It covers synthetic provider integration, SQLite conformance, and bounded PostgreSQL worker tests; it is not a production provider runbook or evidence that a provider account was connected.

## Architecture and trust boundaries

- `Elsa.Connections` owns connection metadata, tenant/environment binding, authorization, refresh orchestration, local disconnect, and offboarding contracts. `Elsa.Connections.Credentials.Persistence.EFCore` owns durable connection, workflow binding, cleanup tombstone, and offboarding rows with conditional revision/fence updates. The SQLite adapter is the executable reference used by the current tests.
- `Elsa.Secrets` remains the encrypted value store. Connections creates one immutable managed Secrets generation per grant or refresh and updates the connection pointer only after the encrypted generation exists. Persisted owner/generation markers make generic Secrets update, rotate, delete, list, and resolve paths reject or hide managed generations. `IManagedSecretManager` is an internal host integration seam; HTTP callers must use the authorized Connections service.
- Human use and management are separate authorization decisions. The Connections feature defaults to deny. The host must provide an `IConnectionUseAuthorizer` that validates the authenticated actor and the requested permission against tenant, environment, and connection identity. A caller-selected system label or permission string is not sufficient evidence for background access. `IConnectionBackgroundUseService` and the recovery service are host-only contracts: they accept exact tenant/environment/connection IDs, mint their internal system identity themselves, and authorize background `use` or `manage:reconcile` before loading credentials. Keep them out of HTTP APIs and caller-controlled workflow inputs.
- Logical workflow bindings select a connection in the trusted tenant and configured integration environment; they do not grant use. Without a binding-store provider, the workflow adapter's default store returns no mappings and binding management/use fail closed. A host that provides a binding store must also configure lifecycle persistence and `IConnectionBackgroundUseService`; a valid mapping with that lifecycle path missing is a host configuration error and is not hidden as a normal unavailable result. A disconnect can race the binding store's active-state check and leave a stale mapping. Each resolve still passes through the lifecycle service, which rejects disconnected connections.
- `WorkflowCredentialUseGrantsFeature` is opt-in. It requires a durable Connections grant store and a separate host-provided `IConnectionCredentialGrantManagementAuthorizer`; its defaults deny grant management and return no grants. At use time, the grant check is mandatory in addition to any host `IConnectionCredentialBindingUseAuthorizer`; enabling grants never replaces a host's extra use restrictions. An authenticated actor may issue a grant only for the trusted tenant, configured environment, exact workflow instance and current active binding revision. Concurrent issuance for the same scope yields at most one grant; recognized PostgreSQL serialization conflicts return a controlled failed issuance. Withdrawing a grant uses a revision check and permanently disables that instance/binding pair; do not delete the row to reauthorize it. Use a new workflow instance until an explicit reissue policy is designed. Grant rows contain no Secrets values. Back up and restore these rows with bindings and connection state; SQLite and PostgreSQL grant migrations intentionally have no in-place `Down` path. After withdrawal, rebind, or disconnect, the next credential resolution fails closed, while a previously admitted provider call can still finish.
- `ResolveForUseAsync` returns an access-only credential. Refresh tokens stay inside lifecycle/provider operations. Connection results, secret listings, and serialized access DTOs contain no token values. The generic Secrets resolver remains a trusted low-level API for unowned secrets and does not authorize an actor.
- Tenant, environment, connection, and generation identity are checked together on reads and mutations. Copying an environment's logical connection configuration does not copy its token generation or encryption key. Do not export or promote raw token material.
- Local disconnect, token-pair revocation, and installation uninstall are distinct authorized actions. Disconnect commits `Disconnected` and its completed local operation record in one SQLite-tested transaction; it does not imply remote revoke or uninstall. A token-revocation request must name a lifecycle-owned generation, and that generation stays pinned while the operation is unresolved. Installation uninstall uses provider-owned host credentials and stores no Connections generation reference. It must not silently fall back to the connection's OAuth token.

## Due-candidate discovery

`IConnectionDueCandidateStore.FindDueCandidatesAsync` accepts a tenant and environment supplied by the trusted host, a fixed `now`, a page size from 1 through 500, and an opaque keyset cursor. The caller must also establish Elsa's ambient tenant context for the current service scope; passing explicit IDs does not disable the EF global tenant filter, and a missing ambient context can return an empty page. Background workers should push the tenant context for each scope. The query returns only tenant/environment/connection identity, candidate kind and ID, and due time. The scheduler must re-read each candidate and use the existing lifecycle CAS/fence operations; a candidate is not a claim or authorization to replay an unknown provider outcome. Expiry, lease, retry, and cleanup boundaries are inclusive (`<= now`). Null cleanup leases are due immediately, null offboarding retry times are surfaced for recovery attention, and claimed/provider-call offboarding rows without a lease are not due. Ordering is `(DueAt, Kind, ConnectionId, CandidateId)` and the cursor omits mutable revision values, so ordinary connection revision changes do not reorder a candidate. Recovery-required candidates sort at `DateTimeOffset.MinValue`; a worker with a per-wake cap must carry the cursor forward or partition/rotate work by kind so persistent recovery rows do not starve timed candidates. New or moved work before the cursor is picked up on the next scan.

OAuth expiry and credential kind are copied from the encrypted credential envelope into nullable nonsecret fields when a staged generation is published. Generation publication changes the active generation pointer, kind, and expiry in the same conditional database update. API-key generations are marked `ApiKey` with no expiry; they can appear for cleanup/offboarding but never as OAuth refresh candidates. The migration deliberately leaves existing rows null. There is no bulk backfill: preexisting rows with unknown kind or expiry are on-demand only and are never silently scheduled for OAuth refresh. An operator must explicitly reconnect or rotate/update such a credential through an authorized lifecycle operation to establish current scheduling metadata.

The EF Connections store normalizes credential expiry metadata to UTC on both direct connection creation and staged-generation writes, and normalizes the `now` query boundary to UTC. This keeps SQLite's textual `DateTimeOffset` comparisons aligned to instant semantics even when a caller supplies a nonzero offset; a SQLite execution test persists `12:00Z` as `14:00+02:00` and verifies it is selected at the inclusive `12:00Z` boundary.

## Opt-in hosted reconciliation

Hosts that provide durable Connections persistence can opt into `ConnectionLifecycleReconciliationFeature`. The worker is disabled when that feature is absent, and its `Enabled` option can pause it without removing the feature. The host must provide `IConnectionLifecycleScopeProvider`; the default provider returns no scope, so enabling the feature without replacing it intentionally performs zero reconciliation. Treat that default as an inactive configuration, not as a healthy worker. A provider chooses tenant and environment from trusted host configuration or tenant infrastructure, never workflow input. It returns one scope per call and should rotate fairly when a host serves multiple scopes. The worker pushes that tenant into Elsa's ambient context before querying and re-establishes it in each dispatch scope.

`ConnectionLifecycleReconciliationOptions` bounds polling interval, due-query page size (1–500), concurrent dispatches (1–64), and exponential retry delay per tenant/environment scope for query exceptions, thrown dispatches, and unsuccessful safe lifecycle results. A failed scope does not lengthen the scan interval for other scopes. The worker keeps a bounded in-memory keyset cursor and monotonic retry timer per recently selected scope, so a fixed or adjusted UTC clock cannot hold a retry indefinitely. It commits the next cursor only after the entire page is handled; a transiently failed page is retried from its prior cursor after that scope's backoff. A `recovery_required` result with no safely promotable generation and an `offboarding_outcome_unknown` result without stable provider idempotency require operator attention, not a transient worker retry: each is handled for the scan without claiming lifecycle success, so later pages remain reachable. After the last page the cursor wraps so inserts before the old cursor are discovered. A process restart starts a fresh scan. Each page has at most `BatchSize` candidates and at most `MaxConcurrency` lifecycle calls in flight.

Candidates are only nonsecret pointers. Refresh, expired-operation recovery, cleanup, and offboarding dispatch use lifecycle entry points that mint the internal background-system identity, require the host authorizer's `BackgroundSystem` decision for the operation purpose, then re-read and claim through existing conditional revision/fence APIs. OAuth refresh candidates are generated only for active OAuth generations with persisted expiry metadata; API-key connections are not refresh candidates. Cleanup remains local and owner-checked. Offboarding replay continues to require provider-declared stable operation-ID idempotency; unknown outcomes without that guarantee remain for operator review. Safe lifecycle failures are not automatically converted into provider retries. Cancellation stops the worker; unprocessed candidates return on a later scan.

Worker logs contain only aggregate cycle or page failure counts. Provider exception messages, candidate identifiers, and credential payloads are not logged. The worker emits these .NET `Meter` counters under `Elsa.Connections`, with **no tags**:

| Counter | Meaning |
| --- | --- |
| `elsa.connections.reconciliation.pages.completed` | A due-candidate query returned and its page was handled, including an empty page. |
| `elsa.connections.reconciliation.pages.failed` | One or more candidates in a returned page failed or were rejected as out of scope; the page cursor was retained for retry. |
| `elsa.connections.reconciliation.scans.failed` | A scope was invalid, a due query failed, or a worker cycle threw before a page outcome was recorded. |
| `elsa.connections.reconciliation.attention.recovery_required` | Reconciliation reported an existing recovery-required state or an expired/failed publication transition that may enter it. |
| `elsa.connections.reconciliation.attention.offboarding_outcome_unknown` | Offboarding reported an unknown remote outcome, including an accepted result whose durable status remains unknown. |

Hosts must subscribe to `Elsa.Connections` in their metrics exporter; adding the opt-in worker does not deploy an exporter or alert. A nonzero increase in failed pages or scans over a five-minute window is a warning to inspect worker health, and persistence over 15 minutes warrants escalation under the host's operational policy. Any increase in an attention counter warrants inspection of the durable connection or offboarding state through an authorized administrative path; a transition may have resolved by inspection time, and an unknown offboarding outcome may be replayable when the provider guarantees stable operation-ID idempotency. Repeated wakes can count the same unresolved item again, so these counters are not a count of distinct incidents. Zero completed pages is not proof of health: the default scope provider yields no scopes. Do not put tenant, environment, connection, candidate, provider, exception or credential values into metric labels or alert text. The worker is not activated by default and does not certify a provider, supply tenant scope policy, or change production configuration.

The built-in lifecycle service also creates operation, cleanup, and offboarding timestamps from `TimeProvider.GetUtcNow()`. Callers that invoke lower-level persistence methods directly must supply UTC `OperationLeaseExpiresAt`, cleanup/offboarding lease, creation, update, and retry timestamps; those existing timestamp inputs are not normalized by every store method, and existing legacy values are not backfilled. SQLite instant ordering for externally supplied non-UTC values in those existing columns is therefore outside this change's guarantee. A returned cursor preserves the stored offset so a legacy non-UTC cleanup/offboarding row cannot make the next page invalid; this does not make its textual due ordering instant-correct.

Custom `IConnectionLifecycleStore` implementations remain source-compatible through default overloads, but that fallback drops the new scheduling metadata. A custom store must implement metadata-aware stage and recovery-promotion overloads plus `IConnectionDueCandidateStore` before a host enables due-candidate reconciliation.

Due-candidate ordering is configured for the SQLite and PostgreSQL Connections providers only (`BINARY` and `C` string collations). Connections has no SQL Server persistence provider, so SQL Server is outside this query/migration scope.

The query has scoped indexes on `Connections(TenantId, EnvironmentId, CredentialKind, CredentialExpiresAt, Id)` and `Connections(TenantId, EnvironmentId, Status, OperationStatus, OperationLeaseExpiresAt, Id)`, plus matching due indexes on cleanup status/lease and offboarding status/retry or lease. PostgreSQL plan inspection in tests forces sequential scans off and confirms the OAuth candidate branch can use `IX_Conn_Due`; this is branch evidence, not a claim that the full union/keyset query is index-only. The union may still require a per-page merge/sort. Inspection of the OAuth path can be repeated with:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT "Id", "CredentialExpiresAt"
FROM "Elsa"."Connections"
WHERE "TenantId" = 'tenant-a'
  AND "EnvironmentId" = 'environment-a'
  AND "Status" = 'Active'
  AND "CredentialKind" = 'OAuth'
  AND "CredentialExpiresAt" <= TIMESTAMPTZ '2026-09-24 12:00:00+00'
ORDER BY "CredentialExpiresAt", "Id"
LIMIT 101;
```

The migration adds only nullable metadata columns and nonunique indexes, so existing rows remain readable without payload decryption or a data rewrite. Rollback is application-only: deploy an earlier binary while retaining the additive columns and indexes. Compatibility of an earlier binary with this newer schema has not been verified, and schema rollback has no supported `Down` path because removing the metadata and indexes would disable scheduled lifecycle discovery. If an earlier binary cannot run against the retained schema, restore the matching pre-upgrade database backup and application together; do not drop the new columns or indexes manually.

## Operation and recovery behavior

Connect and refresh record an operation ID, fence, planned generation, and a two-minute lease before work can be reconciled; refresh also records the source generation. An owning operation that observes a failure marks recovery immediately. A separate worker may reconcile an in-flight operation only after the persisted lease expires; the expiry check is part of the database conditional update. Reconciliation never calls the provider with the prior refresh token.

Before the durable provider-call boundary, a secret-resolution or persistence failure releases the refresh claim and leaves the existing active generation usable. The claim-to-call-start transition checks its lease atomically, so a worker whose claim expired cannot start the provider call. Reconciliation may abandon an expired `Claimed` operation; it does not abandon a `ProviderCallStarted` operation on lease expiry.

After the provider-call boundary, a timeout, cancellation, restart, or lost persistence result is an unknown outcome. The connection moves to `RecoveryRequired` unless the already-encrypted planned generation can be verified and safely promoted for that same operation and source generation. A disconnected or newer operation is never revived by recovery. When the provider response is lost and no replacement generation exists, the owning application must arrange provider-specific reauthentication or recovery; do not retry the old token automatically.

`ConnectionLifecycleReconciliationFeature` adds an opt-in host timer and bounded dispatcher over `IConnectionLifecycleRecoveryService`; it does not add a queue consumer or workflow resumption handler. Hosts must provide a trusted scope provider and a default-deny authorizer that explicitly permits the background operation purposes they intend to run. The synthetic lifecycle surface also supports explicit local disconnect, token-pair revocation, installation uninstall, host-invoked `ReconcileOffboardingAsync`, and cleanup of eligible generations. Real provider adapters and vendor-specific revoke/uninstall semantics, production activation, and workflow activity/run-grant integration remain outside this slice. Before deleting a managed generation, the lifecycle owner must prove that no current connection pointer or unresolved operation references it.

The host-only `IConnectionLifecycleRecoveryService.ReconcileOffboardingAsync` advances one durable offboarding operation per call. It uses the persisted operation ID as the provider correlation key, but that ID alone does not make a remote request idempotent. An adapter may declare stable operation-ID idempotency only when its provider contract guarantees at-most-once effects. Unknown outcomes from such an adapter can retry with the same ID; without that guarantee, an expired provider-call lease or `UnknownOutcome` remains unresolved and is not automatically replayed. A reported retryable failure must mean the provider knows no remote effect occurred. Provider errors and token values are replaced by fixed safe result codes.

Disconnect may happen while refresh is in flight; the refresh CAS prevents later publication/reactivation. An unresolved refresh still blocks generation cleanup and explicit revoke/uninstall admission until the refresh outcome is settled. Cleanup atomically blocks concurrent queueing, checks unresolved refresh and offboarding references, writes a tombstone, and clears a disconnected connection's current-generation pointer only after those references settle. It then deletes only the immutable owner-checked Secrets generation. A successful local cleanup is not evidence of remote revocation. Unknown offboarding keeps its generation pinned until provider-specific recovery marks it complete or terminal.

There is no ordering automation between revoke and uninstall. Callers request each operation explicitly; an adapter that needs a token to uninstall must declare and test that contract before use. The synthetic uninstall interface uses separately configured provider-owned host credentials, so it cannot consume or accidentally revoke the connection's token generation.

## Encryption key and deployment

`SecretsOptions.EncryptionKey` is a 16-, 24-, or 32-byte AES key supplied by the host, outside the database. Every process that reads the same Secrets data must receive the same durable key bytes. Store key material in the deployment's secret/configuration facility, never in the connection database, application logs, exports, or test artifacts. A missing or mismatched key makes encrypted generations unavailable; it does not authorize a fallback to cleartext or a retry of a provider call.

The current protector has one configured key and no key identifier, key ring, or re-encryption workflow. Replacing the configured key without first migrating encrypted values makes existing generations unreadable. Treat key rotation as unsupported until Elsa provides and tests versioned key selection and re-encryption. The current Connections projects are marked `IsPackable=false`; the code and SQLite adapter are not a released production package set.

For a future deployment that packages this slice, sequence work as follows:

1. Configure and validate the same external encryption key on every replica before enabling Connections.
2. Take and verify restorable backups of every database containing connection rows, logical workflow bindings, workflow-use grants, or encrypted Secrets generations. Preserve the matching key material and application artifact/version with the backup record.
3. Apply the selected provider's schema migrations using the normal Elsa deployment path, then validate that the managed-secret resolver can decrypt a synthetic generation before accepting real grants.
4. Configure a real, default-deny host authorizer and provider adapter, then test tenant/environment isolation and background recovery in that host. The synthetic authorizer and provider in the unit tests are not deployment defaults.

## Upgrade, rollback, and restore

The Secrets schema adds nullable managed-owner and generation columns, and Connections adds durable lifecycle, workflow binding, and workflow-use grant metadata. Existing Secrets rows remain unowned. Migration `Down` methods intentionally throw rather than silently erase lifecycle ownership, connection state, workflow bindings, or grant withdrawals, so there is no supported in-place downgrade path. Do not run an older application version against the upgraded schema, and do not manually drop ownership columns or connection/binding/grant tables while lifecycle-managed generations or persisted workflows depend on them.

If rollout must be reversed, restore the complete set of predeployment database backups and the matching predeployment application version together. Restore the key material that encrypts those databases as part of the same recovery. The restore returns the system to the backup point: connections, logical bindings, grants, withdrawals, or token generations created afterward are lost and may require users to reconnect, rebind workflows, or reauthorize with the provider. A backup restored from before a grant withdrawal can make that grant active again; disable connector execution until the withdrawal is reconciled. Do not combine predeployment databases with a postdeployment key or vice versa. If the required backups or matching key are unavailable, stop and escalate; do not run migration `Down` or delete managed secret rows to force an older binary to start.

## Current verification and explicit limits

The current executable proof is documented in the [validation slice](credential-lifecycle-validation.md) and the connection lifecycle unit/PostgreSQL integration test projects. Unit tests verify disabled mode makes no scope or due-query calls, all candidate kinds route through the host-only lifecycle contract, configured concurrency is respected, cross-scope candidates are rejected, a failed tenant does not delay a healthy tenant, a transiently failed page is retried before cursor advancement, and 1,100 repeated page queries keep cursor state bounded across scan wraparound. The PostgreSQL subprocess suite starts two independent hosted-worker processes against the same database and barriers them at refresh claim: one wins the conditional mutation, the other loses, exactly one synthetic provider call is accepted, and repeated wakeups see no additional due refresh. It also verifies that a differently scoped worker finds no candidate, and that killing a worker after the durable provider-call-started edge then restarting after lease expiry leaves the operation in `RecoveryRequired` without making a provider request. An API-key connection is also passed through the hosted worker and produces no due OAuth refresh. Process outputs are checked for synthetic access-token, refresh-token, rotated-token, encryption-key, and API-key markers. SQLite lifecycle tests exercise durable disconnect, explicit offboarding, generation pinning/retirement, and unknown-outcome retry policy. This evidence uses synthetic providers and does not certify live provider semantics, package publication, production activation, multi-replica key provisioning, workflow activity integration, Studio UX, connection export/promotion, or vendor-specific revocation/uninstall behavior.

Worker verification on `audit/8378-credential-worker` ran against net10.0.
