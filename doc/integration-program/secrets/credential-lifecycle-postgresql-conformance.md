# Credential lifecycle PostgreSQL process conformance

`CredentialWorkerProcessTests` in `test/integration/Elsa.Connections.Credentials.Persistence.PostgreSql.IntegrationTests` exercises Connections against the PostgreSQL Connections and Secrets EF providers using real operating-system worker processes. The test-only executable in `test/workers/Elsa.Connections.Credentials.WorkerProcess` composes production code from `src/modules/Elsa.Connections`, `src/modules/Elsa.Connections.Credentials.Persistence.EFCore.PostgreSql`, `src/modules/Elsa.Secrets.Persistence.EFCore.PostgreSql`, and the PostgreSQL workflow-persistence packages. It does not substitute an in-memory store, service instance, lock, or token cache. Every worker receives the same synthetic 32-byte Secrets key and fixed clock through its environment, outside PostgreSQL.

`PostgreSqlConnectionsFixture` in `test/integration/Elsa.Connections.Credentials.Persistence.PostgreSql.IntegrationTests/PostgreSqlConnectionsPersistenceTests.cs` starts an ephemeral `postgres:16-alpine` container through Testcontainers. Each test drops the `Elsa` schema before setup; the collection fixture disposes the container after all tests. `SyntheticOAuthServer` is a local Kestrel OAuth/offboarding provider. It models a consumed single-use refresh token, response blocking, and optional stable operation-ID idempotency. No vendor account, external provider API, or production service is used. Run the suite with Docker available:

```sh
dotnet test test/integration/Elsa.Connections.Credentials.Persistence.PostgreSql.IntegrationTests/Elsa.Connections.Credentials.Persistence.PostgreSql.IntegrationTests.csproj --framework net10.0
```

The test project targets `net10.0` only. It covers independent-process refresh contention, restart after worker termination at durable claim/provider-start/staged/published boundaries, late refresh completion after local disconnect, expired-lease reconciliation, provider-success/local-persistence ambiguity for revocation and uninstall, the queue-versus-generation-cleanup race, tenant/environment denial, redacted process output, and persisted logical-binding lookup during workflow restart. The conformance worker lives under `test/workers` so repository CI's `test/integration` project discovery does not treat the executable as an independent test project; the integration-test project builds and launches it as a project dependency.

The workflow restart scenario persists a real `WorkflowInstance` and invokes Elsa's `RestartInterruptedWorkflowsTask`. Its `IWorkflowRestarter` is a test adapter that reloads the persisted logical reference and invokes the real credential resolver; `ITenantService` and `ActivityTestFixture` supply the synthetic restart context. This proves persisted tenant restoration and binding resolution through that task, not actual workflow execution, installed activity registration, run-grant wiring, or host scheduling.

The suite is provider conformance evidence for this synthetic PostgreSQL setup only. It does not prove SQLite-to-PostgreSQL migration, live OAuth provider semantics, released packages, production key provisioning, scheduled reconciliation, workflow activity/run-grant integration, or remote revocation/uninstall behavior beyond the explicit fake provider contract. See the [lifecycle operations guide](credential-lifecycle-operations.md) for operational boundaries and deferred integrations.
