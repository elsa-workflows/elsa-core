# History-import Workbench and Studio Secrets smoke

On 2026-09-26, the isolated import checkout at `6b6c6fe27a76ead762fc5dc3ec4e9abc5672f8c9` built and started the committed Extensions Workbench and two committed Studio server hosts. This is a browser and process proof for [#8326](https://github.com/elsa-workflows/elsa-core/issues/8326), not a production or package-release proof. The machine-readable [sanitized receipt](../../../scripts/integration-program/history-import-workbench-studio-secrets-smoke-6b6.json) pins the source, fixture patch paths, binary/asset digests, identity policy, and outcomes. Each fixture patch's exact content is reproducible from the pinned head and path with `git show <head>:<path> | shasum -a 256`. The original three-parent import is `d5409c2cb2338166e1bccaf5df07212e5d7bf159` (Core `e96fd36f…`, Extensions `ba8b71d9…`, Studio `20ceaeee…`). No mapped rehearsal overlays were applied to this checkout; the fixture preparer verified clean, committed source inputs.

The Workbench and Studio builds succeeded on `net10.0`; both Studio ClientLib pipelines generated their six required browser assets. Workbench ran with a new private SQLite database, private lock and drop-in paths, loopback ports, empty outbound webhook sinks, and synthetic configuration-backed ElsaIdentity accounts. Its private tenant switch was enabled for this fixture only; the committed default remains disabled. The two tenant hosts shared that database. Host resolution selected `tenant-a` or `tenant-b` before login, and matching `TenantId` claims and tenant-scoped administrator roles selected the same tenant after login. The startup route probe found exactly ten canonical Core Secrets endpoints, one Core owner for each, no legacy Secrets route or assembly, and no obsolete legacy Secrets cleanup job in the host composition.

In separate browser sessions, tenant A and tenant B each created an encrypted secret with the technical name `integration-shared` and distinct metadata and values. Each Studio list, detail page, and workflow expression picker showed only its own tenant's secret. Tenant A also created `integration-a-only`; tenant B received HTTP 404 for its detail route. Switching back to tenant A preserved its own metadata. Both tenants created an unpublished draft with a Write Line activity selected from the real Studio picker. Persisted workflow definitions contain only `{ "name": "integration-shared", "typeName": "text" }` references; each tenant's cross-tenant definition read returned 404. Neither draft was published or executed.

Tenant A's Studio browser updated metadata, rotated the synthetic tenant-only secret from version 1 to 2, tested an active secret successfully, revoked the rotated secret, observed an inactive result when testing the revoked secret, and deleted it. A separately authenticated synthetic tenant-A user with no roles saw no Secrets navigation item; direct list and detail navigation returned HTTP 403, and the Create control was absent. This observed UI gating complements the Core authorization response; it does not replace it. A byte scan found the known rotated value absent from the SQLite database, WAL, SHM, Workbench log, and both Studio logs. Each persisted draft expression field contained a reference rather than a secret value. The byte scan is limited to the known rotated fixture value; no claim is made about arbitrary data.

The repeat procedure is in [the Workbench runtime preflight](../../../scripts/integration-program/workbench-secrets-runtime-preflight.md): prepare the exact clean import head with `--two-tenant --route-probe`, build both Studio ClientLibs, start one Workbench plus two separately configured Studio hosts, and exercise the two tenant browser sessions. After gathering sanitized evidence, stop all three processes and use the preparer's `--cleanup <marked-fixture-root> --host-stopped` ownership guard. Private passwords, keys, HTTP bodies, raw logs, and SQLite files are deliberately excluded from this repository. The import PR remains draft and a later import-head change must be checked against this receipt before claiming final-head validation.
