# Store connector credential material in Secrets; govern its lifecycle separately

- **Status:** Accepted for the initial synthetic Core credential-lifecycle slice.
- **Date:** 2026-09-23
- **Decision scope:** Elsa Core outbound connector authorization and token lifecycle. The source audit below is pinned to `origin/main` commit `610790ec57ae9d5c334181d50c1e65f99613fd86`; the initial implementation follows the boundaries in this ADR and is recorded in the companion implementation and operations guide.

## Context

Outbound integrations need to connect accounts, resolve credentials during workflow execution, refresh credentials in background work, survive process restarts, and disconnect/revoke grants. These operations combine vendor-side state with Elsa-owned connection state. They also need tenant ownership and environment isolation. A database transaction cannot include an OAuth provider call, and the current generic Secrets manager has no lifecycle operation record or caller-supplied revision.

The current Secrets module provides useful encrypted storage, secret type/store abstractions, version metadata, management endpoints, and ambient-tenant persistence. However, `ISecretManager.RotateAsync` reads an aggregate, chooses the next version, retires the active version, and saves without an expected revision; EF `SaveAsync` copies the incoming version list. Existing uniqueness/concurrency logic protects create or deleted-name reuse, not concurrent rotations. `ISecretResolver` checks optional type/scope and resolves the latest active value. Its contracts do not carry actor, tenant, environment, use authorization, or a pinned version. The Secrets endpoints' view/write/delete/test permissions apply to management routes; direct in-process resolution is trusted-caller behavior.

The encrypted store protects `SecretPayload.Value` with the configured AES-GCM key but copies other metadata. The default protector has no key identifier or rotation/re-encryption workflow. The configuration store resolves deployment-owned values by configuration key; its `Write` capability writes only reference metadata and `Delete` does not remove configuration. Thus neither the current name/version API nor the configuration-backed store is by itself an outbound OAuth lifecycle manager.

External Authentication provides a useful pattern: it stages a unique managed secret, then uses a revision-checked connection pointer update and cleans up an unpublished or superseded reference. That module manages inbound identity-provider login connections and is host-scoped; it is precedent for lifecycle mechanics, not an outbound tenant-connection capability.

Provider token behavior also varies. Official Moneybird docs advise persisting both a currently non-expiring access token and its refresh token, and revoking either pair member revokes both. Slack documents optional one-time refresh-token rotation, short grace, token limits, and distinct token revoke versus uninstall operations. Treat these only as examples: each provider adapter must own and test its own rules.

## Decision

Use the existing `Elsa.Secrets` storage and protection abstractions for sensitive token material, and build a separate connector connection/lifecycle application service for connection metadata, ownership, environment binding, provider policy, refresh orchestration, concurrency, reconciliation, and authorization. Do not copy the Secrets encrypted store or add a second generic credential vault. Do not make the generic Secrets API itself responsible for OAuth protocol state.

The lifecycle service stores durable non-secret connection state: provider registration/account identifiers, owning tenant or platform scope, environment binding, scopes, lifecycle/status, current generation reference, expected revision, refresh lease/attempt state, provider policy identifier, and safe operation/audit identifiers. Tenant grants and platform OAuth client registrations have distinct owners and authorization policies. Tenant-supplied OAuth app credentials (BYO app) are outside this recommendation until separately scoped.

For each committed token set, create a fresh, unique Secrets record and publish its reference with a durable compare-and-swap on the connection revision. Keep access and refresh token values together in the encrypted `Value` envelope when the provider rotates them as a set. Do not put tokens, provider bodies, or sensitive headers in `SecretPayload.Metadata`; encrypted store metadata is copied in cleartext. Managed token-set secret records are immutable by lifecycle policy: create one generation per successful provider grant/refresh and move the connection pointer, rather than rotating one name in place. The current `SecretReference` resolves latest-active only and cannot pin an explicit version, so the implementation uses unique generations with persisted owner/generation markers. Generic Secrets write/delete/resolve paths check persisted markers and reject lifecycle-owned material; generic listings omit it. Keep the existing `ISecretResolver`, `ISecretManager`, and `SecretReference` public surfaces compatible for current consumers; ownership enforcement is additive through the managed-secret boundary.

For token caching, default short-lived access tokens to a bounded in-memory cache keyed by tenant, environment, connection, committed generation, and requested scope set. Invalidate entries when the connection pointer changes, or the connection is revoked or disconnected. Require an expiry safety margin before returning cached values. Persist the access token with the refresh token when the provider requires access-token survival across restart, documents a grace/recovery window that depends on retaining it, issues a non-expiring/long-lived token that is operationally needed after restart, or rotates access and refresh credentials as an inseparable durable pair. Persist any issued refresh token in Secrets. Provider policy and provider documentation override this default; do not classify a token as cache-only without evidence that it can be reacquired safely.

Refresh must be serialized by a durable per-connection claim/revision in the lifecycle store, not by the Secrets aggregate's version count or an in-process lock. After an upstream refresh, persist the replacement token set as a fresh secret generation, then compare-and-swap the connection pointer. A losing worker re-reads the connection and must not replay a consumed one-time refresh token. Record a durable operation/idempotency identifier before the provider call and associate staged encrypted generations with that operation so reconciliation can find them without reading token values into metadata or logs. The transition from `Claimed` to `ProviderCallStarted` is a lease-checked CAS immediately before the provider call. Failures before that transition release the claim and preserve the prior active generation; an expired `Claimed` operation is safe to abandon because the provider was not called. Lease expiry after the durable call-start edge fences stale local writes, but does not prove the provider request did not complete: do not let a takeover worker issue another call with the old one-time token while the earlier attempt's outcome is unknown. Reconcile the recorded attempt or move it to `RecoveryRequired` unless provider-specific semantics prove replay safe.

There is no distributed transaction with the provider. If the process loses the provider response or cannot persist a replacement after the provider may have consumed a one-time refresh token, mark the connection `RecoveryRequired` (or an equivalent safe reauthentication state) and do not automatically replay the old token unless that provider documents idempotency, grace, or safe recovery. If the replacement was encrypted and staged but pointer commit failed, reconciliation must find it by the durable operation ID and conditionally commit it against the expected connection revision when that operation is still current. If the provider outcome or replacement material is unavailable, do not discard the only recoverable state and reuse the possibly-consumed token; mark recovery/reauth required. Keep staged or superseded secret material until reference checks and provider policy permit cleanup. Local disconnect, provider token revocation, and provider installation uninstall are distinct actions and states. Disable local use immediately on disconnect; provider revocation/uninstall and secret cleanup follow documented provider semantics and an idempotent retry/reconciliation record.

All human and background resolution goes through the lifecycle service. It restores/validates the connection tenant and environment, authorizes the actor or narrowly scoped system operation, checks status/provider compatibility, then calls existing Secrets abstractions. The generic resolver remains a trusted low-level primitive and gains no implied caller permission. Logs, response DTOs, traces, audit/outbox payloads, and exception messages contain references/status/operation IDs only. This cannot guarantee redaction after a workflow author deliberately copies resolved cleartext into arbitrary workflow values or a third-party activity; that disclosure boundary must be documented and tested at product integration points.

Encryption-key delivery and rotation remain host/platform responsibilities until Elsa provides a key-ring contract. Every runtime replica that resolves a secret must access the same durable key material. Before production key rotation is claimed, define versioned key selection and a tested re-encryption/migration procedure; a single `SecretsOptions.EncryptionKey` switch can make old values unreadable. Environment promotion copies logical connection configuration only; each environment provisions its own secret generation and key context, and raw token values never enter exports.

## Alternatives considered

| Option | Assessment |
|---|---|
| Reuse `ISecretManager` as the complete connection/token lifecycle | Rejected. It has no connection ownership, provider operation state, refresh lease, expected-revision CAS, background tenant authorization, or upstream revoke/uninstall distinction. Its latest-active resolution and unconditional rotate/save are not enough to coordinate a one-time refresh across nodes. |
| Extend Secrets into a connector/OAuth lifecycle manager | Rejected for this integration boundary. It would conflate generic named secret values with provider grants, tenant connection state, upstream protocol behavior, and environment-specific ownership. A future generic expected-version/CAS capability may be useful independently, but this ADR does not assume or require it. |
| Build a dedicated encrypted connector-token store | Rejected. It duplicates existing encrypted value storage and creates a second secret-value boundary. Use Secrets for protected material and add only the lifecycle-specific durable state and operations needed by connections. |
| Separate lifecycle service backed by Secrets | Recommended. It keeps existing Secrets storage and consumer contracts, while assigning provider-aware concurrency, ownership, recovery, and disconnect behavior to the domain that can enforce them. |

## Compatibility and prerequisites

- Existing Secrets APIs and generic references remain source/binary compatible. The new service and connection lifecycle model are additive.
- Lifecycle integration must not infer that management permission grants runtime use permission. Connection manage/use/background policies need explicit definitions and tests.
- Current resolver references do not encode a version; unique, lifecycle-owned secret names are the safe generation boundary until an explicit pinned-reference contract is designed.
- The existing Secrets encryption setting has no key ring. Key delivery, multi-replica availability, and rotation/re-encryption are deployment prerequisites and product gaps, not capabilities provided by this decision.
- A separate inventory found duplicate public Secrets persistence package IDs across Core and Extensions, with divergent source trees. Decide package publisher/compatibility and migration ownership before any cross-repository package cutover; this ADR does not select one.
- No cloud vault, operating-system certificate store, outbound polling, webhook token renewal, or tenant connector support is implied by this recommendation.

## Consequences

The lifecycle service must have durable state and a testable state machine in addition to Secrets persistence. It must explicitly model ambiguous provider refresh outcomes, reconcile staged orphan generations and post-swap cleanup, and carry tenant/environment context into resumed workflows and background renewal. Implementations need fake-provider failure injection and multi-node concurrency tests before claiming safe refresh. Connector code may resolve token values only inside authorized, short-lived operations and must keep them out of general workflow data wherever possible.

## Initial implementation boundary

The initial implementation adds `Elsa.Connections` for connection metadata, authorization, connect/use/refresh orchestration, and recovery contracts; `Elsa.Connections.Credentials.Persistence.EFCore` for tenant/environment-filtered compare-and-swap storage; and a SQLite persistence adapter used by conformance tests. The Connections feature supplies a default `ITenantAccessor` for hosts without multitenancy and preserves a host accessor when configured. Encrypted token generations remain in the existing Secrets store through `IManagedSecretManager`. Its public lifecycle contract is host-facing; callers must still enter through an authorized lifecycle operation. Human `ResolveForUseAsync` returns access material only, while refresh-token values stay within the lifecycle/provider boundary. A separate host-only `IConnectionBackgroundUseService` accepts exact tenant/environment/connection identifiers, mints a private system identity, authorizes background `use`, and then uses the same resolution path; it is not an HTTP or workflow-input API. The default connection authorizer denies access until the host configures its own policy.

Connect and refresh operations record a two-minute lease before work can be reconciled. Reconciliation waits until that durable lease expires before taking over an in-flight operation; an owner that observes a failure can mark recovery immediately. Lease expiry does not prove an upstream request failed. `ProviderCallStarted` refresh outcomes are never replayed automatically. Reconciliation may promote a persisted planned generation only while operation identity, fence, source generation, and connection state still match. The #8296 follow-on adds atomic local disconnect, explicit revocation and uninstall requests, a durable offboarding ledger, and host-invoked reconciliation. These are synthetic host contracts, not provider adapters or evidence of remote revocation. Unknown remote outcomes are retried only when a provider adapter explicitly guarantees stable operation-ID idempotency; otherwise they remain `UnknownOutcome` for provider-specific recovery. A workflow host may bind a trusted execution identity to the host-only background-use contract, but this slice does not implement or prove full workflow activity/run-grant integration.

Local disconnect does not automatically queue remote actions. Token-pair revocation and installation uninstall require separate authorized requests after local disconnect and after any unresolved refresh operation has settled. Revocation pins the requested encrypted generation until the remote result is complete or terminal. Installation uninstall uses provider-owned host credentials and intentionally carries no Connections generation; adapters that need a connection generation for uninstall must define that provider-specific contract before implementation. Offboarding never assumes a local disable or Secrets deletion revoked a provider grant. Cleanup's compare-and-swap checks lifecycle-operation references, current pointer, unresolved offboarding generations, and an immutable cleanup tombstone. A disconnected current pointer can be retired atomically only after refresh and offboarding references settle; ambiguous refresh state blocks retirement.

The migrations add nullable ownership metadata, connection lifecycle state, workflow bindings, and durable offboarding history. `Down` intentionally throws instead of dropping lifecycle ownership or unresolved-operation data. Do not downgrade the database while lifecycle-owned generations or offboarding history exist. If application rollback is required, restore the complete predeployment database backup and matching application version together; do not run older binaries against the upgraded schema. The backup must include connection metadata, workflow binding and offboarding metadata, and encrypted Secrets records, and the externally supplied encryption key must remain available. Restoring the old backup discards connections, bindings, offboarding requests, and token generations created after that backup; users may need to reconnect and rebind.

## Workflow binding refinement

The follow-on workflow slice keeps logical binding metadata in the credential domain and the existing Connections EF context. A binding is a durable `(tenant, environment, logical binding ID) -> connection ID` mapping with a monotonically increasing revision; it contains no token or secret-generation reference. The separate, nonpackable `Elsa.Connections.Credentials.Workflows` adapter depends on the credential domain and Elsa Workflows runtime types. Credential Core does not depend on Workflows, and the existing Extensions `ConnectionDefinition` APIs, middleware, and serialized connection format remain unchanged.

The target `EnvironmentId` is host configuration. Tenant scope comes only from the trusted runtime `ITenantAccessor`; on persisted workflow restart, `RestartInterruptedWorkflowsTask` restores the workflow summary's persisted tenant before invoking the restarter. Blank configuration, missing/default tenant, and the agnostic tenant fail closed. Workflow inputs, properties, definitions, bookmark payloads, and resume data may carry a logical binding ID but cannot set tenant, environment, connection ID, binding revision, or provider identity as authorization. If no binding-store provider is configured, the adapter uses an empty fail-closed store; when a real binding store is configured, the host must also wire lifecycle persistence and background-use service. A missing lifecycle path for a resolved mapping is a host configuration error, not a normal credential-denial result.

Each credential use performs an exact scoped lookup, authorizes the current binding revision and connection for the workflow instance through a host-provided default-deny policy, then reloads the mapping and rejects a changed revision or connection ID before calling the existing host-only background credential resolver. A rebind before that reload prevents admission. A rebind after the reload may let the already-admitted activity finish with its captured connection; the next resolve observes the new revision. Lifecycle status and disconnect checks remain authoritative at the credential resolver. The management authorizer is also host-configured and defaults to deny; it receives the trusted tenant and configured environment and cannot be replaced by workflow-authored fields.

The binding store checks that a target connection is active when creating or rebinding, but the binding write and a concurrent disconnect are separate lifecycle operations. A disconnect may therefore leave a stale mapping. This is safe because mappings are selection metadata, never use permission; the lifecycle resolver still checks current connection status before releasing credential material.

Export/import preserves logical references only. A target environment has no binding merely because the source workflow had one; a target operator must create or explicitly rebind the mapping to a connection authorized in that target environment. Source connection IDs, revisions, secret generations, and credential material do not transfer authorization. The synthetic test proves persisted tenant restoration and mapping policy, not vendor behavior. #8296 adds local disconnect, explicit revoke/uninstall operation records, generation pinning, and host-invoked outbox reconciliation; workflow activity/run-grant integration and live provider semantics remain separate proof.

## Durable workflow-use grant refinement

The opt-in `WorkflowCredentialUseGrantsFeature` replaces the binding adapter's default-deny use authorizer with a durable grant check. A separate host-configured `IConnectionCredentialGrantManagementAuthorizer` must approve issue and withdrawal for an authenticated human; connection management permission alone does not authorize either action. The grant manager obtains tenant from `ITenantAccessor` and environment from host configuration. It rejects missing, default, or agnostic tenant and never accepts workflow-authored scope or actor values. No host policy or durable grant store means denial.

A grant records one tenant, environment, workflow instance, logical binding, connection ID, and binding revision. It contains an issuing actor ID and timestamps but no token, Secrets value, or provider payload. The Connections EF context holds the grant beside connection and binding state. Issue checks the current binding revision and active connection in a serializable transaction; the composite key permits one issuance for a given workflow instance and logical binding. Withdrawal uses a grant-revision compare-and-swap and is permanent for that instance/binding pair: a new authorization requires a new workflow instance rather than silently resurrecting a withdrawn grant. This conservative rule can be expanded only with an explicit reissue revision and policy contract.

Each resolution reloads the grant, checks its active state and exact binding revision, checks the current connection status, then repeats the binding check before the existing background credential resolver. Withdrawal before the grant read, rebind before the binding recheck, and disconnect before the lifecycle service's final status check block a new call. An operation admitted before one of those changes may finish with its captured credential; the next resolution fails closed. The grant check does not replace the lifecycle service's final credential-use authorization. The SQLite and PostgreSQL migrations are additive and irreversible so rollback must restore matched application, database, and encryption-key backups together. The installed-activity and actual persisted-restart proof remains #8345, and the legacy Extensions adapter remains separate.
