# Protect and authorize native compensation recovery data

- Status: Proposed
- Date: 2026-10-21
- Owners: Elsa 3 program lead with Security, Core, Studio, Hosting, Runtime, and Persistence reviewers
- Related: [E2 contract](../../core/docs/specs/native-compensation/recovery-data.md), [native-compensation packet](../../core/docs/specs/native-compensation/README.md), [root instance journal ADR](2026-10-20-native-compensation-instance-journal.md), [guarded snapshot ADR](2026-10-21-native-compensation-guarded-snapshots.md), [#8778 general secret redaction](https://github.com/elsa-workflows/elsa-core/issues/8778), [#8181 external-auth tenant selection](https://github.com/elsa-workflows/elsa-core/issues/8181).

## Context

Native compensation needs immutable recovery captures after child execution contexts disappear, but only for schema-declared, policy-approved fields. “Exact” refers to those approved recovery values, not arbitrary request/result object graphs or exception objects. A cause must be a bounded, sanitized record under the existing sensitivity policy; an unreviewed exception graph/message/stack, authentication header/token, or resolved secret snapshot is not a valid capture. Credentials should be re-resolved through existing Secrets references and authorization when a participant supports that safely; recovery-detail authority is not Secrets read authority.

The workflow instance GET and export paths expose `WorkflowState`; the default execution mapper copies inputs, outputs, properties, metadata, journal data, and exceptions into ordinary records. The exception paths are independent: activity middleware logs an exception before sending `FaultSignal` and logs a thrown handler exception; workflow exception middleware logs the exception and builds `ActivityIncident` and execution-log entries from its message and `ExceptionState`; the incident model stores both and workflow state contains the incident collection. Protected data therefore needs suppression before early logger/incident copies as well as an authorized projection, not only encrypted storage, mapper filtering, or hidden Studio fields.

The E2 source audits on [#8890](https://github.com/elsa-workflows/elsa-core/issues/8890#issuecomment-6304516651), [permission matching](https://github.com/elsa-workflows/elsa-core/issues/8890#issuecomment-6304689763), and [tenant binding](https://github.com/elsa-workflows/elsa-core/issues/8890#issuecomment-6305029397) pin their observations to `488ace13b509b64bd15ecfe23e73cc980c3a4941`. ASP.NET Data Protection registration in SasTokens does not qualify durable key storage or restore. The Secrets protector uses one configured AES-GCM key and is not the contextual, historical-key contract needed here. Permission declarations become anonymous when global endpoint security is disabled. Header-based tenant resolution selects a tenant but does not establish authenticated ownership. These findings define design work, not a demonstrated exploit or passed runtime proof.

## Options

1. Store captures in root workflow state and rely on generic instance/execution APIs or UI redaction. Rejected: current serializers, mapper, exception logging, and incident creation can copy the state and values into ordinary disclosure surfaces before read-time filtering.
2. Reuse the existing Secrets protector unchanged. Rejected: its one configured AES-GCM key does not supply the proposed tenant/instance/occurrence/purpose binding or the host's persistent historical-key restore proof.
3. Use any injected Data Protection provider and authorize detail through the existing instance `view` permission. Rejected: provider registration does not qualify key continuity; broad `view` grants and disabled endpoint security do not protect detail; tenant selection is not principal ownership.
4. Add a narrow internal recovery-capture adapter over host-configured ASP.NET Data Protection, suppress protected values before ordinary record/log/incident copies, expose a safe allowlisted summary, and require a separate protected-detail grant plus exact tenant ownership. Select this for Security/Core/Studio review as the bounded E2 proposal, with capture fields constrained by existing sensitivity and Secrets policy.

## Proposed direction

Protect immutable, schema-declared, policy-approved recovery fields with context tied to schema, exact tenant and instance, stable recovery occurrence, and capture kind. Preserve the opaque protected bytes and the obligation metadata whenever decryption or admission fails. Represent the original cause only through a bounded sanitized form; do not select arbitrary exception graphs or raw message/stack by default. Do not capture authentication headers/tokens or resolved Secrets material. If a participant needs a credential, prefer existing server-side Secrets reference resolution under existing authorization; neither the reference nor its secret is returned through recovery summary/detail, and protected-view grants no Secrets read. If this cannot reproduce a required input safely, reject that participant before effect. Require host evidence for persistent/shared-within-profile keys, stable application identity, new-process decrypt, and historical-key restoration. Do not claim at-rest key protection from a persistence location alone and do not specify a key backend or retention duration here.

Ordinary reads receive only an allowlisted recovery summary with server-generated opaque IDs for occurrence-to-attempt-to-concrete-execution navigation and pinned-version provenance, fixed code-defined status/reason categories, and bounded counts/timestamps. The summary preserves forward-operation and recovery outcomes separately. Exact route/DTO spellings remain open. A protected-detail projection uses a separately authorized candidate `protected-view` verb, proposed on `workflows/instances/recovery-data`, pending caller and permission-catalog review. The candidate resource spelling does not impose exact-resource matching: a matching resource-pattern grant carrying that explicit verb may authorize the projection under Elsa's native matcher. The existing instance `view` baseline and authenticated exact owning-tenant authority remain required; ordinary `:view` permissions alone remain summary-only, and explicit native all-verb wildcards retain their current semantics. Every protected read or mutation independently checks authenticated exact owning-tenant authority. A configured default tenant remains supported only through the host's existing explicit null/empty normalization. Wildcard read visibility and request selectors do not establish ownership.

The proposed first profile is one local host with endpoint security and tenant filtering enabled, and a validated issuer whose authenticated identity has a trusted exact tenant claim. API-key and name-only tenant resolution are excluded until their actual binding path passes proof. Unsupported profiles fail before protected reads or effect-capable activation. General secret-origin redaction remains owned by #8778, but its completion and generic origin-tracking coverage are not assumed; this contract defines recovery-value classification and requires proof at every source boundary, including early exception logs and incident copies. #8181 remains separate external-auth/database-selection work.

Full instance export, import, variable and alteration paths, single/bulk deletion, execution listing/detail, activity/workflow incident reads, exception and execution logs, and live notifications must preserve this boundary. For supported protected work, sanitization/suppression must occur before a raw exception reaches middleware logging, fault signaling, incident construction, or execution-log copying; later fault handling, mapper redaction, or read masks cannot retract those copies. If an operation boundary cannot make every early copy safe without changing required failure behavior, reject the participant/profile before its effect. Preserve existing exception/log behavior for unprotected workflows. Studio reads through the server projection and clears cached detail/selection when backend, tenant, or environment changes. M4 operator mutation UI remains out of scope.

## Consequences and gates

- This ADR and the [E2 contract](../../core/docs/specs/native-compensation/recovery-data.md) are proposals. They freeze no route, DTO, role policy, cryptographic algorithm, key backend, or numeric retention rule.
- E2 proof includes new-process decrypt, integrity/context/missing-key failures with opaque-byte preservation, typed data-unavailable/blocked-admission reasons and zero effects; no participant `Unknown` or journal status is inferred when decryption or status verification fails. It also proves safe non-credential summary/detail with occurrence-to-attempt-to-execution navigation and pinned-version provenance, separate forward/recovery outcomes, baseline plus exact-resource and matching resource-pattern grants carrying the explicit `protected-view` verb, denial of broad `:view` grants, exact JWT-to-tenant binding, disabled-security/filtering rejection, configured-default and wildcard negatives, generic disclosure/import negatives, suppression before the first exception log and all incident/execution-log copies, unprotected compatibility, and the actual Studio authenticated read/cache-clear path.
- E1 must first provide the accepted guarded admission/commit and byte-preservation boundary; E3 must provide the actual Studio path. Until then, design is independent but no protected M1 profile is qualified.
- No purge may remove eligible, unresolved, unknown, or in-flight obligations, required pins/captures/evidence, or needed decrypting keys. Product + Hosting + Security must choose numeric retention, erasure, backup horizon, and key retirement before M5/purge support, or earlier if those choices invalidate M1 qualification.
- M4 owns operator mutation UI. There is no implementation, endpoint, schema, migration, or production support claim in this decision.

## Revisit

Review after the named Security, Core, Studio, Hosting, Runtime, and Persistence owners accept the contract and its proof boundary. Revise before M1 readiness if the native guard cannot preserve opaque captures through hydrate, import, mutation, delete, or restore; if the actual caller needs a different safe summary/detail; if protected participant failures cannot be sanitized before generic log/incident paths; or if the host cannot retain the keys required by unresolved obligations. Resolve retention and key-retirement policy before purge/retirement is supported.
