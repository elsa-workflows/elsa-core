# Preserved maintenance build rehearsal

Task [#8677](https://github.com/elsa-workflows/elsa-core/issues/8677) prepares Core-controlled build/test/NuGet-pack proofs for original Studio and Extensions 3.8.4/3.9.0 trees. It does not activate a writable maintenance home, publish packages or retire source repositories. Individually selectable future Core/Studio/Extensions releases remain a separate deliverable under #8217.

The [source register](maintenance-source-register.json) admits exactly four product/line/original-commit bindings. Earlier advertised 3.8.1/3.8.2 refs remain historical provenance only. Existing Core `release/3.8.4` and `release/3.9.0` refs are untouched. Source trees remain rooted at their original `src/`, solution and build paths; consolidated `core/`, `studio/` and `extensions/` layouts are not backported. Original source histories and source-pinned Elsa/ElsaStudio 3.8.4/3.9.0 dependencies remain intact.

## Run a nonpublishing proof

Use a reviewed, clean Core checkout with all history and SDKs 8/9/10, Node 22 and Python 3.12 on an isolated hosted runner. All four source commits are ancestors of the reviewed Core baseline `8802a883d6`; `fetch-depth: 0` obtains them without source repository fetches or new remote refs. The controller rejects missing objects, changed parent/tree/workflow inventories and unregistered selections. Source checkout uses a local Git fetch without tags or credentials and sets the original public repository URL solely for truthful original-source metadata.

```sh
python scripts/integration-program/prepare_maintenance_build.py \
  --product studio --line 3.8 \
  --commit 9bff3f785fd13bd80a3a7ecf88fec4aec8eef7ae \
  --version 3.8.4-proof.12345.1 \
  --output /absolute/new/directory/maintenance-proof
```

The output must be new and outside the controller checkout. Only `MAJOR.MINOR.PATCH-proof.RUN.ATTEMPT` versions on the selected 3.8 or 3.9 line are allowed. Released versions, tags, arbitrary refs, cross-product commits, 3.10 versions and registry/token/command inputs are not accepted. This rehearsal has no version allocation or publisher capability.

The [workflow](../../.github/workflows/prepare-maintenance-build.yml) runs four independent jobs on the temporary reviewed `codex/maintenance-builds-8677` push branch. After registration on main, manual dispatch accepts one explicit product, line, original commit and proof version; dispatch from other refs is skipped. Registration on main is routine nonpublishing verification, not publisher activation. Each job has `contents: read`, `actions: none`, checkout credentials disabled, no OIDC, environment, registry secret or publisher action. Source subprocesses receive a small environment allowlist excluding GitHub/registry credentials and Actions output/authority handles. Historical workflow YAML and composite publisher actions are never invoked. Only Actions evidence artifacts are uploaded.

Studio 3.8 builds both original ClientLibs, then builds, tests and packs `Elsa.Studio.sln`. Studio 3.9 first restores the Designer project and checks generated BPMN types and ClientLib tests before building those assets. Extensions invokes its original `./build.sh Compile+Test+Pack --version VERSION --analyseCode true`. The fixed proof-only `EmbedUntrackedSources=true` MSBuild property is passed explicitly to Studio build/test/pack and through the controlled environment to the original Extensions NUKE recipe. The receipt records this property; source code and dependency pins remain unchanged. Extensions retains its source-configured `--analyseCode true` recipe: pinned NUKE supplies a per-project TRX logger, and the original build writes those results to `source/testresults`. Both products use the same strict actual TRX project/TFM verifier; runnable cells require positive passing results, and only the two source-bound placeholders described below can remain skipped; console `Passed!` summaries do not establish acceptance. There is no CustomElements publish or wasm/react npm packing in this task. Dependency builds required by these recipes are allowed; other products are not silently published.

## Evidence and current completion boundary

`receipt.json` is written on success and failure. `success:true` is assigned only after the original build/test/pack commands, positive execution of every runnable test cell and explicit accounting for inherited placeholders, complete evaluated package inventory, exact named assembly payload for every source-evaluated TFM and build-output policy, actual archive metadata/dependencies/frameworks, real DLL/PDB association and checksum verification, and SourceLink document checks pass. Each package and symbol archive has its original byte hash and size recorded. `published` and `maintenance_refs_activated` remain false. Evaluated inventory, sanitized structured counts/failure stages, verified package provenance and original archives are retained for 30 days under product/line/source/run/attempt artifact identities. Actions records the uploaded archive digest independently. A green workflow flag alone does not establish these checks; read the receipt and retained files. Raw command logs and TRX stay private on the runner and are not uploaded. Receipts contain numeric process exit codes and closed process outcomes, at most 32 compiler/NuGet/MSBuild diagnostic-code counts, exact recognized NUKE failed-target markers, known static verification reason codes (unknown failures stay unknown), expected test project/TFM cells, admitted observed cells and closed unknown/duplicate/positive-summary counts, relative source/project locators and counts; no raw exception text, machine identifiers or absolute runner paths are retained.

The safe base package inventory is retained immediately after evaluation, before test-evidence verification, symbol-helper preparation or SDK metadata staging. Failures in those later stages preserve that base inventory and a failed receipt; successful metadata staging replaces it with enriched public evidence.

After the original build/test/pack, each evaluated project stages SDK dependency metadata using `_GetRestoreProjectStyle;GenerateNuspec`, the same Release/proof-version/embedding properties, `NoBuild=true` and `ContinuePackingAfterGeneratingNuspec=false`. Package output is forbidden during this stage. Complete main and symbol dependency groups must match their respective SDK-rendered expectations, including third-party ranges, include/exclude metadata and empty framework groups. Main and symbol framework-reference groups must also match their respective SDK-rendered expectations, including empty groups, and target evaluated frameworks. Missing expected metadata fails. The existing same-line Elsa version and main/symbol agreement checks also apply. Retained inventory binds both kinds of expected groups to the staged nuspec hashes, unchanged actual restore-input hashes and resolved SDK/compiler identities. Raw nuspecs and restored assets remain private inside the unretained source checkout; this stage does not rebuild or repack products.

PDB maps must name the original source repository and exact original commit. Tracked document checksums are compared with immutable original Git blobs, not workspace files regenerated during the build; mismatches cannot fall back to embedded content. Non-Git documents require matching embedded bytes plus a known family bound to the admitted original source, evaluated project and TFM, and verified actual resolved SDK, analyzer or restored generator identity. SDK metadata and the canonical Razor, Refit, logging, regex, JSON, resx and PolySharp families use exact project/Release/TFM paths. Physical gRPC and ProtoGrain families use explicit original Extensions project/path bindings; LocalCache grains are admitted only for 3.8. Their embedded bytes are producer-bound, not independently regenerated. Unmapped documents are limited to audited manifest Hints from the exact officially pinned `.50` archive, matching archive-entry and extracted bytes and actual resolved Compile input membership. Unknown paths, families or missing/ambiguous producer evidence fail even when embedded checksums match. Receipts use closed `[embedded]/document-N` locators and allowlisted family/producer identities, hashes and archive entries. Absolute compiler, targeting-pack, package-cache and input paths stay private.

Assembly identity must match evaluated AssemblyName. Only explicitly evaluated IncludeBuildOutput=false permits an assembly-free package. Per-framework SDK SatelliteDllsProjectOutputGroupOutput items supply exact culture-relative satellite paths; their archived bytes must equal the emitted FinalOutputPath bytes and recorded hash. Resource satellites are recorded separately and do not require primary-style external PDBs. Unlisted nested DLLs are rejected. Assembly versions and informational versions are recorded as actually built; consolidated 3.10 assembly assertions are not applied. The real accepted `VerifyPackageSymbolPair` helper verifies the Portable PDB identity and normalized checksum and reports the unchanged PDB hash.

An empty PDB document table is admitted only when real PE inspection validates any present method-body RVAs and reports exact integer zeros for executable bodies, nonabstract bodyless methods and native/external methods, a positive real non-module type count, and a known false reference-assembly flag. Missing, malformed or ambiguous shape evidence fails. External PDB association, identity/checksum, original-commit SourceLink and package checks still run. The receipt records `no-documents-no-executable-method-bodies` applicability and actual counts; this is no source-document coverage claim. Assemblies with any documents retain the full checksum verification, and executable assemblies without documents fail. No package-name exception is used.

Both registered Extensions releases intentionally contain two all-placeholder test cells: Azure Service Bus `AzureServiceBusTests.WorkflowReceivesMessage_WhenSendingMessageToTopic` (`Skip="TODO"`) and Slack `CreateChannelTests.ExecuteAsync` (`Skip="Not implemented yet."`). The [source register](maintenance-source-register.json) binds each exception to both exact original commits, the original source-file blob, project/net10.0, class, method and literal skip reason. The controller validates immutable source binding before admitting it. Each cell must still produce exactly one linked TRX definition/result for that known class/method, outcome `NotExecuted`, a `Completed` summary, matching test/execution ID chains, and exact original-logger counters `total=1, executed=0, passed=0, failed=0, notExecuted=0`. The sole actual `NotExecuted` result is independently counted as `not_executed_result_count=1`; the logger counters are preserved without normalization. All standard TRX counters must be present and numeric; unknown counters are rejected without retaining their names. Error, timeout, aborted, inconclusive, warning and other nonpassing counters must be zero for both categories. Runnable cells also require a single `Completed` summary. Unknown runtime representation fails; it is not normalized or inferred from a successful command.

These results are recorded separately as `inherited_skipped_placeholders`, with source identities and counts. They are never counted as passing tests or live Azure/Slack provider coverage. Every other evaluated project/TFM cell requires positive, linked passing results, zero failures and zero unexpected nonexecutions. Missing, duplicate, new/unknown placeholder identities and changed source/skip bindings fail. The verifier collects the full available result set before rejection, retaining known project/TFM counters and closed failure codes; raw unknown test names, result IDs, paths, messages and TRX stay private. This preserves the historical coverage gap without changing release source or requiring credentials/provider implementations.

Runnable TRX cells support flat dynamic-theory executions that share one unique test definition. Every result must have a globally unique nonempty execution ID, reference a known definition, and match exactly one `(testId, executionId)` TestEntry; the complete entry and result sets must agree. Each definition has exactly one Execution anchor belonging to its own result group. Every flat result must pass and agree with the full execution counters and single `Completed` summary. Duplicate, empty, orphaned or conflicting identities, nested results and unsupported aggregate structures fail. Safe per-cell structural diagnostics retain only definition/result/entry/unique-execution/repeated-definition counts and linkage/summary booleans; they retain no raw identities or test names. The inherited-placeholder policy still requires its sole exact definition/result/entry.

## Locally prepared containment descendants

The [containment ledger](maintenance-containment.json) records deterministic local-only descendant commit/tree identities, their exact original parents, and every workflow move with unchanged blob/mode. Review the four small patches in [maintenance-containment](maintenance-containment). Only `.github/workflows/*` paths are moved to `.github/maintenance-inert-workflows/*.source`; release code and original ancestry are unchanged. No branch/tag refs are created by preparation, and no whole-history bundles are needed. Recreate the objects and patches without moving refs:

```sh
python scripts/integration-program/prepare_maintenance_build.py \
  --prepare-containment --output /absolute/new/directory/containment
```

These commit objects are not assumed to survive Git garbage collection. The exact deterministic inputs and patches recreate them; compare resulting parent/tree/commit/blob identities with the ledger before use. Patch generation pins rename detection, prefixes, ordering, relative-path and external-diff/textconv/color settings. Conflicting local settings are covered by a regeneration contract. Do not push these descendants or their raw historical parents as maintenance branches during this rehearsal.

A contained new tip does not disable historical workflow dispatch/release/rerun paths or revoke broad Core repository/organization Feedz aliases. Remote maintenance ref creation requires the separate reviewed authority handoff, historical-path review, protection configuration and accounting for credentials already loaded into queued/running jobs. Stop on unknown authority or changed evidence. Local cleanup requires no rollback of remote refs because none were created. Publication recovery and source archival are outside this rehearsal.

Future Core-created maintenance commits require a separately verified admission/provenance adaptation: accurate Core repository metadata, remotely reachable Core SourceLink and dependency compatibility. Original-source proof does not establish that adaptation, a completed publisher handoff, npm ownership implementation, or full 3.10 acceptance.
