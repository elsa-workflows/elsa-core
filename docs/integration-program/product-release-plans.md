# Individual product release plans

This nonpublishing planner is the first bounded deliverable under #8217. It describes one product, historical source line and explicitly requested version. It does not allocate that version, create a tag/ref, build or publish product artifacts, or complete the individual-release/publisher and operational-cutover gates.

Run from a clean controller checkout with .NET SDK **10.0.300** installed. Private tooling/source parents pin that SDK with roll-forward disabled, without changing historical tracked files:

```sh
PYTHONDONTWRITEBYTECODE=1 python3 scripts/integration-program/plan_product_release.py \
  --product extensions --line 3.8 --version 3.8.5 \
  --output /absolute/new/private-plan-directory
```

Products are `core`, `studio`, and `extensions`; supported historical lines are `3.8` and `3.9`. A `3.10` request produces an explicit `aligned_baseline_pending` ineligibility receipt. Product-qualified tags remain a proposal. The finer Slack release-unit manifest and sealed 225-package executor remain separate contracts.

## Source and membership

Core observes its exact `release/3.8.4` or `release/3.9.0` branch commit/tree and separately records a bounded matching-tag-ref snapshot, without claiming complete tag history. A release branch need not equal a stable tag. Per-package registry indexes remain the version-history authority. The controller must contain the observed source objects; otherwise the command fails closed. Studio and Extensions use the four exact admitted maintenance descendants in `maintenance-core-candidates.json`, validating complete original/contained/bridge ancestry and declared source deltas with the existing admission verifier. An admitted parent's unregistered descendant is never inferred as an authorized source. Current-main project references do not replace historical dependency evidence.

Every tracked C# project is evaluated in the original layout. Publication scope is restricted to packable, non-test, source projects in that source's original release solution, with explicit excluded membership for nonpackable projects, samples/tooling and projects outside the original recipe. For example, the Core3.8 tracked `Elsa.Testing.Extensions` project is visible but absent from its historical release solution, so its packability alone does not authorize a new outgoing package.

The [settled Secrets ownership disposition](consolidation/secrets-legacy-package-disposition.md) binds the four `Elsa.Secrets.Persistence.EFCore*` IDs to Core and `Elsa.Studio.Secrets` to Studio for both lines. Their five historical Extensions occurrences stay visible as ownership exclusions; the five legacy Secrets Api/Core/Management/Models/Scripting packages remain Extensions-owned. The receipt binds the reviewed policy's hash. Logical product ownership is distinct from publisher home: the October8 #8216 decision places maintenance publishing in Core, and this planner activates no publisher.

Selected/excluded project membership is a complete disjoint partition. Package IDs are case-insensitively unique within the selected inventory. Outgoing publication prerequisites and affected build/test closure never expand publication scope. Test impact uses the existing project/package-reference graph; it is a plan, not evidence that tests ran.

## Pre-build metadata and prerequisites

The SDK generates real nuspecs after restoring the exact historical source inputs, with `NoBuild=true` and `ContinuePackingAfterGeneratingNuspec=false`. Two explicit metadata-only projections suppress unavailable compiled **file collection**: `IncludeBuildOutput=false` and `ElsaPackageManifestIncludeInPackage=false`. They preserve actual dependency/framework groups. The receipt retains original per-TFM output/symbol/manifest requirements, the restored generator target identity, SDK pack-target hash and restore-assets hash. It creates neither DLL placeholders nor synthetic manifests. Future real artifacts must contain and verify their genuine compiled outputs/manifests. Missing or failed metadata stays `source_metadata_unavailable`; members are retained, and the plan is ineligible.

For each actual outgoing nuspec dependency/TFM, the plan retains its range and the exact version resolved by that source's NuGet restore. The SDK's NuGet.Versioning parses/compares versions and ranges; NuGet.Frameworks chooses the nearest compatible dependency group. Bare `1.0` is an inclusive minimum, `[1.0]` is exact. The planner is not a new restore solver. Selected-package dependency intent uses the cohort's requested version, checked against its actual source range. Private/build-only package references remain inventory/restore provenance and are not mislabeled as outgoing publication dependencies.

The SDK's NuGet.Configuration evaluates only the exact source `NuGet.Config` with `Settings.LoadSpecificSettings`, matching explicit `RestoreConfigFile`. The actual restore assets must name that configuration alone and the same public sources; only the selected SDK's local library-pack source is additionally allowed. Its hash, enabled sources and each package's applicable source names are recorded without private machine paths. Only the six source cells' reviewed public nuget.org/Feedz endpoints are permitted; service-index discovery must return the exact expected PackageBaseAddress origin/path. Missing source names, unavailable services and malformed endpoints block eligibility. Historical configuration mistakes are retained rather than rewritten.

Fresh unauthenticated GET observations bind each applicable feed's exact version nuspec and full npm packuments to origin, observation time, byte length and SHA256. Requests reject redirects, read at most16MiB, time out after30seconds, and do not retry. Freshness is at most one hour; future/naive timestamps, wrong origins and mismatched identities are rejected. Per-feed missing and unavailable responses stay distinct. A dependency is missing only after every applicable feed reports missing; an unreadable applicable feed blocks the decision. Byte-different metadata for the same exact package/version across applicable feeds is explicit ambiguity. Missing, unavailable, malformed, duplicate/ambiguous, stale, wrong-version, range-incompatible or TFM-incompatible evidence blocks eligibility with a closed reason. Cache download origins are not fresh feed availability evidence. Dependency metadata compatibility does not certify package assets, transitive restore resolution or clean-consumer execution.

## Requested versions and Studio npm

Every selected package has its own full observed history from nuget.org's public publication authority plus applicable configured preview feeds, with separate feed observations and decisions. Restore mapping does not remove the public publication-history authority. NuGet's PackageBaseAddress version index includes listed and unlisted versions. Native normalized identity rejects reuse, including build-metadata/zero-revision aliases. The requested version must exceed every observed version on its selected major/minor line, including higher-patch previews; a newer minor line alone does not prohibit an older-line maintenance patch. A missing/unreadable history cannot certify novelty. The command normalizes the requested NuGet spelling and retains the original input. It allocates nothing.

Studio additionally plans `@elsa-workflows/elsa-studio-wasm` and `@elsa-workflows/elsa-studio-wasm-react` atomically at the same requested version/source. Original manifest and inert workflow hashes bind the historical same-run local-tarball and wrapper-dependency semantics. Checked-in versions/dependencies remain recorded as historical values; the same-version dependency is intent, not a rewritten source file or an artifact proof. Each npm member needs its own fresh full packument `versions` and `time` observations; retained version-time/tombstone evidence prevents reuse. This is current registry evidence, not a claim of complete unknowable lifetime history. Partial/unavailable evidence blocks the pair. Core and Extensions explicitly exclude both npm IDs. Current-main #8679 evidence is not relabeled as historical proof.

## Receipts and remaining gates

Only `plan.json` is intended for upload. The surrounding source checkout, restored assets, generated nuspec file lists and raw command logs contain private paths and remain private. Public receipts retain exact controller/source/tree/inventory identity, complete membership/reasons, expected nupkg/snupkg/npm filenames, each history check, prerequisite observations, applicable tests, SDK/NuGet identities, paired intent, eligibility and `published:false`. Expected filenames are not produced bytes. A genuinely blocked history/prerequisite is a successful planning observation with `eligible:false`; incomplete input/source evaluation is a failed command and must not be counted as a complete plan.

The read-only workflow runs six explicit hypothetical requests for Core/Studio/Extensions ×3.8/3.9 on matching pull-request changes. It never infers registry tips or expands a release set. Manual dispatch requires main and selects one product/line/version. Receipts include actual run/attempt identity; every execution refreshes observations. Contracts run normally and optimized alongside existing source-admission, Slack release-unit/test-closure and npm-pair guards.

After independent exact-head receipt review, the remaining #8217 deliverables are real selected artifact builds, applicable tests, clean consumers, atomic historical Studio npm artifact/consumer proof, and controlled artifact-only publisher/recovery. #8220 retains credential/authority activation, competing-publisher retirement, source archival and operational cutover approvals. The first aligned3.10 release remains a separate required deliverable. This planner supplies no approval or evidence for those actions.
