# Selected Studio control seal and original ZIP readback

This source-only interface supports the explicit Studio 3.8 selected control. Core, Extensions and Studio 3.9 remain rejected by this seal until their source-specific semantic adapters are joined and reviewed. Existing offline producer/consumer support for those cells does not imply hosted artifact acceptance. Actual proof order remains Studio 3.8, then generator-bearing Extensions 3.8, then the full six-cell matrix.

`selected_control_seal.py seal` freezes original plan, successful producer/consumer receipt, selected NuGet/symbol archives and historical npm pair bytes before inspecting them. It validates complete closed concrete writer schemas, exact source/controller/hosted job identity, historical plan admission at the producer's actual start, separate complete current consumer admission counts/time/digest, all selected package/TFM coverage and representative runtime coverage. Fixed trusted source contracts are loaded separately; the semantic validator never reads artifact-declared paths, environment, Git or network.

The Studio source contract pins the reviewed continuation's host/wrapper metadata, host project and inert original workflow. Npm validation uses the original historical archive schema: `file`, `name`, `version`, `sha512_integrity`, `inventory`, `package_metadata_sha256`. It recomputes full tar inventories, original package metadata with requested-version/dependency staging, paired SRI, original command ledger, generated lifecycle assets and copied dist bytes. There is no historical embedded provenance manifest or current-main npm helper transplant.

Every selected NuGet/symbol archive is compared to the original receipt's raw SHA256, size and complete member inventory. Actual nuspec identity, requested version, repository commit, dependency groups and framework references must match the admitted plan. All selected restored raw SHA256/SHA512, restored selected payload sizes/hashes and loaded runtime asset bytes join those exact archives. Native NuGet content hash, raw archive SHA512 and signed status remain distinct typed fields. Full original external catalog/native edge validation and original feed mapping were executed by the exact source-bound consumer; raw private catalog/assets are not uploaded or reconstructed from their public digest.

Private recipe-only outputs retain their original closed metadata, bound to excluded plan IDs and requested version, with safe basename/suffix, unique safe member paths, hashes and size ceilings. Their names need not be synthesized canonical filenames. Excluded archive bytes are forbidden in the upload. Raw diagnostics, TRX, caches, planning snapshots and private absolute paths are never staged. Incomplete/failed receipts cannot produce a success manifest.

The canonical staged names are `plan.json`, `producer/receipt.json`, `producer/nuget/<exact selected filenames>`, `producer/npm/<exact two tarball filenames>`, `producer/npm/receipt.json`, `consumer/receipt.json`, and `preupload-manifest.json`. Receipt/archive bytes are unchanged. The manifest binds full file closure, hashes, source/version, controller/context and distinct artifact/consumer execution envelopes. The external trusted workflow output supplies its digest; a transport-only manifest cannot authorize a control.

`selected_control_seal.py readback` verifies the untouched original provider ZIP against the closed projected repository/run/attempt/head/ref/workflow/control-job/artifact-ID/name/digest/size/expiry observation. It checks complete safe ZIP closure before repeating every semantic and nested archive join. It never extracts files or executes native/product/consumer code. It does not read the original control job's environment. Its own CLI requires a clean exact-controller checkout and rejects repository-read tokens in the Python process. The resulting separate receipt explicitly says the consumer executed pre-upload from those exact local bytes and that readback independently verified the original provider ZIP.

Compiler, native SDK/SourceLink, original test and representative runtime execution judgments are inherited through the exact successful, source-bound producer/consumer receipts. They are not rerun by Python. Studio's producer does not retain detailed native package verification rows; this seal does not invent such fields. Likewise, current eligibility observations remain private: readback validates the executed gate's public count/time/digest binding, not a recomputation of private GET results. Original Core tracked documents use the existing `original-git` branch without a remote-fetch claim; this Studio adapter introduces no Core policy.

The selected-only limits remain 2 GiB original ZIP, 8 GiB outer expanded bytes, 10,000 members, 512 MiB per raw/expanded package, 64 MiB receipt/manifest and 32 MiB plan. Failures reject bytes; there is no truncation or automatic expansion. Actual product output sizes remain an execution gate.

The separate workflow uses only the explicit trusted temporary push ref and a committed hypothetical Studio 3.8.5 request. It runs fresh planning/private snapshot, original producer, cold consumers and seal in one `contents:read/actions:none` job. It preserves the private planning cache independently of the producer cache. One cheap exact source commit/file checksum GET precedes product work; the original producer retains its complete SourceLink checks. It uploads only the newly validated staging folder.

The retrieval job has `actions:read/contents:none`, no checkout or repository imports, and only fixed GET requests. API redirects are disabled. A validated HTTPS object-storage Location is downloaded by a distinct credential-free opener, also without redirects; Authorization never crosses the API boundary. Original ZIP bytes and two safe projected JSON files are transferred separately. Readback checks their exact expected hashes and runs with `contents:read/actions:none`, an exact SHA checkout and an exact transport artifact ID. Current provider availability and eventual terminal workflow conclusion still require lead acceptance rechecks. No publisher credential, OIDC, protected approval, version allocation, tag or publication is introduced.

The workflow and validators have only offline adversarial fixture evidence. They have not run an actual hosted selected control. The fixed retrieval's object-storage origins, API field assumptions and six-hour control budget remain genuine hosted compatibility gates; unexpected provider behavior fails closed. No actual six-cell compatibility or release readiness is claimed.
