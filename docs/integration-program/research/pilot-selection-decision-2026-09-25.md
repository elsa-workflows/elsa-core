# Conditional pilot selection decision — 2026-09-25

## Decision

For [#8212](https://github.com/elsa-workflows/elsa-core/issues/8212), retain OneDrive, Moneybird, and Slack together in the catalog's rank-1 **validation cohort**. Select no customer-facing or live-provider pilot at this checkpoint. This decision validates three complementary workflow shapes; it does not by itself justify provider-backed implementation, contacting providers, registering apps, accessing accounts, or publishing packages.

The catalog's numeric demand scores are null for every candidate, and its demand-sensitivity intervals overlap for all 18 deep assessments. There is no evidence-backed winner within the cohort or against the other cohorts. The cohort order is conditional sequencing from program scope, operation coverage, reuse, and effort assumptions; it is not a popularity ranking. Revisit the candidate set when a specific user/sponsor, Elsa owner, and provider test path are documented.

## Evidence and demand limits

The [accepted candidate catalog](candidate-catalog.json) records 67 candidates, 18 deep assessments, 124 operations, six workflow hypotheses, and 172 source records, checked 2026-09-23. Its three rank-1 entries are `ms.onedrive`, `moneybird`, and `slack`. Source-backed API feasibility does not establish Elsa implementation, customer demand, live account access, or readiness for shared cloud.

- **OneDrive:** its catalog entry has no direct demand evidence. The proposed file-intake scenario is a program hypothesis, not a customer request or sponsor commitment.
- **Moneybird:** its entry has no direct demand evidence. The paid-invoice notification is a bounded workflow hypothesis, not evidence that an accounting customer wants or will operate it.
- **Slack:** the catalog records one historical public request, [Extensions #89](https://github.com/elsa-workflows/elsa-extensions/issues/89), created 2024-06-09 and closed 2025-10-10, for approval workflows with Cognito/Step Functions handoff. It is a lead, not a present sponsor, volume estimate, or validation of current Slack triggers. The [#26 comment](https://github.com/elsa-workflows/elsa-extensions/issues/26#issuecomment-2660720464) says the listed activities were ideas, not a request to implement all of them.

Charter inclusion, public connector directories, activity counts, and package proof do not count as verified demand. No candidate receives a demand score until comparable, authorized user evidence exists. No owner or sponsor is currently named in the catalog.

## Exclusions and uncertainty

- No numeric demand comparison, target-provider winner, sponsor, support rotation, engineering owner, or customer pilot is claimed.
- No live OAuth, app verification, provider test account, production tenant, customer record, sandbox, or provider contact was used.
- No OneDrive arbitrary-file ingestion, unselected cross-tenant copy, or unbounded transfer is in scope. Folder/deleted items are skipped; changed bytes require current metadata reconciliation.
- No Moneybird write-side invoice creation, bookkeeping/tax policy, or cross-connection administration mapping is in WF-02.
- No Slack message search or watch trigger is in the initial operation slice. Existing Slack package identity/activity contracts must be audited and preserved; a package or offline fake-client proof is not workspace behavior.
- Provider terms, tenant policy, actual admin consent, app review, sandbox fidelity, data residency, operations/on-call burden, and customer willingness remain unknown. The catalog's engineer-day ranges assume reusable OAuth/connection, webhook, and rate-limit infrastructure that is not yet established; they exclude approval delays.

## Selection gates and next actionable task

All of these gates apply before assigning a provider pilot or implementation commitment:

1. **Demand:** an authorized user or sponsor supplies one real, bounded workflow, frequency/value context, and acceptance outcome. Record only approved, sanitized evidence; do not turn public idea issues into demand counts.
2. **Ownership:** an Elsa maintainer accepts responsibility for code, support, provider changes, and credential/event lifecycle operations.
3. **Platform:** the required connection/secret lifecycle, authorization boundaries, durable event handling, retries, idempotency strategy, file controls, and diagnostics are reviewed against the selected slice. Provider-specific trigger work depends on E4/E5 outcomes.
4. **Provider readiness:** a user-controlled test tenant/admin/workspace and documented consent path are available; least scopes and any provider app review are understood.
5. **Acceptance:** the workflow passes offline contract/replay tests and then a bounded provider test, with privacy, retention, recovery, and failure outcomes reviewed.
6. **Release:** package ownership, supported compatibility, and any publisher/cutover approval are separately established. This decision grants no publication authority.

The actionable next task that needs no provider credentials or external publication is to refine those child work plans around the operation slices and gates above, and prepare synthetic/offline contract, replay, redaction, and failure fixtures.
