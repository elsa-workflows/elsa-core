# Workflow definition registry reconciliation

Workflow-as-activity descriptors are cached in each node's local `IActivityRegistry`. Local mediator notifications update the writing node, so clustered nodes need a durable signal that their registry may be stale.

The management persistence layer stores a monotonically increasing generation per tenant, including a distinct `*` generation for tenant-agnostic definitions. Workflow-definition lifecycle handlers advance the generation after the definition store has accepted the change. Runtime nodes poll the current tenant and agnostic generations every five seconds with two indexed generation reads per active tenant per replica. The interval is configurable through `RecurringTaskOptions.Schedule.ConfigureTask<RefreshWorkflowDefinitionActivityRegistryTask>(...)`; component tests use a two-second override for a bounded catch-up proof. When either generation changes, the node invalidates that tenant's local workflow-definition query cache and reconciles its workflow-as-activity descriptors from the store. Cache entries subscribe to both the existing global local-write token and a tenant-scoped reconciliation token; an agnostic generation change makes each active tenant invalidate its own combined tenant-and-agnostic view. The poll is at-least-once and coalesces multiple mutations into one refresh; an offline node observes the latest generation after it returns. The five-second catch-up bound assumes a healthy shared store, a running scheduler, and successful generation and definition queries; failures can extend the delay.

Reconciliation replaces only descriptors visible to the current tenant: that tenant's entries and tenant-agnostic entries. It preserves all other tenant buckets and clears stale entries even when the provider now returns no descriptors. A periodic full reconciliation runs every minute, measured with a monotonic clock, to repair missed invalidations, including a process crash after a definition write but before its generation increment. This bound assumes the scheduler and store queries remain healthy.

The EF Core management persistence adapter stores generations in the shared management database. The default in-memory adapter supports single-node development and tests only; it does not synchronize separate processes. For an external definition store, a crash between its write and the generation increment can leave peers stale until the one-minute full reconciliation, provided the external store has made the change visible to readers. Atomic write-plus-invalidation requires that store to participate in the same transaction or provide its own durable change hook. Cross-pod convergence also requires every node to read the same durable generation store and workflow-definition source.
