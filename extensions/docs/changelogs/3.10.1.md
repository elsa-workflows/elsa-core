# Elsa 3.10.1 — Extensions notes

## Persistence (Dapper)

- Dapper `Store<T>` now matches EF Core tenant-agnostic visibility on reads: a concrete tenant also sees `*` rows (and the default tenant still sees `NULL` / `''` rows). [#9010](https://github.com/elsa-workflows/elsa-core/issues/9010)
- `DapperWorkflowDefinitionStore.TryUpdateLatest` uses the same `*` read visibility, so a concrete tenant can update the latest version of a shared definition without restamping it. [#9023](https://github.com/elsa-workflows/elsa-core/issues/9023)
- Upserts and `UpdateAsync` are scoped to the tenant. A save whose Id already belongs to another concrete tenant throws instead of overwriting that row.
- Stamping keeps an explicit `*`, stamps only when `TenantId` is null, and throws when an explicit concrete tenant id differs from the ambient tenant. A concrete tenant cannot restamp an existing `*` row to itself.
- **SQLite hosts must use SQLite 3.24 or later.** The Dapper provider emits `INSERT … ON CONFLICT DO UPDATE` (UPSERT) instead of `INSERT OR REPLACE`. Microsoft.Data.Sqlite with the bundled e_sqlite3 engine already meets this. A host that swaps in an older system SQLite library will fail on save.

## Upgrade: multi-tenant Dapper hosts

`ClrWorkflowsProvider` marks a workflow as shared when the workflow identity declares no tenant (`workflow.Identity.TenantId ?? "*"`). Before 3.10.1, Dapper restamped that `*` to the ambient tenant and moved the row on each load, so upgraded databases hold each such definition under the last tenant that loaded it.

On the first startup after this patch, the definition-store populator re-stamps each CLR (`ProviderName = 'CLR'`) row to the tenant declared in code. No operator SQL is required, and startup does not throw:

- A shared CLR workflow (no declared tenant) that was stamped to the last loading tenant is re-stamped to `*` and becomes visible to every tenant again.
- A CLR workflow that declares a concrete tenant and was stored as `*` is restored to that tenant and is no longer visible to or runnable by other tenants.
- Non-CLR rows are not re-stamped. Normal `Store<T>` saves still refuse a tenant takeover of `*`.

Single-tenant and fresh multi-tenant hosts do not need a data step: the default tenant still sees `NULL` / `''` rows, and a new database stores shared CLR workflows as `*`.
