# Elsa 3.10.1 — Extensions notes

## Persistence (Dapper)

- Dapper `Store<T>` now matches EF Core tenant-agnostic visibility on reads: a concrete tenant also sees `*` rows (and the default tenant still sees `NULL` / `''` rows). [#9010](https://github.com/elsa-workflows/elsa-core/issues/9010)
- `DapperWorkflowDefinitionStore.TryUpdateLatest` uses the same `*` read visibility, so a concrete tenant can update the latest version of a shared definition without restamping it. [#9023](https://github.com/elsa-workflows/elsa-core/issues/9023)
- Upserts and `UpdateAsync` are scoped to the tenant. A save whose Id already belongs to another concrete tenant throws instead of overwriting that row.
- Stamping keeps an explicit `*`, stamps only when `TenantId` is null, and throws when an explicit concrete tenant id differs from the ambient tenant. A concrete tenant cannot restamp an existing `*` row to itself.
- **SQLite hosts must use SQLite 3.24 or later.** The Dapper provider emits `INSERT … ON CONFLICT DO UPDATE` (UPSERT) instead of `INSERT OR REPLACE`. Microsoft.Data.Sqlite with the bundled e_sqlite3 engine already meets this. A host that swaps in an older system SQLite library will fail on save.

## Upgrade: multi-tenant Dapper hosts

`ClrWorkflowsProvider` marks a workflow as shared when the workflow identity declares no tenant (`workflow.Identity.TenantId ?? "*"`). Before 3.10.1, Dapper restamped that `*` to the ambient tenant and moved the row on each load, so upgraded databases hold each such definition under the last tenant that loaded it. After this patch the other tenants cannot see that row, and saving a new `*` record with the same Id throws `already exists in another tenant`.

**If any code-first (CLR) workflow declares a concrete tenant, exclude those definition ids.** The declaration lives in code; SQL cannot see it. Resetting those rows to `*` would make the workflow visible and trigger-runnable for every tenant.

If such a row is wrongly reset to `*`, that workflow is visible to and runnable by every tenant until `TenantId` is restored to the declared tenant. The next startup does not treat the row as shared: the populator logs an error, skips trigger indexing, and leaves `TenantId` as `*`. Re-running the reset statement with that `DefinitionId` excluded changes 0 rows and does not undo the reset. Dapper will not restamp a `*` row to a concrete tenant. Use the restore `UPDATE` below, then restart.

Then run the matching reset statement and restart so each tenant can load the shared definition and re-index its triggers. Replace the placeholder list with the definition ids of every CLR workflow that declares a tenant; omit the `AND` clause only when none do.

**Reset shared CLR rows — SQLite, SQL Server, and MySQL** (unquoted FluentMigrator identifiers):

```sql
UPDATE WorkflowDefinitions
SET TenantId = '*'
WHERE ProviderName = 'CLR'
  AND DefinitionId NOT IN ('tenant-declared-definition-id');
```

**Reset shared CLR rows — PostgreSQL and Oracle** (quoted, case-preserved identifiers):

```sql
UPDATE "WorkflowDefinitions"
SET "TenantId" = '*'
WHERE "ProviderName" = 'CLR'
  AND "DefinitionId" NOT IN ('tenant-declared-definition-id');
```

To restore a wrongly reset row, set `TenantId` back to the declared tenant for those `DefinitionId` values:

**Restore a wrongly reset row — SQLite, SQL Server, and MySQL:**

```sql
UPDATE WorkflowDefinitions
SET TenantId = 'tenant-a'
WHERE ProviderName = 'CLR'
  AND DefinitionId = 'tenant-declared-definition-id';
```

**Restore a wrongly reset row — PostgreSQL and Oracle:**

```sql
UPDATE "WorkflowDefinitions"
SET "TenantId" = 'tenant-a'
WHERE "ProviderName" = 'CLR'
  AND "DefinitionId" = 'tenant-declared-definition-id';
```

Dapper ships SQLite, PostgreSQL, and SQL Server dialects. The same tables are created for MySQL and Oracle through FluentMigrator; use the quoted form on Oracle and the unquoted form on MySQL.

Single-tenant and fresh multi-tenant hosts do not need this step: the default tenant still sees `NULL` / `''` rows, and a new database stores shared CLR workflows as `*`.
