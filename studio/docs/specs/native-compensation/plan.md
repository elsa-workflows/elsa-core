# Elsa 3 Studio compensation interaction design

Status: proposed design for [#8896](https://github.com/elsa-workflows/elsa-core/issues/8896), 20 October 2026. Backend source, semantics, persistence, security and remaining decisions live in the [Core packet](../../../../core/docs/specs/native-compensation/README.md). The [E3 native Core/Studio caller contract](../../../../core/docs/specs/native-compensation/e3-studio-contract.md) is canonical for source-verified child serialization/traversal, strict pins, the real Save + Publish diagnostic caller and safe occurrence/attempt/execution navigation. This plan owns the visual interaction and accessibility behavior. The [21 October standing authorization](https://github.com/elsa-workflows/elsa-core/issues/8884#issuecomment-6303225186) permits end-to-end delivery through actual readiness gates; E1–E3 still prevent premature M1 readiness. Follow [Studio guidance](../../../src/AGENTS.md) and the [design system](../../design/system.md).

## Elsa 3 implementation boundary

Use Blazor components in focused Studio modules and existing activity descriptor/input/output editors. The StateMachine custom designer, embedded-activity resolver and validation are the precedent for owned forward/handler children; X6 activity-port providers map diagram connections, not paired composite slots. Extend the owning Workflows module through public contracts and notifications; do not reach into unrelated module internals. Preserve existing package/activity/serialization identities and supported Server/WebAssembly boundaries.

The Elsa 4 paired-step semantics are reused, not its React/Vite components, structure facets, `enterSlotScope` APIs or runtime projections. The reviewed E3 contract identifies native child traversal/serialization and exact extension placement for a bounded effect-free authoring prerequisite; its implementation must verify them through explicit draft round-trip, negative-publication and child-execution-refusal tests. Effect-capable M1 activation and acceptance still require integrated E1–E3 proof.

## Effect-free authoring prerequisite

The bounded #8956 slice adds `Elsa.CompensationScope` v1 with draft schema 1, stable `StepId` rows, separate pinned forward/handler children, the O3 draft setting, and a native paired-row designer. It preserves mapping records as read-only metadata and preserves unsupported scope/child pins as opaque evidence. The dedicated `Elsa.NativeCompensationDraftAuthoringV1` feature advertises only this draft-authoring surface. A missing or unverified fresh feature catalog leaves an existing compensation document read-only and blocks creation, import, and save.

Native draft editing also requires a positively participating authenticated request binding. Studio Core's optional `IBackendRequestContextBinding` matches its per-circuit context epoch to the exact `IPermissionRefreshSignal` used by ElsaIdentity's token provider. The configured handler resolves the current circuit services, awaits token acquisition, then validates the bound context before it writes the Authorization header or sends the request. The final Refit Save/Publish write is wrapped in that binding. Legacy URL-only providers and authenticated providers without this active signal binding keep ordinary workflow calls but cannot enable native compensation editing. ElsaIdentity is the first supported Server and WebAssembly auth profile; Security and Studio review is required before enabling OIDC or custom transports. This is a draft-write safety boundary only and does not qualify publication, execution, M1 or E1. The token provider observes every stored/refreshed token, including still-valid tokens, and advances the same signal when the canonical security-claim fingerprint changes. Only exp/iat/nbf/jti are excluded; tenant, issuer, audience, subject, permission, role, session and custom security claims remain identity context. A missing or unparseable token cannot preserve an active native write binding. Lifecycle-only refreshes preserve the context. The registered permission signal is injected independently of an optional authentication-state provider; ordinary legacy constructor calls remain compatible.

Every scope remains unpublishable and unexecutable in this slice, including an already-published stored row. Core refuses the entire graph before owned-child scheduling on supported Runner, built-in pipeline and invoker paths. This does not implement a participant, capture binding, journal, external effect, recovery action, or successful compensation path. It does not qualify M1 or satisfy E1–E3 persistence, participant, disclosure, restart, or integrated browser proof; those gates remain open.

## Authoring — sequential

```text
Order fulfilment > Compensation scope: Reserve and recover
Steps run top to bottom. Recovery undoes eligible occurrences newest first.

#  Operation              Forward             Compensation          Capture
1  Reserve inventory      [Reserve inventory] [Release inventory]   [reservationId -> targetId]
2  Reserve delivery       [Reserve delivery]  [Cancel delivery]     [deliveryId -> targetId]
3  Reject order           [Reject order]      [Add handler]         —

[Add step]     After successful recovery: [Continue with Compensated (default) | Propagate original fault]
```

Each row carries stable opaque StepId, separate editable label and stable MappingIds. Renaming/reordering never changes existing runtime identity. Delete/recreate creates a new StepId. Node/activity IDs identify child locations, not logical external operations; one StepId can produce many forward OccurrenceIds, each with its own forward OperationKey and recovery UndoKey. Draft JSON contains native child activity definitions plus stable IDs/mappings; exact serialized field/public names are not frozen here.

Row actions: rename, named Move up/Move down controls for reorder, open forward activity, open/edit/remove handler, open capture mapping and remove step after confirmation. Breadcrumbs identify scope, step label and role. Do not use ordinary flow lines to imply that a handler executes on the successful forward path.

The M1 no-fault flow also has a minimal authored Confirm activity after scope Done, with an authored scope reference resolved to the exact retained occurrence. It closes eligible obligations before root completion under accepted O1 policy; runtime/Studio realization remains unproved. The bounded M1 validator rejects a reachable successful exit that omits it, at publication and again before effects. An already-armed invalid/altered instance remains visibly blocked with no supported M1 operator release path; it needs a separately authorized repair or later control. It cannot silently report workflow success. Wider targeting/cascade and operator confirmation remain later milestones.

Accepted O3 makes the displayed choice a per-scope published-version setting. After durable successful settlement, either continue through the distinct Compensated outcome or propagate the original fault; never run both outward paths. The inspector keeps forward failure and Compensated recovery history visible in either mode. Pending, failed or uncertain recovery cannot report successful compensation. Explain that propagation applies to fault-triggered recovery: an explicit non-cancellation recovery without an original fault uses Compensated even if the setting is enabled. O2 cancellation follows its Cancelled settlement path without inventing a fault. Backend/child-container support for these paths remains E1/E3 proof work, not a component capability claimed here.

## Captured-data mapping

```text
Release inventory — required input targetId
Source: [Captured output of THIS Reserve inventory occurrence: reservationId]
Type: String   Capture schema: 1   Target: targetId
[Validate mapping]
```

Show paired descriptor-backed outputs first. A mapping binds the exact forward and handler child activity type/version, descriptor property name and declared type, plus stable StepId/MappingId; display labels and row positions are not identity. M1 supports direct compatible assignments and compatible authored handler literals, but no converter transforms until a versioned immutable recovery-converter identity is reviewed. The declared capture schema must state required/optional, omission/default and nullable/explicit-null semantics: current Core descriptors do not establish these rules, so an unknown rule blocks the mapping. Freeze request capture at Armed; append result capture only on committed Applied. A lost response keeps request, keys and pins but leaves result data Unknown/unavailable; block a required handler binding until keyed lookup or deduplicated replay recovers and commits the result. Never fill a capture from current workflow variables or latest node output. Use the [canonical E2 recovery-data contract](https://github.com/elsa-workflows/elsa-core/blob/60aa5933f08ff14ba0332d05e2acb13d53003ca4/core/docs/specs/native-compensation/recovery-data.md) for classification, source suppression, protection and authorized previews; ordinary editor/run panels do not show protected values.

In occurrence detail, show distinct “Request captured at Armed” and “Result captured at Applied” panels with their committed ordinals when available. A lost response retains the former panel and marks result data unavailable; it must not synthesize a null result or imply a business outcome. Until keyed lookup or deduplicated replay commits the result, disable a handler whose declared required binding depends on it.

## Nested and loop examples (M3 notation, not M1 support)

```text
2  Delivery [Nested scope: Delivery]   Undo inner obligations, then optional outer handler
1  For each item: Reserve item         3 occurrences; each has its own captured values
```

Expand a nested scope's actual occurrence/owned entries. Unresolved inner recovery blocks the outer handler. Loop execution groups the authored row but lists concrete occurrences and iteration ancestry, each with separate operation key, capture and attempt history. Recovery order is the persisted completion ordinal; do not sort by label or browser clock. Selecting one iteration must not change the displayed capture to the most recent iteration. Unsupported nesting/loop shapes remain preserved in drafts and blocked at publication/execution until the backend advertises support.

## Publication and runtime validation

Core validation is authoritative. The normal Studio Publish action reads the current designer root, then calls `WorkflowDefinitionEditorService.SaveAsync(..., publish: true)` and the existing POST save endpoint. The #8956 draft-only implementation checks raw scope and owned-child pins before Latest fallback, then refuses publication independent of `ManagementOptions.FailOnValidationErrors`, before publication notification or state mutation. Both Save + Publish and stored Publish return the existing message envelope plus the feature-owned `NATIVE_COMPENSATION_DRAFT_ONLY` code and stable scope/activity, StepId, role, MappingId and related IDs. The stored endpoint checks historical rows before its already-published shortcut. Never correlate errors to rows by array index. An older server shows the message in an accessible summary without inventing a target; capability absence disables unsupported authoring and preserves the draft. This implementation never qualifies positive publication or execution; E1–E3 gates remain open.

Block publication for duplicate/missing IDs, missing forward children, effectful steps without qualified handlers, a reachable M1 successful exit without exact-scope confirmation, invalid handler pins, unavailable types/schema/converters, undeclared capture-input semantics, invalid mappings, unsupported effects/profiles/compositions and nonresolvable targets. Incomplete drafts can be saved and round-tripped without dropping unknown children. Unsupported draft schema remains readable/preserved with editing limitations; it is not published as an empty scope. Server execution also rechecks mandatory safety capability; it cannot substitute for the mandatory publish gate.

The bounded #8956 draft-only UI focuses an alert named “Native compensation publication refusal” with fixed localizable wording. Both Save + Publish and stored Publish recognize only the feature-owned code, including code-only or malformed diagnostic envelopes; unfamiliar errors retain existing behavior. Display only bounded, encoded stable identifiers and allow-listed roles, never server exception text or captured values. Details require a qualifying authenticated backend context; otherwise show the static refusal without identifiers. Identity/environment invalidation clears stale details. The shared typed diagnostic model is public because Workflows.Core parses the response and the separate Workflows UI assembly renders it; it is not a shared recovery abstraction. This summary does not promise row navigation through the custom owned-step collection.

Later qualified publication diagnostics must focus the correct step/control. Examples: “Reserve inventory needs a forward activity”; “Captured reservationId is unavailable for targetId”; “This backend has not qualified recovery for the selected persistence profile.” Do not hide a pre-effect safety requirement as an optional warning deferred to release polish. Studio owns the navigation work; revisit before positive publication is enabled. The draft-only candidate binds native import and template creation to the authenticated transport and sends the same owned root snapshot that was classified after supported callbacks. Stored single and bulk publication latch an established binding requirement through dispatch; losing that qualification fails closed. Legacy ordinary publication remains compatible after the native-draft check. A feature-owned client refusal uses the same static, identifier-free summary in both list handlers. These client checks do not qualify recovery operations or positive native publication; the backend's mandatory denial remains authoritative. The authenticated request boundary reads the token source's monotonic identity generation directly after token acquisition and validates that actual source against the registered transport. A delayed permission-refresh subscriber cannot preserve the old write context. Transport replacement or loss invalidates established bindings, including replacement back to a prior source; ordinary first-connection discovery remains compatible. This is a same-circuit client safeguard, not server tenant authorization or proof of a recovery operator grant.

Unsupported native scope shapes and recognized opaque wrappers make the containing document read-only, including Code View and its apply/save controls, even when draft capability is present. Resolver and designer selection use the same recursive native-wrapper recognition. Legacy stored-publication inspection uses logical definition IDs and the latest version; an unavailable view grant does not become a new prerequisite for an existing publish grant. Any readable native target is refused when draft capability is absent. A forbidden optional read preserves the original publish route, its authenticated context checks and the server's permission decision. This compatibility path cannot retrofit native refusal into an older backend; the native server gate is authoritative.

## Execution inspection

```text
Scope occurrence sc-7 / phase AwaitingIntervention / root definition v-42 / cause ref c-1

Forward occurrence ID / Step ID*     Forward code   Recovery code   Attempt count
occ-1 / step-1                       Applied        Pending         1
occ-2 / step-2                       Applied        Failed          2
[Open occurrence] [Open attempt history] [Recovery actions, if authorized]
```

Exact root definition/version provenance is part of the recovery summary. Show an authored `StepId` only where E2's safe-field policy permits; otherwise use the occurrence ID and fixed codes. User-authored labels/layout require separately authorized and reviewed definition access.

The E2-safe server recovery projection, not diagram color/latest execution per node, supplies obligation state and stable forward-to-handler links. The current viewer bootstrap fetches generic full WorkflowInstance state and a definition, while node selection chooses `LastOrDefault` then fetches a generic activity execution; neither is a guarded recovery read path. The recovery viewer must use the separate safe summary route and must not depend on a generic full-instance GET or an empty-state workaround. Navigate scope activation → each distinct forward occurrence → direction-tagged attempts → exact execution; link a forward execution to the recovery attempt that responds to it, including repeated StepIds. Definition labels/layout require the definition resource's own authorization; if unavailable, show the accessible safe occurrence table rather than assuming summary access includes definition access. An exact execution ID may link to a separately authorized protected-detail projection. Follow the [pinned E2 reviewed recovery-data proposal](https://github.com/elsa-workflows/elsa-core/blob/60aa5933f08ff14ba0332d05e2acb13d53003ca4/core/docs/specs/native-compensation/recovery-data.md) for canonical disclosure and permission rules. Display original failure separately from recovery errors; distinguish absent/null/present value state, data availability and business outcome. Never equate queued/started work with Compensated or treat unavailable viewer fields as business Unknown.

The projection has separate dimensions: `scopePhase` (Forward/Recovering/AwaitingIntervention/etc.), `forwardOutcome` (Pending/Running/Applied/NoEffect/Failed/Uncertain), `obligationState` (Eligible/NoHandler/Confirmed/Compensating/Compensated/Unresolved), `attemptOutcome` (NotRun/Pending/Running/Succeeded/Failed/Uncertain), `captureValueState` (Absent/Null/Present), and `dataAvailability` (Available/NotLoaded/Redacted/Unavailable/MissingVersion/UnknownSchema). These are proposed wire concepts, not new global runtime enums. Compose text/icons from them, for example “Forward applied; recovery failed; intervention required”; distinguish forward failure from undo failure and data unavailable from an uncertain external effect. Paged history uses a bounded server cursor; “more not loaded” is not “no more attempts”. Finished-scope inspection works from the retained journal even if its runtime child context or ordinary logs were pruned.

## Recovery action interaction

An action dialog identifies instance, exact scope/occurrence/attempt, current state/revision, consequences and a required reason. The server returns allowed actions based on capability, permission and state; it independently checks all authority on submission. Proposed commands and audit rules are in the [recovery API contract](../../../../core/docs/specs/native-compensation/recovery-api.md). Use backend API clients through the existing provider, not a generic anonymous bookmark link or a browser-owned mutation of workflow state.

A stale revision produces an explicit conflict and refetch; it must not silently retry against a newly selected occurrence. Retrying the same submitted action retains CommandId. Pending action state, reconnect and asynchronous completion are visible. Unknown schema/version/capability or missing protection key disables mutation and offers diagnostic guidance without leaking payloads. Manual force-success is absent; any future resolution/abandonment requires its own policy/evidence.

Accepted O2 adds an explicit Cancel and compensate journey at the planned cancellation/operator milestones. Distinguish request accepted, recovery in progress, uncertain/needs intervention, and completed cancellation using text/icons; request acceptance is not Cancelled. Preserve the cancellation reason separately from handler failure. Repeated submission retains command identity and joins existing progress. Confirmed effects stay in place; a deadline never silently abandons remaining obligations. Offer the action only with the required cancellation/recovery authority; ordinary cancel permission is insufficient. Unqualified backends must not expose it as working native cancellation. Host shutdown/reconnect resumes committed state without creating cancellation intent. This policy acceptance does not ship components or advance M1 readiness.

## Accessibility, capabilities and environments

Use semantic tables/lists and text/icons, never color alone. Accessible row/control names identify label, occurrence and action: “Open compensation for Reserve inventory, occurrence 2”. Arrow keys navigate rows; reordering uses named Move up/Move down controls and announces the new position; Tab traverses forward/handler/capture controls; Enter opens; Delete confirms. Restore focus after dialogs/navigation; announce validation and material status changes without flooding live regions. Cover narrow screens, long labels and large histories.

Probe optional recovery capability/version and supported profile/composition matrix. Unknown or unavailable capability cannot enable actions. Distinguish loading, empty, unauthorized, disconnected, stale and unsupported states. On backend/tenant/environment changes, cancel in-flight requests, dispose subscriptions, clear selected occurrence/actions/cached protected details and refetch capabilities; cache keys include backend and trusted tenant identity. A response for the old environment cannot populate the new view. Supported Server and WebAssembly hosts must both use the same authorized contract.

## Verification responsibilities

Reuse existing client/component tests at the lowest useful level and add paired browser coverage where the infrastructure supports it. V1/V4/V5a–c/V7 in the [qualification plan](../../../../core/docs/specs/native-compensation/verification.md) define the actual integrated journey, permission/disclosure negatives, action races and accessibility states. The restart journey must abruptly force-stop the backend (`SIGKILL` or equivalent), positively prove the old process exited, preserve the same database and persistent protection keys, start a new process, and reconnect the real Studio client; graceful flush is not proof. Wireframes are review artifacts; no browser or backend capability is demonstrated by this document. Studio plus backend review is required before a first production leaf is Ready.
