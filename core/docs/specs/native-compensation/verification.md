# Qualification plan and design validation

This is a plan, not a test report. No implementation, .NET/browser run or restart proof is delivered by #8896. Candidate provider/host support remains unproved. The design can pass source/scenario/document review while production readiness remains blocked by E1–E3. O1–O3 product policy is accepted, with its runtime behavior still to be proved.

## Common real-journey fixture

Use a real supported Studio host/browser and the candidate local Elsa runtime against a persistent database. A separate participant owns a separate durable ledger, with keyed Reserve, Undo and Lookup operations. Its ledger records unique effect counts, receipts, delayed-request refusal and operation closure. No transaction or in-memory fixture is shared with Elsa's state. Use deterministic injection barriers at actual pre/post commit/effect boundaries, never sleeps as correctness synchronization.

Record exact source head, host/provider/commit configuration, workflow and handler versions, tenant, scope/occurrence/operation/attempt IDs, process IDs and kill points, persisted Elsa revisions, participant receipts, UI/API state and sanitized accessibility evidence. Restart a new backend process against the same database and persisted protection keys, then reconnect Studio. A same-process reload or mocked client does not satisfy the gate.

## Guarded-snapshot E1 proof detail

The [guard contract](guarded-snapshot.md) narrows the storage checks required before M1. Extend the actual-provider test fixture, not a standalone fake, with:

| Guard case | Required observation |
|---|---|
| Stale row revision and owner epoch | Two contexts read one row. After the winning guarded commit or owner handoff, a stale revision and a stale epoch each affect zero rows or map to conflict. No effect or correctness-dependent side-store write follows either conflict. |
| Pending-intent preimage across owner claim | Bind the durable transition ID/hash to the exact canonical protected preimage, including snapshot/codec, lifecycle fields and participating work/bookmark/variable/callback state. Positive case: owner claim changes only ownership metadata and current row revision; prove the protected preimage is identical, then rebind the same intent. Negative case: interrupt/status or any protected state changes; the old intent cannot be rebound. Resolve/refuse before interrupt, and after proven noncommit any new intent must start from freshly admitted state while preserving business keys and obligations. |
| Local ownership restart | Kill old backend and verify positive supervisor evidence that it stopped before a new process claims a higher epoch. Reuse of the old receipt fails. A timeout/heartbeat-only takeover remains blocked. Claim/interrupt sequencing cannot overwrite an unresolved prepared intent. |
| Lost local commit acknowledgement | Inject loss before commit and after commit. Reconcile using canonical transition ID, exact hash and revision; only an exact committed receipt permits dependent participant call. Stable participant keys alone do not acknowledge a database commit. |
| Outer/inner restore admission | Cover invalid outer JSON, compression mismatch/unknown codec, unknown inner schema, missing definition/activity pins, queued-work node and callback owner/child. Each blocks before loader fallback, extractor omission, Save, runner or effect; verify original Data and codec preservation. |
| Core write bypasses | Try Save, Update, SaveMany, timestamp update, TryMarkInterrupted, delete, bulk delete, runtime cancel, instance import, alteration retry and interruption recovery against a marked unresolved row. Each follows a defined receipt-checked transition or refuses. Then run an old-interface provider and normal writes on an unmarked legacy row to confirm compatibility. |
| Tenant authority | Tenant B cannot load a usable receipt or mutate tenant A by known ID. Test exact tenant, default null/empty compatibility, asterisk-visible but mutation-blocked row, and request execution with disabled/unknown tenant filtering. |
| Transaction boundary | With candidate SQLite and actual contexts, force final instance CAS to conflict after required bookmark/variable/work writes are staged. Verify all correctness-dependent records roll back together or prove the selected durable repair protocol completes before any effect. Exclude logs only if they are shown irrelevant to recovery. |

The test-only guard-disabled control should reproduce stale-write and null-resave risks. Do not add a production opt-out. The E1 report is Partial; these are acceptance requirements, not results.

For provider or mode support, repeat the material crash/security matrix for the advertised configuration. Do not infer every provider or Blazor host is qualified from one successful run. A failed demonstration keeps its milestone open and identifies the corrective work; issue closure and compilation are not proof.

## M0 design review walkthroughs

- Sequential: arm inventory, acknowledge/capture it, arm delivery, acknowledge/capture it, definite rejection, reserve delivery undo then inventory undo; each P0–P6 boundary has an explicit stored/participant state.
- No fault (M1, accepted O1–O3): scope Done retains obligations; minimal authored Confirm resolves the exact serial scope occurrence, records confirmation and permits root completion. Without Confirm, publication and pre-effect execution reject the invalid shape. For an already-armed altered/imported invalid instance, preserve a blocked wait and explain the lack of an M1 operator release path. Authored confirmation audits the workflow actor and trusted initiator provenance. Test all paths before M1 support.
- Outcome handoff (M1, accepted O3): settle recovery, durably retain the pinned selected handoff, kill before delivery, then restore. Observe Compensated continuation OR original-fault propagation, never both; preserve original-cause and recovery evidence and correct native fault counts.
- Unknown: lose delivery response; do not omit delivery because no Completed event exists. Same-key lookup/closed-key participant rule settles it, otherwise stop without reporting Compensated.
- Repeated/nested: two iterations of the same authored StepId retain distinct OperationKeys/captures. A completed inner scope's journal stays addressable from the parent even after its context is pruned; confirm/recover affects exact ownership.
- Safety: missing handler pin cannot use ordinary Published/Latest fallback; invalid profile cannot reach effect code; an operator request without correct tenant/permission/revision/reason cannot reserve work.

Review against PRD FR1–FR11, evidence links and the physical proof gates. Record reviewer findings at a specific document/line, fix coherent findings, and repeat on the final candidate. Runtime/persistence, Studio/accessibility, security and program acceptance are separate review lenses. Proposed product policies must remain marked Proposed after technical review until the owner accepts them.
