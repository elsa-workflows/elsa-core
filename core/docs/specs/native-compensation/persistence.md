# Proposed data and durable recovery protocol

The architecture choice is a versioned recovery journal in **root WorkflowState.Properties**, persisted with serialized native work in the workflow-instance snapshot. It is not private state owned only by a completed child context, and execution logs are not its source of truth. No separate compensation table is selected for M1. A separate retained store requires an ADR revision if measured size, lifecycle or atomicity evidence makes the instance snapshot unsuitable.

This selects the logical record boundary, not an already-proven physical durability/fencing guarantee. Current conditional commits, no-op default transactions and opt-in EF wrapper do not meet the whole contract by themselves. Evidence gate E1 is mandatory before M1 readiness.

## Identities and versioned shape

Illustrative names are internal design terms; public API names/DTOs remain reviewable. All IDs are opaque and server-generated except stable StepId/MappingId authored in the definition.

| Identity | Meaning / lifetime |
|---|---|
| WorkflowInstanceId + TenantId | Trusted owning instance and isolation boundary; tenant is resolved by server, not taken as command authority. |
| ScopeOccurrenceId | One scope activation; persists beyond its child execution-context cleanup. |
| StepId / MappingId | Stable definition identities; labels and row indexes are presentation only. Delete/recreate produces new IDs. |
| OccurrenceId | One forward operation occurrence, including one loop iteration; not regenerated on retry. |
| OperationKey / UndoKey | Separate stable participant idempotency keys for forward/undo; all attempts of that direction reuse their key. Both target the same logical operation. |
| AttemptId / execution ID | A distinct execution attempt linked to the occurrence; no assumption that retry preserves a runtime context ID. |
| JournalRevision / owner token | Expected serialized state revision plus current runtime ownership evidence; not a substitute for commit-time CAS/fencing. |
| ArmSequence / CompletionOrdinal | Preparation sequence versus first durable success-registration order; neither is a wall-clock timestamp. |

A root envelope, under one namespaced module-owned property key, carries schema version, root revision, pinned workflow definition/version and scope records. A scope record carries its owner/parent occurrence, phase, cause reference, cursor and ordered entries. Accepted O3 also retains the pinned post-recovery behavior and one selected outward handoff identity/intent with final settlement. Restore must recover the same native completion or original-fault path without losing it or dispatching both paths. Do not infer delivery from prunable logs. E1/E3 must establish the exact reservation/acknowledgement and native callback/fault bookkeeping protocol across the settlement-to-signal crash gap before M1 readiness. These are internal design terms, not a second event scheduler or frozen public API.

An entry carries StepId, OccurrenceId, operation/undo keys, status, completion ordinal if known, forward/handler node IDs, exact handler/activity versions, capture schema, protected immutable input/result/receipt material, attempt references and unresolved error/evidence references.

Accepted O2 uses a canonical cancellation record in this root journal: a stable cancellation-operation identity, owning instance/target scope occurrences, immutable initiating reason/actor provenance, phase and references to existing recovery cursors/attempts. Command receipts map request CommandIds to that one operation. An authorized compatible request with a different CommandId joins the active cancellation under the same revision/ownership fence; it does not allocate a second unwind or overwrite the initiating reason. Conflicting target/action payloads are rejected and additional requests are audited separately. Persist intent and accepted command receipt before resulting effects, preserve mappings across restart, and return the retained result for repeats after settlement rather than restarting recovery. Exact internal field/DTO names and proof remain E1/E2 work; this is no public API freeze.

Use a deliberate versioned JSON/property-bag codec, not an unregistered CLR object hidden in Properties. Encode the envelope with explicit primitive/maps/arrays and stable field names; decode supported serializer materializations through the codec. Current polymorphic fallback can restore an unaliased object as an ExpandoObject, so CLR type identity is not the schema. Preserve the original representation on an unknown schema; expose a blocked safe summary without replacing it with an empty journal. E1/V8 must prove exact encode/store/new-process/decode round trips, including protected payload bytes, keys, pins, callbacks and work identity.

Outer snapshot hydration is a separate fail-closed boundary from the inner journal codec. The current EF loader catches decompression/deserialization failures and can retain a default state before journal admission is possible. For a compensation-enabled instance, retain the original opaque snapshot plus trusted identification of its recovery obligations, block resume/effects and prevent saving an empty replacement on any outer decode failure. A persisted non-resumable failure marker may support safe inspection, but cannot discard the original bytes or obligations. E1 selects and proves compatible identification/interception before fallback; a valid outer snapshot with an unknown inner schema is a different negative case.

Before the first effect, identity allocation uses a server-minted seed and serial cursor persisted with scope activation. A versioned deterministic allocator derives opaque occurrence/direction keys from that durable scope seed and operation slot, not a label, node ID or ExecutionCount. On unknown preparation-commit outcome, reload the canonical instance: if the slot is Armed, reuse its keys; if absence is proved under effective ownership/fencing, prepare that same slot again. Never advance the cursor or mint another business key while intent/effect may exist. Unknown scope-activation acknowledgement cannot permit an effect; its seed must be recovered from committed state before preparing work. E1 proves the exact allocation/lookup protocol, including an absent and a committed-but-unacknowledged write.

Captured payloads may be protected inline envelopes in that same root snapshot, keeping the first design's truth in one record boundary. Do not place raw secrets or unrestricted external payloads in Properties: generic instance APIs can return it. Reuse existing host protection with durable key continuity, tenant/purpose separation and explicit authorized detail disclosure; E2 selects/verifies the exact provider mapping. Capture schema, protection/key reference and content identity survive restart. Request captures contain only resolved values available before invocation; result/receipt captures are a separate append available only after a known outcome commits. A lost response leaves the request, keys and pins available, but no invented reservationId/result. The participant lookup or deduplicated replay must recover a required result before handler binding; otherwise block. A retry cannot change the original business target or required recovery values.

## Native integration responsibilities

1. A focused native compensation scope owns its children through existing scheduling and completion callbacks; it claims only faults belonging to its current scope occurrence. Native work state must carry typed recovery identity through serialization and invocation. This is an additive proposed extension where the current state shape lacks it; arbitrary Tag, transient properties and expression variables are not the identity channel.
2. Effect-capable forward and handler execution must pass a mandatory preparation boundary **after required inputs are resolved and before user effect code**. Select the precise invocation seam during E1. Prefer one narrow extension to native invocation/scheduling, rather than duplicating the whole activity pipeline. Ordinary commit strategies cannot disable this boundary for a compensation-enabled effect.
3. Required recovery values are frozen under occurrence identity. Handler binding reads this retained protected capture, not `GetOutput(activityId)` or live workflow variables. Additional mutable expressions, if ever permitted, must be labelled as recovery-time values and cannot supply the operation key or mandatory recovery target. M1 accepts only captured/literal required handler inputs.
4. Complete callbacks update the root journal, completion ordinal/cursor and next serialized work as one accepted transition. Fault handling durably establishes recovery ownership before native incident policy can strand it; the existing FaultSignal middleware remains the sole owner of fault-count recovery. Persist the protected original cause before returning from a claimed fault: RecoverFromFault clears the live exception and incident, and the context snapshot does not serialize that Exception. E3 selects a safe persisted-cause/native-fault representation; arbitrary CLR exception reconstruction or type-specific catch compatibility is not inferred. The final handoff must retain a valid native owner/status and account for completion/cancellation clearing callbacks or withdrawing work. Prove both O3 paths and native incident/count effects after restart; return a changed observable fault contract to the owner.
5. Restore admission validates the journal codec/schema, exact pinned definition/activity nodes and every journal-owned work/callback owner/child reference **before** ordinary state extraction can omit unresolved references. Elsa 3's generic extractor can skip missing scheduled nodes/callbacks; recovery cannot accept that omission as settled work. Preserve original state and expose blocked recovery if a reference is missing; do not dispatch partial recovery. E1/E3 select the narrow restore-admission seam and prove it before M1.
6. Native runner/dispatcher/resumer executes the serialized work. A bounded recovery adapter may requeue journal-owned pending work through existing runtime interfaces after restart; it must deduplicate and validate journal revision/ownership. It is not a second scheduler or a global polling substitute for native execution ownership.

## Commit protocol and crash table

| Boundary | Required acknowledged durable contents | Effect / restart behavior |
|---|---|---|
| P0 preparation fails or commit outcome unknown | No trusted new committed revision | Do not invoke external body. Reload/reconcile commit outcome using the same operation/command identity before retrying preparation. |
| P1 before forward effect | Armed entry, frozen request/keys/pins and specific forward work/context identity | Only the successful acknowledged boundary permits effect execution. Restart reuses the same key. |
| P2 participant committed, local result absent | P1 intent remains authoritative; external receipt may be unknown | Retry/query only under participant contract. Otherwise Uncertain/await intervention. No new key and no inferred NoEffect. |
| P3 forward acknowledgement | Result capture/receipt + Applied + exactly one completion ordinal + next work/cursor | Duplicate callback does not re-register or advance twice. |
| P4 before undo effect | Compensating + concrete handler attempt/work identity and stable UndoKey | Same durable transition reserves the handler; restart resumes/replays it. |
| P5 undo committed, local acknowledgement absent | P4 remains authoritative | Reuse UndoKey; participant deduplicates, or reconciliation/intervention settles uncertainty. |
| P6 undo acknowledgement / next handler | Compensated receipt/attempt + next reservation/cursor, or final settlement + the one selected O3 outward handoff intent | Only a committed settlement advances; process death between handlers or before outward completion/fault loses no obligation/handoff and cannot select both paths. |

The boundary includes all stores whose state is necessary for correctness: workflow snapshot, required bookmark/queue/outbox participation, variable/capture state and any command/audit receipt. Do not make correctness depend on best-effort logs. If these records cannot commit together, specify durable intent plus a repairing resumption protocol and prove each gap before support is claimed; never describe two independent saves as atomic.

A transaction does not encompass the remote participant. Participant idempotency, closed-key behavior and explicit uncertainty remain necessary even with perfect local transactions.

## Candidate first profile and evidence gates

Candidate: one local Elsa 3 runtime host, EF SQLite workflow persistence, one serial scope/participant lane, no concurrent sibling work or background/distributed execution, and an independently persisted key-aware reference participant. SQLite is a **candidate developer proof configuration**, not an accepted supported profile. E1 must demonstrate actual transaction/store participation, durable acknowledgement, abrupt-kill resumption and stale-writer rejection. Do not infer these from an EF transaction option or host count. If the candidate cannot meet them, select a different provider/profile and update the decision before M1 readiness; no silent fallback to in-memory or weaker guarantees.

The first candidate needs effective exclusive instance ownership and commit-time stale-owner/revision checks. Existing execution guards/locks are useful inputs, not persisted write fences. A protected recovery mutation cannot succeed from a stale owner merely because it passed an earlier invocation check. If commit CAS/fencing needs a new native persistence seam, describe it as an additive runtime-owned change with focused tests; do not freeze its public API in this design task.

Only explicit operation-aware activities/participants qualify for the first journey. Arbitrary HTTP/custom activities are not automatically safe just because a handler is attached. Publication and execution inspect the declared effect/recovery capabilities and the accepted host profile. Unsupported configurations must reject before effects, even if global publication validation is disabled or JSON/API publication bypasses Studio.

## Pins, retention and upgrades

Pin root definition version ID, exact handler definition when external, activity type/contract version and capture schema. Preserve resolver provenance. Root pinning alone is insufficient: ordinary ExecuteWorkflow resolves Published, and WorkflowDefinitionActivity can fall back to Published/Latest. Recovery must resolve exact pins or enter a missing-version intervention state. It must never silently adopt a newer handler.

Keep unresolved/eligible entries, captures, participant evidence and required handler artifacts recoverable after child completion, normal log pruning and deployment restart. Guard deletion/import/alteration/retention paths from discarding these obligations or changing their pins/keys. Preserve original 3.x APIs for unaffected workflows; compensation-aware paths add explicit validation and protection. Schema upgrades are additive with defined readers/upcasters; an unknown schema is preserved and blocked, not deserialized as an empty journal. Final purge requires the accepted retention policy, no remaining obligation, and an audit record.
