# Proposed native Core and Studio caller contract (E3)

Status: Proposed design for [#8953](https://github.com/elsa-workflows/elsa-core/issues/8953), based on source commit [`7ca753ccc212cfcffe3e6cf3dd8e01090e9bcd6f`](https://github.com/elsa-workflows/elsa-core/commit/7ca753ccc212cfcffe3e6cf3dd8e01090e9bcd6f). This is an E3 design artifact, not implementation or runtime, security, browser, or persistence qualification. E1–E3 remain open and M1 remains Not Ready. O1–O3 remain accepted as recorded in [decisions](decisions.md).

This contract settles the bounded native Core/Studio caller shape for the first authored compensation scope. It keeps public DTO, endpoint, and permission names open until their real callers are implemented and reviewed. The Studio [interaction plan](../../../../studio/docs/specs/native-compensation/plan.md) remains canonical for user interaction; this document owns the source-grounded Core serialization/traversal, pinning, publish-diagnostic, and recovery-read caller contracts.

## Owned activity and stable authoring identities

The proposed native `CompensationScope` is an Elsa 3 `Activity`, registered with the existing Core workflow activity assembly. Its versioned serialized model owns an ordered collection of step rows. Each row has a stable opaque `StepId`, editable label, required forward child, optional handler child, and zero or more capture mappings. A separate stable `MappingId` belongs to every mapping. Concrete JSON property names and public DTO names remain implementation choices.

Each forward and handler is a real nested `IActivity` serialized inside its owning row. A hidden `[JsonIgnore][Browsable(false)]` `IEnumerable<IActivity>` projection exposes each actual child to Core graph construction in deterministic row/role order. It does not replace serialized ownership. Studio's Workflows.Core resolver traverses the JSON row collection and emits each child with its logical StepId and role; the custom Workflows designer edits the pair and delegates selected-child property editing to the standard descriptor-based editor. Graph links/ports continue to mean graph execution/data flow; they do not represent the compensation pairing.

Keep authored, execution, operation and navigation identities distinct:

- `StepId` and `MappingId` are authored logical identities. Reorder/rename preserves them; deleting and recreating a row or mapping creates new IDs.
- Each nested activity keeps its own Elsa `Activity.Id`. It locates an executable child, not the business operation or repeated occurrence.
- Studio graph `NodeId` identifies a rendered location and may vary by graph construction. It is a navigation hint, never a durable capture key.
- Runtime-generated opaque `ScopeOccurrenceId` identifies one scope activation. A distinct `OccurrenceId` identifies each forward step activation, including repeated invocations of the same StepId. `OperationKey` and `UndoKey` are separate participant idempotency keys for the forward and recovery directions, not navigation identities. Each `AttemptId` has an explicit direction and links to its exact concrete Elsa execution ID when one exists. Retries in a direction reuse that direction's participant key and create distinct attempts; repeated step activations never collapse into one occurrence.

At runtime, bind each exact child invocation to its scope activation, forward `OccurrenceId`, operation/direction key, attempt and execution. Associate each forward execution with the corresponding recovery attempt and execution as a causal link; a scope with repeated steps or several operations cannot be flattened to one row status. [StateMachine](https://github.com/elsa-workflows/elsa-core/blob/7ca753ccc212cfcffe3e6cf3dd8e01090e9bcd6f/core/src/modules/Elsa.Workflows.Core/Activities/StateMachine/Activities/StateMachine.cs#L227-L251) demonstrates the existing `ScheduleActivityAsync` plus completion-callback pattern; it does not supply recovery identity or durability. Do not use child Activity.Id, graph NodeId, or arbitrary `ScheduleWorkOptions.Tag` as the operation key. The carrier and persisted callback/attempt association must be proved across restore under E1/E3; a Runtime-private association is acceptable if proved and does not require a new public Core context field. O3 requires exercising both the distinct Compensated continuation and original-fault handoff without duplication.

The draft must preserve incomplete and unknown row/activity JSON across save/reopen, with editing limitations made visible. It must not silently drop an unknown child, infer a handler, substitute the current descriptor/version, or publish an empty scope. If the authoring serializer cannot preserve a protected draft's unknown material safely, reject its edit/publish path before overwriting it.

## Binding, capture and pinning

Bindings refer to descriptors on the selected child, never display labels or array positions. A source is a schema-approved capture field produced by the forward participant and a target is a declared recovery input on the paired handler. The mapping records the exact source and target child activity type/version, descriptor property name, and declared type, alongside child Activity.Id, StepId, and MappingId. These keys are proposals grounded in descriptors that expose names/types, not opaque property IDs. If future descriptor contracts add stable IDs, E3 may adopt them after checking cross-version meaning. A mapping is not a license to capture every ordinary activity output or bind from current workflow variables. A compatible handler literal may remain an authored value under the exact pinned definition and participant contract; this does not turn it into a captured result.

At the Armed boundary, freeze the schema-approved request capture for that exact forward occurrence. Append the approved result capture only when its qualified forward result is committed as Applied. A handler reads that immutable occurrence-bound capture, never current variables or latest output-by-node. O3's original cause remains the bounded persisted cause defined by accepted policy. E2 owns field classification, source suppression, protection, retention and disclosure; use the canonical [protected recovery-data contract at reviewed PR #8952 head `60aa5933f08ff14ba0332d05e2acb13d53003ca4`](https://github.com/elsa-workflows/elsa-core/blob/60aa5933f08ff14ba0332d05e2acb13d53003ca4/core/docs/specs/native-compensation/recovery-data.md) rather than restating its capture-security rules here.

The M1 executable participant/profile set stays empty until E1/E2 qualify an explicit allowlist entry for exact activity `TypeName@Version`, participant profile and capture schema. For each entry, E2 must prove suppression at the source before Core's first raw exception log, later incident/execution-log copies, and generic execution-record mapping; the exception middleware and mapper source evidence above identifies those copy boundaries. A child is not safe because it is nested, has an output descriptor, or reaches a parent fault callback. Unsupported types and profiles are rejected at publish/activation before effect. Coordinate with [generic redaction work #8778](https://github.com/elsa-workflows/elsa-core/issues/8778), without assuming it provides compensation origin tracking or adding a new origin framework here. The canonical [E2 contract](https://github.com/elsa-workflows/elsa-core/blob/60aa5933f08ff14ba0332d05e2acb13d53003ca4/core/docs/specs/native-compensation/recovery-data.md) owns the detailed protection and disclosure policy.

For the bounded M1 mapping subset, permit direct type-compatible assignments and compatible authored handler literals only. Core's current converter descriptor exposes a stable ID and settings schema but no converter version. Do not claim that current output conversion is a strictly pinned recovery transform; a converted mapping is rejected until a versioned converter identity/immutability contract and its execution path are reviewed. The declared schema, not the descriptor or C# property, defines whether a source/target is required, optional, nullable, defaulted or allowed to be omitted. Apply a default only when its exact semantics are declared by the schema and accepted by the participant; otherwise absence stays absent. Publication validates the declared participant, capture schema and mapping shape; it cannot validate future runtime values. At runtime, required missing or unavailable data blocks before the handler. Optional omission is allowed only when declared; explicit null is allowed only when both the schema declares the target nullable and the participant contract accepts null. `NotLoaded`, `Redacted`, `MissingVersion`, `UnknownSchema` and `Unavailable` are data-availability states, not null values or business outcomes. If a required/default/null rule cannot be established, the mapping is unsupported. Preserve any existing required-input validators.

Pin the root to its exact workflow definition version record and pin every inline handler activity by exact `(TypeName, Version)`. Pin the chosen O3 behavior with that root version as already stated in the accepted decision. No handler path may quietly resolve Latest/Published. `WorkflowDefinitionActivity` and workflow-as-activity are excluded from M1 handler trees because their current initialization includes Published/Latest fallback after materialization; revisit this reusable-handler case at M3, or earlier if a concrete caller requires it and both strict definition selection and restore are demonstrated.

The strict check has two stages and neither can be skipped:

1. In `ActivityJsonConverter.Read`, before `GetActivityDetails` can select Latest, recognize the raw compensation-scope type and inspect its owned forward/handler subtrees and exact `type`/`version` tokens. `ActivityConstructorContext` cannot enforce this because it does not expose the parsed JSON. If the full protected scope cannot be resolved safely, preserve the entire original scope as `NotFoundActivity.OriginalActivityJson` for a read-only draft; do not materialize it by fallback. Prove the branch on the current Save + Publish request and ensure diagnostics are returned before effects. The normal fallback for non-compensation activities remains unchanged.
2. Prove the same raw-scope admission on stored workflow JSON before protected activation/reopen/recovery materialization and graph building. The exact management boundary and whether it invokes the same converter must be verified in implementation. Then use normal `WorkflowDefinitionValidating` for declared schema, mapping and profile rules, and the existing execution-guard location for protected invocation admission. This is a narrow compensation path, not a global serializer or resolver framework.

Any pin/check failure is a typed, visible admission/validation refusal before side effects. Preserve the original opaque draft/version/journal evidence. Missing or tampered capture data is a typed `unavailable`/blocked recovery-data reason; preserve opaque obligation and any known outcome metadata. It does not by itself manufacture business uncertainty or change a known forward/recovery outcome. Actual participant effect uncertainty retains its own semantics under [semantics](semantics.md) and [persistence](persistence.md).

## Publish diagnostics through the real Studio path

The authoring tracer must exercise `WorkflowEditor.SaveChangesAsync` → `WorkflowDefinitionEditorService.SaveAsync(..., publish: true)` → the existing POST workflow-definition endpoint → `WorkflowDefinitionPublisher.PublishAsync` → `WorkflowValidator` and its notification handlers. It must also exercise the stored-definition Publish endpoint through the same mandatory compensation gate. Since the publisher currently materializes before validation, raw-token admission belongs earlier as described above; semantic checks may use workflow validation only after safe materialization. A mandatory compensation refusal must not depend on `ManagementOptions.FailOnValidationErrors`: that option currently permits the publisher to continue and mutate publication state despite validation errors. Place the proposed gate before `WorkflowDefinitionPublishing`, retractions, published/latest flag changes and saves. The current notification is not a refusal channel. Prove a typed refusal/diagnostic mapping through both publish callers and verify that a rejected request leaves definition rows/flags unchanged. The tested participant must be named in the qualified allowlist; a generic script or HTTP activity is not a substitute.

The proposed additive error contract preserves the old top-level messages and carries a feature-owned diagnostic code/data payload that can identify each diagnostic's stable scope/activity/StepId/role/MappingId target and related IDs. Studio resolves the payload against the current authored graph by IDs, focuses the correct control, and announces the message accessibly. Do not correlate error arrays to step arrays by position. On a server without the recognized payload or capability, show the server message in the normal accessible summary and preserve the draft; do not guess a target or claim the profile is publishable. Exact route, version, payload and DTO spelling await implementation caller review.

The publication rules for M1 include duplicate/missing authored IDs, absent forward children, unqualified effects/handlers, missing or changed exact pins, unsupported nested workflow handler, incompatible or converted capture binding, undeclared required/nullable/default semantics, unsupported profile/composition, and the accepted minimal exact-scope Confirm requirement on the no-fault path. Publication validates schema and mapping declarations, not values that will only exist at runtime. A required capture that is absent/unavailable when the forward occurrence commits blocks the handler before effect. These restrictions are checked by a compensation-owned gate even when global validation errors are configured not to fail publication; Studio validation alone never authorizes an effect. Save-as-draft must round-trip an incomplete/unknown draft without turning it into a published empty scope.

## Safe recovery inspection caller

Studio must navigate the E2 recovery projection, not infer recovery from diagram color, latest node execution, generic workflow-state JSON, generic incident/log text, or ordinary execution outputs. E2's [reviewed protected-data proposal in PR #8952](https://github.com/elsa-workflows/elsa-core/pull/8952) (reviewed proposal head `60aa5933f08ff14ba0332d05e2acb13d53003ca4`) is a linked design dependency, not implementation proof. Keep its safe-field and authorization rules canonical there rather than duplicating them here.

The caller must support a real, paged causal path:

1. An authorized instance summary leads to each server-generated opaque `ScopeOccurrenceId`, pinned root definition/version provenance, fixed reason/status/capability codes, bounded counts and opaque cause references. Preserve forward and recovery outcomes separately. Do not include arbitrary definition labels, capture values or free-form exceptions in the safe summary.
2. Selecting one scope occurrence lists each distinct server-generated opaque forward `OccurrenceId` (including repeated activations of one StepId), its safe fixed status/reason codes, and only those authored IDs/provenance fields allowed by E2. Selecting a forward occurrence lists attempts with opaque `AttemptId` plus explicit direction, fixed status/reason codes and bounded order metadata. Each attempt may reference its exact concrete Elsa execution ID; absence of an execution is explicit. Recovery attempts must remain causally linked to their forward occurrence and, when available, to the exact forward execution they recover. Paged history uses a bounded server cursor; not-yet-loaded history differs from no history. `OperationKey` and `UndoKey` remain participant idempotency keys, not navigation handles.
3. Selecting an exact execution ID requests its authorized protected-detail projection; it never asks for the latest execution of a diagram node. Capture value state (absent, explicit null, or present) stays separate from data availability (for example not loaded, redacted, unavailable, missing version or unknown schema), and both stay separate from business outcomes. A viewer's unavailable field is not business `Unknown`. E2's [canonical contract](https://github.com/elsa-workflows/elsa-core/blob/60aa5933f08ff14ba0332d05e2acb13d53003ca4/core/docs/specs/native-compensation/recovery-data.md) governs protected fields and detail authorization; no protected detail grants generic Secrets/credential access.

The current `WorkflowInstanceViewer` bootstrap must be replaced or bypassed for guarded compensation instances: its first request is the generic full instance GET, followed by an exact-definition GET. Do not retrofit security by clearing workflow state in Studio. The recovery-summary caller is independent from the generic full instance response. If a caller elects to add the diagram, it must authorize the exact pinned definition with its normal definition permission and independently review labels/layout as a disclosure surface; otherwise use the safe occurrence table. Never assume instance summary permission grants workflow definition access or permission to show authored labels.

Use E2's canonical per-resource baseline, separate protected-detail grant/pattern and trusted-tenant rules for every request. An instance summary still requires instance-level authority; activity-execution authority alone is not instance authority. A Studio-side filter is never authorization, and the instance caller must not confer definition-resource access. Do not restate or alter E2's matcher and disclosure policy here.

Use the E2 host identity contract for validated issuer/user claims and trusted exact tenant binding. The separate [tenant database selection work #8181](https://github.com/elsa-workflows/elsa-core/issues/8181) concerns database selection, not proof that the authenticated principal is bound to that tenant. Follow the canonical E2 policy rather than treating a selected database or caller-supplied tenant hint as identity proof.

Use `IBackendApiClientProvider`, probe the optional server capability/version before requesting recovery pages, and distinguish loading, empty, unavailable, unsupported, unauthorized, disconnected, stale, and error states. Server and WebAssembly use the same authorized contract. On backend, tenant, or environment changes, cancel in-flight requests, dispose subscriptions, clear occurrence/attempt/execution selection and protected caches, then reload capability state; late responses from the old context cannot repopulate the view. No recovery mutation controls are designed here: M4 owns operator mutation UI.

## First implementation tracer and proof handoff

Split the tracer into two gates. First, immediately prove visual authoring, draft save/close/reopen, row reorder/rename preserving StepId/MappingId, child-role resolution, incomplete/unknown draft preservation, and safe invalid-publish diagnostics through Save + Publish and stored Publish. Do not claim a positive publish while the real participant/profile allowlist is empty. Later, after an exact participant/profile and capture schema pass E1/E2 source suppression and storage qualification, exercise a successful publish and the authorized scope → forward occurrence → direction/attempt → exact execution caller. Include repeated activations of one StepId and causal links from forward execution to its recovery attempt; verify this never collapses to latest-node navigation.

The later tracer is still not the M1 end-to-end proof. E1 must qualify the actual persistent commit/store profile and new-process restore, E2 the real host protection/key/security/source-suppression/read gates, and E3 a real Studio host plus trusted tenant and controlled participant. The restart proof must force-stop the backend (`SIGKILL` or equivalent abrupt termination), positively verify the old process stopped, retain the same database and persistent protection keys, start a new process, and reconnect through Studio. Graceful shutdown/flush and same-process reload are not restart proof. The integrated [V1/V1b, V4, V5a and V7 scenarios](verification.md#scenarios-and-negative-controls) retain their full requirements; a serializer/resolver/component test, mock API or successful publish is not a substitute. No E1–E3 gate or milestone is marked passed here.
