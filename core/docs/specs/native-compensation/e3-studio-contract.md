# Proposed native Core and Studio caller contract (E3)

Status: Proposed design for [#8953](https://github.com/elsa-workflows/elsa-core/issues/8953), based on source commit [`7ca753ccc212cfcffe3e6cf3dd8e01090e9bcd6f`](https://github.com/elsa-workflows/elsa-core/commit/7ca753ccc212cfcffe3e6cf3dd8e01090e9bcd6f). This is an E3 design artifact, not implementation or runtime, security, browser, or persistence qualification. E1–E3 remain open and M1 remains Not Ready. O1–O3 remain accepted as recorded in [decisions](decisions.md).

This contract settles the bounded native Core/Studio caller shape for the first authored compensation scope. It keeps public DTO, endpoint, and permission names open until their real callers are implemented and reviewed. The Studio [interaction plan](../../../../studio/docs/specs/native-compensation/plan.md) remains canonical for user interaction; this document owns the source-grounded Core serialization/traversal, pinning, publish-diagnostic, and recovery-read caller contracts.

## Owned activity and stable authoring identities

The proposed native `CompensationScope` is an Elsa 3 `Activity`, registered with the existing Core workflow activity assembly. Its versioned serialized model owns an ordered collection of step rows. Each row has a stable opaque `StepId`, editable label, required forward child, optional handler child, and zero or more capture mappings. A separate stable `MappingId` belongs to every mapping. Concrete JSON property names and public DTO names remain implementation choices.

Each forward and handler is a real nested `IActivity` serialized inside its owning row. A hidden `[JsonIgnore][Browsable(false)]` `IEnumerable<IActivity>` projection exposes each actual child to Core graph construction in deterministic row/role order. It does not replace serialized ownership. Studio's Workflows.Core resolver traverses the JSON row collection and emits each child with its logical StepId and role; the custom Workflows designer edits the pair and delegates selected-child property editing to the standard descriptor-based editor. Graph links/ports continue to mean graph execution/data flow; they do not represent the compensation pairing.

Maintain four distinct identity layers:

- `StepId` and `MappingId` are authored logical identities. Reorder/rename preserves them; deleting and recreating a row or mapping creates new IDs.
- Each nested activity keeps its own Elsa `Activity.Id`. It locates an executable child, not the business operation or repeated occurrence.
- Studio graph `NodeId` identifies a rendered location and may vary by graph construction. It is a navigation hint, never a durable capture key.
- Runtime-generated opaque `ScopeOccurrenceId`, `OperationKey`, `AttemptId`, and concrete execution ID identify one run, one logical effect, one attempt, and one Elsa execution. Repeated invocations of one StepId create separate occurrences/operations; retries keep the logical key while adding attempts under the participant contract.

At runtime, bind each exact child invocation to the occurrence/operation/attempt tuple and associate its native completion or fault callback with that same tuple. [StateMachine](https://github.com/elsa-workflows/elsa-core/blob/7ca753ccc212cfcffe3e6cf3dd8e01090e9bcd6f/core/src/modules/Elsa.Workflows.Core/Activities/StateMachine/Activities/StateMachine.cs#L227-L251) demonstrates the existing `ScheduleActivityAsync` plus completion-callback pattern; it does not supply recovery identity or durability. Do not use child Activity.Id, graph NodeId, or arbitrary `ScheduleWorkOptions.Tag` as the operation key. The carrier and persisted callback/attempt association must be proved across restore under E1/E3; a Runtime-private association is acceptable if proved and does not require a new public Core context field. O3 requires exercising both the distinct Compensated continuation and original-fault handoff without duplication.

The draft must preserve incomplete and unknown row/activity JSON across save/reopen, with editing limitations made visible. It must not silently drop an unknown child, infer a handler, substitute the current descriptor/version, or publish an empty scope. If the authoring serializer cannot preserve a protected draft's unknown material safely, reject its edit/publish path before overwriting it.

## Binding, capture and pinning

Bindings refer to descriptors on the selected child, never display labels or array positions. A source is a schema-approved capture field produced by the forward participant and a target is a declared recovery input on the paired handler. The mapping records the exact source and target child activity type/version, descriptor property name, and declared type, alongside child Activity.Id, StepId, and MappingId. These keys are proposals grounded in descriptors that expose names/types, not opaque property IDs. If future descriptor contracts add stable IDs, E3 may adopt them after checking cross-version meaning. A mapping is not a license to capture every ordinary activity output or bind from current workflow variables.

Before the forward effect, snapshot only policy-approved resolved request inputs needed for later recovery. On a qualified forward commit, bind only schema-approved capture fields to that exact occurrence and mapping. A handler reads only those immutable occurrence-bound captures, never current workflow variables or latest output-by-node. O3's retained original cause is a bounded policy-approved cause record/reference, not the raw CLR exception graph or an incident/log copy. Capture schema/purpose and protected storage belong to E2; this document does not duplicate its cryptographic or key-retention design. Payloads are limited to approved recovery captures: they are not arbitrary CLR exception graphs, authorization headers/tokens, resolved-secret snapshots, or a general export of activity inputs/outputs. Reuse existing Secrets protection and sensitivity rules without assuming they provide a reusable unchanged recovery envelope. The Studio authoring UI may show safe descriptor/type metadata, but capture values and protected detail need the E2-reviewed view grant and projection; they must not become generic Secrets authority.

The M1 supported profile must be an explicit, default-deny allowlist of exact forward/handler activity type versions and participant profile/capture fields whose source boundary is proven to suppress protected outputs and exceptions before any generic execution-record, incident, or log copy. An allowlist entry names the exact activity `TypeName@Version`, participant/profile capability, permitted capture schema fields and the tested suppression boundary. The proposed initial allowlist is empty until E1/E2 qualify its real participant and host profile; this design names no Elsa activity as already approved. A generic native activity, HTTP call, script, or custom activity is not safe merely because it is nested in a compensation scope or has an output descriptor. If a type/profile cannot prove suppression at the actual source path before those copies, reject publication/activation before effect. E2 owns that proof with the real participant and host profile; coordinate the separate [generic redaction work #8778](https://github.com/elsa-workflows/elsa-core/issues/8778) rather than assuming it supplies compensation origin tracking. Do not invent a generic sensitive-origin framework or mark an unqualified activity as safe here.

For the bounded M1 mapping subset, permit direct type-compatible assignments only. Core's current converter descriptor exposes a stable ID and settings schema but no converter version. Do not claim that current output conversion is a strictly pinned recovery transform; a converted mapping is rejected until a versioned converter identity/immutability contract and its execution path are reviewed. Missing or incompatible source/target descriptors, unknown child type/version, unknown capture schema, redacted required input, or unsupported participant/mapping blocks before effect.

Pin the root to its exact workflow definition version record and pin every inline handler activity by exact `(TypeName, Version)`. Pin the chosen O3 behavior with that root version as already stated in the accepted decision. No handler path may quietly resolve Latest/Published. `WorkflowDefinitionActivity` and workflow-as-activity are excluded from M1 handler trees because their current initialization includes Published/Latest fallback after materialization; revisit this reusable-handler case at M3, or earlier if a concrete caller requires it and both strict definition selection and restore are demonstrated.

The strict check has two stages and neither can be skipped:

1. On the existing save/publish request, inspect the original root JSON—including nested child `type` and `version` tokens—before `ActivityJsonConverter` can apply its latest-version fallback. Today the endpoint request model exposes `Root` as an `IActivity`; the current caller therefore needs a compensation-only raw-token admission seam before that binding/conversion boundary. Preserve the ordinary 3.x path unchanged. The exact endpoint/model-binding implementation must be reviewed by Core/Management owners before code; the existing post-materialization validation notification cannot prove the original pins survived.
2. Before stored workflow JSON is materialized for protected use, recheck the stored raw `StringData` at the narrow `WorkflowDefinitionService.MaterializeWorkflowAsync`/equivalent management boundary, before `JsonWorkflowMaterializer` and graph building. This protects activation/reopen/recovery from changed or unavailable registrations. Then use normal `WorkflowDefinitionValidating` for structural binding and profile rules, and the existing execution-guard location for protected invocation admission. None is a reason to change global converter fallback semantics.

Any pin/check failure is a typed, visible admission/validation refusal before side effects. Preserve the original opaque draft/version/journal evidence. Missing or tampered capture data is `unavailable`/blocked recovery data; it does not by itself manufacture business uncertainty or change a known forward/recovery outcome. Actual participant effect uncertainty retains its own semantics under [semantics](semantics.md) and [persistence](persistence.md).

## Publish diagnostics through the real Studio path

The first authoring tracer must exercise `WorkflowEditor.SaveChangesAsync` → `WorkflowDefinitionEditorService.SaveAsync(..., publish: true)` → the existing POST workflow-definition endpoint → `WorkflowDefinitionPublisher.PublishAsync` → `WorkflowValidator` and its notification handlers. The publisher currently materializes before validation, so raw-token admission belongs earlier as described above; semantic checks can be added through the validation notification after exact materialization. The sample forward/handler types must be named in the implementation's tested allowlist; a generic script or HTTP activity is not a substitute for a qualified source-suppressed participant.

The proposed additive error contract preserves the old top-level messages and carries a feature-owned diagnostic code/data payload that can identify each diagnostic's stable scope/activity/StepId/role/MappingId target and related IDs. Studio resolves the payload against the current authored graph by IDs, focuses the correct control, and announces the message accessibly. Do not correlate error arrays to step arrays by position. On a server without the recognized payload or capability, show the server message in the normal accessible summary and preserve the draft; do not guess a target or claim the profile is publishable. Exact route, version, payload and DTO spelling await implementation caller review.

The publication rules for M1 include duplicate/missing authored IDs, absent forward children, unqualified effects/handlers, missing or changed exact pins, unsupported nested workflow handler, incompatible or converted capture binding, missing required capture, unsupported profile/composition, and the accepted minimal exact-scope Confirm requirement on the no-fault path. These restrictions are repeated by the server before protected execution; Studio validation alone never authorizes an effect. Save-as-draft must round-trip an incomplete/unknown draft without turning it into a published empty scope.

## Safe recovery inspection caller

Studio must navigate the E2 recovery projection, not infer recovery from diagram color, latest node execution, generic workflow-state JSON, generic incident/log text, or ordinary execution outputs. E2's [reviewed protected-data proposal in PR #8952](https://github.com/elsa-workflows/elsa-core/pull/8952) (reviewed proposal head `60aa5933f08ff14ba0332d05e2acb13d53003ca4`) is a linked design dependency, not implementation proof. Keep its safe-field and authorization rules canonical there rather than duplicating them here.

The caller must support a real, paged causal path:

1. An authorized instance recovery summary lists bounded scope occurrences with server-generated opaque occurrence IDs; exact root definition/version provenance; an opaque StepId only where the E2 safe-field policy permits it; fixed reason/status/capability codes; bounded counts; and opaque cause references. It preserves separate forward and recovery outcomes. It does not include user-authored definition labels, capture values or arbitrary exception text.
2. Selecting one occurrence lists its attempts by opaque AttemptId, with recovery role and fixed status/reason codes plus bounded order metadata. Each attempt can reference the exact concrete Elsa execution ID when one exists; absence of a concrete execution is explicit. Paged history uses a bounded server cursor, and not-yet-loaded history is distinct from no history.
3. Selecting an exact execution ID requests its authorized protected-detail projection; it never asks for the latest execution of a diagram node. The UI keeps capture/data availability separate from business outcome, e.g. available, redacted, unavailable, unknown schema, while forward and recovery status remain their own dimensions. Protected detail never expands into generic secret or credential read access.

The current `WorkflowInstanceViewer` bootstrap must be replaced or bypassed for guarded compensation instances: its first request is the generic full instance GET, followed by an exact-definition GET. Do not retrofit security by clearing workflow state in Studio. The recovery-summary caller is independent from the generic full instance response. If a caller elects to add the diagram, it must authorize the exact pinned definition with its normal definition permission and independently review labels/layout as a disclosure surface; otherwise use the safe occurrence table. Never assume instance summary permission grants workflow definition access or permission to show authored labels.

Authorization follows E2's per-resource baselines: instance `view` authority is required for that instance's recovery summary; activity-execution `view` alone is not instance authority. Protected detail additionally requires the reviewed distinct protected-view verb/pattern grant **and** its own baseline resource authorization plus the exact trusted-tenant check. Role-name-only access grants neither summary nor detail. Broad generic `view` and Secrets read are not protected-detail grants. Link the E2 proposal for the reviewed exact matcher semantics; do not substitute a Studio-only filter.

Use the E2 host identity contract for validated issuer/user claims and trusted exact tenant binding. The separate [tenant database selection work #8181](https://github.com/elsa-workflows/elsa-core/issues/8181) is not proof that the authenticated principal is bound to that tenant. A selected database, header alone, API key or role name alone must not populate the protected recovery caller's trusted principal/tenant context.

Use `IBackendApiClientProvider`, probe the optional server capability/version before requesting recovery pages, and distinguish loading, empty, unavailable, unsupported, unauthorized, disconnected, stale, and error states. Server and WebAssembly use the same authorized contract. On backend, tenant, or environment changes, cancel in-flight requests, dispose subscriptions, clear occurrence/attempt/execution selection and protected caches, then reload capability state; late responses from the old context cannot repopulate the view. No recovery mutation controls are designed here: M4 owns operator mutation UI.

## First implementation tracer and proof handoff

The smallest useful authoring tracer is one real registered native scope with one forward child, one inline handler child, one direct compatible mapping, stable StepId/MappingId, and a minimal explicit Confirm on a no-fault path. In the supported Studio host, author it visually, save as draft, close/reopen, rename/reorder without changing logical IDs, and verify both children and mapping still resolve to the correct controls. Then run one valid and one invalid publish through the actual Save + Publish path: valid pins succeed validation; a missing/unavailable child version and an invalid mapping are refused by the server before fallback/effects, and their structured diagnostics focus the stable target. Preserve an incomplete unknown draft without silently deleting the child. Exercise the authorized summary → occurrence → attempt → exact execution navigation using the E2 caller once available; verify old/latest-node navigation is not used as recovery identity.

That tracer verifies authoring and API mapping only. It is not the M1 end-to-end proof. E1 must qualify the actual persistent commit/store profile and new-process restore, E2 the real host protection/key/security/redaction/read gates, and E3 a real Studio host plus trusted tenant and controlled participant across process termination. The integrated [V1/V1b, V4, V5a and V7 scenarios](verification.md#scenarios-and-negative-controls) retain their full requirements; a serializer/resolver/component test, mock API, same-process reload or successful publish is not a substitute. No E1–E3 gate or milestone is marked passed here.
