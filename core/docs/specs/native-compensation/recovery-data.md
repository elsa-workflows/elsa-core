# Protected recovery data and tenant authority

- Status: Proposed E2 design for review; no runtime, endpoint, protection, browser, or restart proof has run.
- Date: 2026-10-21
- Owners: Security + Core/Studio for projection, authorization, and source suppression; Hosting + Security for key configuration and restore; Product + Hosting + Security for retention and erasure policy.
- Related: [native-compensation packet](README.md), [recovery API proposal](recovery-api.md), [guarded snapshot contract](guarded-snapshot.md), [root-journal ADR](../../../../docs/adr/2026-10-20-native-compensation-instance-journal.md), [guarded-snapshot ADR](../../../../docs/adr/2026-10-21-native-compensation-guarded-snapshots.md), [this contract's ADR](../../../../docs/adr/2026-10-21-protect-native-compensation-recovery-data.md), [task #8948](https://github.com/elsa-workflows/elsa-core/issues/8948).

## Contract

For a compensation-enabled instance, retain immutable, schema-declared, policy-approved values needed for recovery in the root journal. “Exact capture” means the exact approved fields and values, not an arbitrary request/result object graph or exception object. A cause is a bounded, sanitized recovery record selected under the existing sensitivity policy; it is not an arbitrary CLR exception graph, raw message/stack by default, authentication header/token, or resolved secret snapshot. Where a participant needs a credential, prefer runtime resolution through an existing server-side Secrets reference and its existing authorization. Do not expose that reference or credential material through recovery detail, and do not grant Secrets read authority through the recovery permission. If a participant or mapping cannot meet this boundary, reject protected activation before the effect.

Only an explicit allowlisted summary may flow through ordinary inspection. It must retain independent forward-operation and recovery outcomes rather than flattening one into the other. A separately authorized protected-detail projection may disclose only reviewed, non-credential capture/evidence fields after the backend verifies the authenticated caller and exact owning tenant. Any route, log path, import, mutation, host profile, or restore path that cannot enforce this boundary must reject protected activation or the operation before it has an effect.

O1–O3 remain accepted owner policy. This E2 proposal does not qualify the E1 persistence guard, mark M1 ready, or complete E3's Studio path. Integrated E2 proof waits for the accepted E1 guard and actual E3 Studio authentication/read path; design review can proceed independently.

## Bounded M1 host profile

The proposed first E2 profile is one local Elsa 3 host with both endpoint security and tenant filtering enabled. Protected entry points require actual authentication and authorization; a declared permission is insufficient when `EndpointSecurityOptions.SecurityIsEnabled` is false because the current helper calls `AllowAnonymous` in that mode. Ordinary unprotected hosts keep their existing behavior.

For this profile, authenticate a JWT from a configured, validated issuer and read the exact tenant from its configured tenant claim. The token's tenant must match the instance's owning tenant on each protected read or mutation. A request header or route tenant is a selector only; if a trusted host/gateway supplies one, the host must bind it to the authenticated tenant or reject the mismatch. A permission wildcard never substitutes for this ownership check.

Preserve the existing, explicitly configured default-tenant null/empty normalization. A configured host default may establish that default tenant; an unknown, absent, or caller-controlled empty value may not. Asterisk-agnostic read visibility is not ownership; [ADR 0009](../../../../docs/adr/0009-asterisk-sentinel-value-for-tenant-agnostic-entities.md) documents the `*` sentinel. The first profile does not qualify API-key authentication unless the validated application record's tenant is bound and proved on the actual route. It also excludes name-only identity resolution unless uniqueness and tenant binding are proved. These are support-profile boundaries, not changes to the general authentication system.

This is a local proof profile, not a claim for multiple replicas or a distributed key service. The actual key backend and restore process remain Hosting/Security decisions and must meet the tests below before any protected workflow is enabled.

## Protection and preservation

Use a narrow internal recovery-capture adapter over the host-configured ASP.NET Data Protection provider. It protects only schema-declared, policy-approved recovery fields and uses a purpose/context chain bound to the stable values that own the capture: feature and schema version, exact tenant and workflow instance, scope/operation occurrence where applicable, and capture kind (request, known result, or bounded sanitized cause). Attempt IDs may be recorded as capture provenance but must not make a stable occurrence capture undecryptable on a later attempt. Persist an explicit schema discriminator and accept only a supported decoder/purpose; an unknown version stays blocked with its original bytes. These are proposed internal bindings, not a public API or general cryptographic platform.

Do not capture arbitrary request/result objects, exception graphs, authentication headers or tokens, resolved secret values, or unreviewed free-text response/error bodies. Preserve the existing Secrets and sensitivity policy. If a participant requires a credential, prefer re-resolving a server-side Secrets reference at use through the existing Secrets authorization; the reference is not a summary/detail field and protected-view does not grant Secrets read. If the reference/version/authorization cannot safely reproduce a required input, or a participant/mapping cannot avoid a resolved-secret snapshot, reject it before effect. The exact bounded cause fields remain for Security/Core review; until that review, the recovery cause is sanitized before generic logging/incident handling and no raw message/stack/exception graph is selected by default.

Host qualification must demonstrate a persistent key ring, stable application identity, decrypt after a new process starts, and availability of historical keys after the host's supported restore path. `AddDataProtection`, a default application name, or a persistent filesystem location alone is not evidence that the required keys can be restored or protected at rest. This design selects no key backend, cryptographic algorithm, key-retention interval, or at-rest guarantee. The existing one-key Secrets protector is not reused unchanged.

Tamper, wrong purpose/schema, wrong tenant/instance/occurrence/capture kind, and unavailable historical keys produce a typed protected-data-unavailable or blocked-admission result with a reason; exact API mapping remains open. Preserve the exact opaque protected bytes, obligation metadata, and any independently verified journal/participant outcome; do not replace them with null, an empty capture, a newly serialized default, or a different value. Capture decryption failure is not a business outcome: do not infer participant `Unknown` solely because capture data is unavailable, and do not claim a journal status that cannot be verified from the preserved bytes. Actual participant uncertainty continues to follow O1–O3 semantics. Do not log ciphertext, keys, or decrypted values in the failure path. The E1 storage guard must prevent a later ordinary save, import, or failed outer decode from overwriting those bytes. If the selected native store cannot make that preservation guarantee, reject protected activation before effects.

Treat all effect results and original causes as protected by default, while allowing only the reviewed schema-declared fields above into the recovery capture. A result capture exists only after a known participant outcome is durably accepted; absence after an unknown outcome remains unknown. Required recovery values stay bound to the original occurrence and pins. Protection does not change the journal's obligation, idempotency, or uncertainty semantics.

## Read, record, and mutation boundaries

The M1 ordinary summary is an allowlist of server-generated opaque identifiers for the instance, scope/operation occurrence, attempt, concrete execution, pinned definition/mapping version, and (when needed) cause/evidence navigation; parent/iteration ancestry; fixed code-defined phase, eligibility, capability/reason, and outcome/status codes; bounded ordinals/counts/revisions; and timestamps needed to navigate recovery. These semantic categories support occurrence-to-attempt-to-execution history and pinned-version provenance without exposing payloads or fixing DTO/route spellings. Keep forward and recovery outcomes separate. A field is not safe merely because it is a string or called a label. Keep arbitrary labels, free text, captured values, exception messages/stacks, participant URIs, outputs, properties, journal payloads, incident messages/exception state, actor claims, Secrets references, key references, ciphertext, and raw audit reasons out of ordinary summaries. An opaque cause/evidence reference is navigation only, not the cause itself. The exact public DTO remains open until a caller requires and reviews it.

Protected detail is a separate projection that returns only specifically authorized, reviewed, non-credential capture/evidence fields. It never serializes the internal `WorkflowState`, journal envelope, generic activity/incident record, or export object. It cannot return resolved Secrets material, authentication headers/tokens, arbitrary exception graphs, or an unreviewed raw cause. Authorizing detail does not waive exact tenant ownership, grant generic Secrets read, or convert unrelated generic logs into a protected-data API.

If source suppression cannot cover every ordinary copy, including an early logger or persisted incident copy, the participant or host profile is unsupported and must be rejected before the effect. Fault handling, a later `RecoverFromFault`, generic redaction work, mapper filtering, or a read mask cannot retract an exception already logged or persisted. Historical records created outside this boundary are not proof of safety and are not rewritten by this design.

## Authorization and tenant check

Recommend a distinct protected-detail verb candidate `workflows/instances/recovery-data:protected-view`, registered in the existing permission descriptor catalog and role editor if implementation review accepts it. This is recovery projection authority only; it is not generic Secrets read permission. The proposed recovery summary requires the existing `workflows/instances:view` baseline. Protected recovery detail requires that same reviewed instance baseline plus the distinct protected-view grant and exact owning-tenant authority. A caller reading a generic activity-execution record separately needs its `workflows/activity-executions:view` baseline; neither the recovery grant nor activity-executions:view grants the other resource's read. A bare role claim without an Elsa permission claim grants no read. Broad `workflows/*:view` / `workflows/instances/*:view` grants can satisfy only the baseline views they match, not protected-view; explicit native all-verb subtree/admin wildcards keep their current semantics but still require exact owning-tenant authority. The candidate does not establish a new admin model or freeze a route/DTO.

Protected detail must deny anonymous callers, bare role-only identities, `workflows/instances:view` without protected-view, protected-view without the required instance baseline, `workflows/activity-executions:view` alone, and cross-tenant known-ID lookup. It may allow the reviewed baseline-plus-detail permissions or an existing explicit all-verb wildcard when the authenticated principal is bound to the exact owning tenant. Host configuration with endpoint security disabled must fail the protected profile before reads or effect-capable activation; it must not rely on the endpoint declaration to add authorization in that configuration.

## Retention and ownership

No purge may remove an eligible, unresolved, unknown, or in-flight obligation, its required pins/capture/evidence, or a key needed to decrypt it. This holds across workflow deletion, import, backup/restore, log cleanup, and key rotation. Numeric retention, legal erasure, backup horizon, and key retirement remain Product + Hosting + Security decisions; resolve them before M5/purge support, or earlier if they make the M1 key-restore profile invalid. This proposal invents no timeout or retention duration.

Runtime/Persistence owns E1 admission and commit/opaque-preservation integration. Security + Core/Studio own the projection, permission catalog, source suppression, and exact tenant checks. Hosting + Security own persistent key configuration, stable application identity, and historical-key restore qualification. Product + Hosting + Security own lifecycle and retention policy. M4 remains the owner of operator mutation UI and does not enter this E2 contract.
